# IT 团队角色绩效评分 PRD

> 版本：v1.1
> 日期：2026-07-22
> 状态：矩阵角色绩效方案开发设计基线
> 适用范围：团队管理 → 人效评分、活动积分、学习成长（“培训提升”“学习任务”两个标签页）、岗位编制
> 说明：本 PRD 仅覆盖 CIO 以外的 IT 团队成员；加分、扣分继续沿用现有独立机制。

## 1. 背景与问题

当前 IT 团队采用“业务服务线 × 专业线”的矩阵式管理：

- 横向服务线：市场运营与销售、供应链与生产、产品研发、财经与综合服务；
- 纵向专业线：IT 产品、IT 开发、IT 运维、IT PMO；
- 平台服务角色：数据治理、AI 技术、信息安全、架构等，跨业务域提供能力。

同一名员工可能同时承担一个业务服务线角色和一个专业线角色，例如“供应链 IT 业务伙伴 + IT 产品经理”。如果只按岗位或单一直属上级评价，会出现业务价值与专业能力失衡、平台岗位无合适评价主体、项目/需求/运维工作互相不可比等问题。

现有系统已经具备：

- 按考核期计算人效分；
- 服务工单、变更、项目、需求、知识和活动积分等系统证据；
- 角色/岗位绑定的评分方案；
- 管理岗逐维度核定、加分和扣分留痕。
- 业务域、岗位、用户组和流程任务等组织/流程数据，可作为评分范围和评分主体的基础。

本次设计将现有“岗位评分方案”升级为“矩阵角色评分”，保留现有积分台账和加减分机制。

## 2. 目标与非目标

### 2.1 目标

1. 每个 IT 员工的常规绩效由业务服务线、专业线和团队贡献三部分组成。
2. 业务服务线与专业线的角色权重合计固定为 80%；团队贡献固定占 20%。
3. 每个角色独立按 100 分制设计职责维度和权重。
4. CIO 可以按考核期为每名员工配置角色权重和评分主体。
5. 系统评分提供可追溯证据，管理者可以核定，但不能无痕覆盖。
6. 把“学习成长任务完成情况”纳入活动积分和团队贡献评分。
7. 业务服务线负责人和专业线负责人分别对所管理范围进行初评；CIO 对全部评分进行终审，并直接评价各类负责人和平台服务角色。
8. 对系统无法直接取得的外部业务评价等原始事实，提供独立录入、核验、锁定和审计能力。
9. 评分发布前只对有权限的评审人开放；被评价者只查看发布后的最终结果，不查看系统初评、负责人微调、CIO 微调和外部评价明细。

### 2.2 非目标

- CIO 不纳入本套常规评分；CIO 只作为评分主体、规则配置者和最终核定者。
- 加分、扣分不并入团队贡献积分，继续使用现有 `perf_adjustment` 独立处理。
- 不以角色自动授予系统权限；权限仍由用户、用户组和权限矩阵管理。
- 平台服务角色的专业评分不交给业务线或普通专业线负责人；数据治理、AI、信息安全、架构等平台角色默认由 CIO 直接评分。

## 3. 适用人员与角色分类

评分范围沿用团队管理统一口径：仅统计在岗 IT 团队成员。业务部门人员、仅持 `requester` 或 `auditor` 的人员不进入本评分。

| 角色分类 | 角色/角色档案 | 默认评分主体 |
|---|---|---|
| 业务服务线 | `it_bm` 业务线负责人 | CIO；不得自评 |
| 业务服务线 | `it_bp` IT 业务合作伙伴 | 所属业务线负责人 + CIO（不得自评） |
| 专业线管理 | `it_tm` IT 专业线负责人 | CIO；评价专业资源池建设与管理 |
| 产品专业线 | `it_pdm_leader`、`it_pdm` | 产品负责人评价产品经理；产品负责人由 CIO 评价 |
| 项目专业线 | `it_pmo`、`it_pm` | IT PM 虚拟团队的 PMO 负责人评价项目经理；PMO 由 CIO 直评 |
| 开发专业线 | `it_dev_leader`、`it_dev` | 开发负责人评价开发人员；开发负责人由 CIO 评价 |
| 运维专业线 | `it_op_leader`、`it_ops` | 运维负责人评价运维人员；运维负责人由 CIO 评价 |
| 平台服务 | `is_mgr`、数据治理、AI、架构等平台角色 | CIO 直接评价 |
| 不纳入 | `admin`、`auditor`、`requester` | 不建立 IT 常规绩效评分 |

说明：数据治理、AI、架构等角色可以使用自定义角色码或岗位绑定的角色档案；不要求为每一个技术方向新增内置权限角色。

## 4. 总体评分模型

### 4.1 三部分构成

每个员工的常规绩效分为：

1. **业务服务线角色分**：该员工在业务服务线上的角色评分，单个角色满分 100 分。
2. **专业线角色分**：该员工在专业线或平台服务上的角色评分，单个角色满分 100 分。
3. **团队贡献分**：由活动积分按贡献维度折算，满分 100 分。

加分、扣分单独记录，不改变以上三部分的原始分值。

### 4.2 权重约束

- 当前有效业务服务线角色权重 + 当前有效专业线角色权重 = **80%**；
- 团队贡献权重 = **20%**，固定且所有成员一致，不允许个人化修改；
- 同一员工同一条线存在多个角色时，该条线内部角色权重之和必须等于该条线分配的权重；
- 只有业务角色：业务角色权重为 80%，专业角色权重为 0%；
- 只有专业/平台角色：专业角色权重为 80%，业务角色权重为 0%；
- 业务和专业角色均存在时，由 CIO 按员工实际工作投入配置，例如 35% + 45%。

### 4.3 计算公式

```text
业务角色贡献 = Σ(业务角色分 × 该角色权重)
专业角色贡献 = Σ(专业角色分 × 该角色权重)
团队贡献项 = 团队贡献分 × 20%

常规绩效分 = 业务角色贡献 + 专业角色贡献 + 团队贡献项
最终展示分 = 常规绩效分 + 加分项 - 扣分项
```

角色权重以百分数存储，例如 35 表示 35%。由于角色权重合计为 80、团队贡献为 20，常规绩效满分为 100。

示例：某员工业务角色 86 分、权重 35%；专业角色 79 分、权重 45%；团队贡献 72 分：

```text
常规绩效 = 86×35% + 79×45% + 72×20% = 80.05
若加分 5、扣分 2，则最终展示分 = 83.05
```

## 5. 评分周期与冻结规则

沿用系统现有考核周期：

- `YYYY-Q1`、`YYYY-Q2`、`YYYY-Q3`：季度考核；
- `YYYY-All`：全年考核，Q4 数据并入全年，不单独生成 Q4 评分。

考核期开始时生成员工的角色快照和角色权重快照；考核期中人员岗位、角色、部门或服务线发生变化，不影响历史周期。CIO 可以在考核期内调整权重，但发布后必须生成新版本并保留旧版本。

评分状态：

1. `draft` 草稿：配置周期、角色快照、权重和评分主体；
2. `auto_scored` 系统初评：系统完成自动取数和角色基础分计算；
3. `external_input` 外部原数据：录入和核验系统无法直接获取的业务评价等原始事实；
4. `manager_review` 负责人初评：业务线负责人和专业线负责人分别提交各自范围内的微调；
5. `cio_review` CIO 终审：CIO 查看系统分、外部原数据、负责人初评和证据，可再次微调；
6. `published` 已发布：被评价者只能查看最终结果页；
7. `locked` 已锁定：只有 CIO/admin 可以通过生成新版本重新打开，原发布版本保留。

发布前不向被评价者返回任何初评、微调和外部评价细节。已发布周期如果需要重新调整，必须建立新版本，不能静默覆盖已发布快照。

## 6. 评分主体与冲突处理

### 6.1 业务服务线评分

默认评分主体及权重：

- 普通业务服务线成员：业务线负责人 60%，支持该服务线的业务 BP 40%；
- IT 业务线负责人本人：CIO 100%；
- 业务 BP 本人：所属业务线负责人 70%，CIO 30%；
- 同一业务线存在多个 BP 时，BP 评分取有效 BP 的平均分；
- 评分主体不得给自己评分；评分主体缺席或与被评分人存在冲突时，由 CIO 指定替代人，替代过程必须留痕。

### 6.2 专业线评分

- 专业线成员：由其专业线负责人评分；IT PM 虚拟团队的 `it_pm` 资源池负责人必须具备 `it_pmo` 角色；
- 产品/开发/运维/PMO 负责人：由 CIO 评分；
- `it_tm` 专业线负责人：由 CIO 评分，重点评价资源池建设、能力培养和专业治理；
- 数据治理、AI、信息安全、架构等平台角色：由 CIO 直接评分；
- 一人兼任 `it_tm` 与某个功能负责人时，只有在 CIO 对两个角色分别配置非零权重时才分别评分；`it_tm` 只评价资源池管理，不重复评价具体交付。

### 6.3 分级评审权限

- 业务服务线负责人只能评价其负责业务域内人员的业务服务线角色；
- 专业线负责人只能评价其负责专业资源池内人员的专业线角色；
- 业务线负责人不能修改专业线评分，专业线负责人不能修改业务线评分；
- 平台服务角色默认跳过业务线/专业线负责人初评，由 CIO 直接评价；
- 负责人不得评价自己；负责人本人的业务角色、专业角色均由 CIO 评价；
- CIO 可以查看和调整全部角色评分、外部原数据折算结果和最终得分；
- 负责人不能修改团队贡献原始积分和外部原始数据，只能在被授权的角色评分范围内提交初评；
- 所有初评、终审和清除调整动作都必须记录操作者、前后分值、原因和证据。

### 6.4 评分方式

- 每个角色维度均为 0–100 分；
- 系统自动产生的客观指标提供“参考分”；
- 评分主体可以确认参考分，也可以填写核定分和说明；
- 核定分必须填写证据或评价说明；
- 同一角色由多个评分主体评分时，按评分主体权重加权平均；
- 评分主体未完成时，角色分显示“待评分”，不得偷偷按 0 分或自动改变角色权重；
- 角色内某一维度明确标记为“不适用”时，剩余有效维度按比例归一到 100；所有维度均无效时，角色分为“待评分”。

负责人初评和 CIO 终审采用“系统参考分 + 建议生效分”模式。页面必须同时展示系统参考分、当前阶段建议分和调整幅度；提交建议分时必须填写原因，必要时附证据。最终展示分只取 CIO 终审后的生效分。

### 6.5 外部原数据录入

系统无法直接获得的业务评价不得直接作为无来源的人工覆盖分。必须先录入外部原数据，再由评分规则折算到对应评分维度。

外部原数据录入字段至少包括：

| 字段 | 说明 |
|---|---|
| `period` | 考核期。 |
| `metric_code` | 当前启用的外部原数据指标为 `external_business_satisfaction`（外部业务满意度）。`internal_external_satisfaction` 是系统组合指标，不允许直接录入；`business_value_confirmation` 仅作为后续扩展预留，未纳入当前启用规则。 |
| `target_type/target_id` | 外部业务满意度固定按业务服务域录入；系统根据该域 IT 侧负责人（BM）及 IT BP 成员自动归属评分。业务 BDO 不属于 IT 人效归属对象。 |
| `evaluator_name/evaluator_department` | 系统外业务评价人的姓名和部门。 |
| `raw_score/raw_scale` | 原始评分及满分。界面建议按百分制录入（例如 86/100 表示 86%），服务端兼容 4.5/5 等量表并统一按 `raw_score / raw_scale × 100` 折算为 0–100% 的 `normalized_score`。 |
| `normalized_score` | 系统折算后的 0–100 分，只读派生值。 |
| `comment/evidence_refs` | 外部意见、问卷、邮件、会议纪要或附件。 |
| `inputter_id/status` | 录入人、草稿/已提交/已核验/已锁定。 |

外部业务满意度与 ITSM 工单满意度分开保存。业务域负责人录入 86/100、系统计算该域内部 ITSM 满意度为 92% 时，系统按当前“团队贡献与满意度组合规则”中的可配置比例计算；默认 50%+50% 时为 89%，若配置为内部 40% + 外部 60% 则为 89.6%。组合结果写入 `internal_external_satisfaction`，不产生第二条人工录入记录。业务域评价只对该域 IT 侧负责人（BM）和 IT BP 生效，不扩散给业务 BDO、其他业务部门成员、开发或运维成员。外部原数据锁定后不能直接修改，只能由 CIO 生成修订版本。

## 7. 角色评分规则（每个角色满分 100）

以下为 v1 默认规则。CIO 可以调整维度权重，但同一角色所有启用维度权重必须合计 100%。

### 7.1 业务服务线角色

#### `it_bm`：IT 业务线负责人

| 维度 | 权重 | 评分口径 |
|---|---:|---|
| 业务价值与结果 | 25% | 业务目标、系统使用效果、价值链打通和经营结果改善。 |
| 服务体验与满意度 | 20% | 业务域满意度、服务质量、关键用户反馈和重大问题闭环。 |
| 需求与服务组合治理 | 20% | 需求准入、优先级、路线图和资源投入是否与业务战略一致。 |
| 资源协调与跨域协同 | 15% | 在产品、开发、运维和外部供应商之间解决冲突、调配资源。 |
| 风险与合规 | 10% | 数据、信息安全、变更、供应商和系统生命周期风险管理。 |
| 复盘与持续改进 | 10% | 服务复盘、问题根因、改进项和改进闭环率。 |

#### `it_bp`：IT 业务合作伙伴

| 维度 | 权重 | 评分口径 |
|---|---:|---|
| 需求质量 | 25% | 需求目标、范围、优先级、验收标准和业务价值是否清晰。 |
| 业务流程与场景理解 | 20% | 能否准确梳理业务流程、痛点、角色和数据流。 |
| 业务协同与沟通 | 20% | 业务访谈、跨部门协调、预期管理和冲突处理。 |
| 验收与价值闭环 | 20% | 组织业务验收，确认上线效果并推动遗留问题关闭。 |
| 数据与主数据意识 | 10% | 是否主动识别数据口径、主数据和系统边界问题。 |
| 响应与服务 | 5% | 需求响应、跟进及时性和服务对象体验。 |

### 7.2 专业线管理与产品/项目

#### `it_tm`：IT 专业线负责人

| 维度 | 权重 | 评分口径 |
|---|---:|---|
| 专业能力建设 | 25% | 专业路线、技术/方法能力、资源池结构和能力覆盖。 |
| 资源规划与派工 | 20% | 按业务优先级、技能和负载合理配置人员。 |
| 标准与质量治理 | 20% | 专业规范、评审机制、质量门禁和复盘机制。 |
| 人才培养与梯队 | 15% | 培训、辅导、岗位成长、备份人和梯队建设。 |
| 横向协同 | 10% | 与业务服务线、其他专业线和供应商协同。 |
| 专业线运营 | 10% | 例会、指标、问题升级、知识沉淀和决策记录。 |

#### `it_pdm_leader`：IT 产品负责人

| 维度 | 权重 | 评分口径 |
|---|---:|---|
| 产品组合与路线 | 25% | 产品地图、系统边界、路线图、整合和淘汰计划。 |

## 8. 团队贡献评分规则（固定占常规绩效 20%）

### 8.1 团队贡献维度

团队贡献分满分 100，默认维度权重如下；CIO 可调整维度内部权重，但合计必须为 100%。

| 维度代码 | 维度 | 权重 | 主要来源 |
|---|---|---:|---|
| `special_activity` | 专项活动贡献 | 20% | `activity_campaign` / `campaign_task` 完成。 |
| `learning_growth` | 学习成长任务 | 20% | 学习任务、认证、技术研究、轮岗/实验任务完成。 |
| `training_knowledge` | 培训与知识分享 | 15% | 培训主讲/组织、内部分享、交叉培训。 |
| `suggestion_improvement` | 建言与流程改进 | 15% | 建言提交、点赞、采纳、流程改进落地。 |
| `knowledge_asset` | 知识资产与复盘 | 15% | 知识文章、故障复盘、根因分析、标准作业沉淀。 |
| `cross_team_support` | 跨团队协作与关键支援 | 15% | 重大事件支援、跨线协作、导师辅导和关键任务支援。 |

### 8.2 团队贡献分计算

每个维度先按目标积分折算为 0–100 分，再按维度权重加权：

```text
维度分 = min(100, max(0, 本期该维度有效积分 ÷ 该维度目标积分 × 100))
团队贡献分 = Σ(维度分 × 维度权重)
```

- 团队贡献目标积分由 CIO 在“活动积分 → 积分规则”配置；角色绩效计分规则只配置岗位职责结果的取数和权重，不按岗位族重复维护团队活动目标；
- 没有该维度贡献时计 0 分，不进行团队最高值归一化；
- 同一事件只能归入一个团队贡献维度，避免重复计分；
- 加分、扣分、管理员临时调整不进入团队贡献维度，仍在最终展示分中单独处理；
- 积分流水必须保留来源单据、事件类型、维度、周期和创建人，并保持幂等。

### 8.3 新增：学习成长目标

当前首期实现为“员工自填、系统自动折算”：员工在本人的考核周期页面维护学习成长目标、目标说明、实际完成比例、佐证和补充说明；系统保留操作审计，并允许系统管理员、CIO 和 IT 团队负责人查看团队目标。后续如需要强制验收，可在此基础上增加验收节点，不改变已保存的目标和积分流水。

任务字段建议：

| 字段 | 说明 |
|---|---|
| 目标 | 例如：完成 PostgreSQL 性能调优实验、完成安全认证课程。 |
| 目标说明/验收标准 | 说明目标范围、预期产出和可验证标准。 |
| 实际完成进度 | 0–100%，系统按同一周期目标的等权平均进度折算。 |
| 相关佐证 | 报告、代码、演示、证书、知识文章或实验记录链接/说明。 |
| 补充说明 | 完成情况、遇到的问题和后续计划。 |
| 积分 | 按学习成长维度目标积分 30 分自动折算并写入 `point_entry`，同一周期多目标总积分不超过 30 分。 |

每次保存目标或进度都会幂等更新 `learning_growth` 积分流水；同一员工同一考核期的多个目标按等权平均计算，当前实现不额外引入验收状态。

### 8.4 既有积分事件映射

| 既有事件/来源 | 团队贡献维度 |
|---|---|
| 专项活动任务完成 | `special_activity` |
| 培训主讲/组织/参与 | `training_knowledge` |
| 建言提交/点赞/采纳 | `suggestion_improvement` |
| 知识发表/被点有用 | `knowledge_asset` |
| 问题根因定位、故障复盘、标准作业 | `knowledge_asset` |
| 跨业务域关键支援、导师辅导、重大事件指挥 | `cross_team_support` |
| 学习成长任务完成 | `learning_growth` |
| Bug 修复子任务关闭 | 默认岗位结果 `role_result`，不进入团队贡献 |
| 普通委派任务关闭 | 默认岗位结果 `role_result`，不进入团队贡献 |
| 明确标记为团队贡献的技术研究/跨团队支持/知识分享任务关闭 | 分别进入 `learning_growth` / `cross_team_support` / `training_knowledge` |

### 8.5 角色结果与团队贡献的边界

现有工单、需求、项目和知识数据可能同时产生“工作结果证据”和“活动积分”。同一事实只能在一个评分桶中生效，避免角色分和团队贡献分重复计算。

- `role_result`：用于岗位职责结果，例如工单 SLA、变更合规、需求按期交付、项目里程碑和流程治理结果。该类数据只进入业务/专业角色维度，不进入固定 20% 团队贡献。活动积分读接口排除这一分桶，因此项目经理里程碑等岗位结果事件不会再次显示为团队活动积分。
- `team_contribution`：用于职责之外的专项活动、学习成长、知识分享、跨团队支援等团队贡献维度。该类积分只进入固定 20% 团队贡献。
- 活动积分、团队总览和 Dashboard 人员积分排行必须统一只读取 `team_contribution`；Dashboard 不得把 `role_result` 岗位结果流水混入人员积分排行。
- `PointRule`、`PointEntry` 必须增加 `contribution_bucket` 和 `contribution_dimension`，在积分生成时确定归属；不能在计算绩效时根据人员或结果临时改桶。
- 当前已由工单、需求、项目计算角色结果的事件，可以继续保留积分台账用于激励和追溯，但默认标记为 `role_result`，不再重复计入团队贡献。
- Bug 修复子任务完成和委派任务关闭事件分别使用 `bug_fix_task_done`、`delegated_work_done` 规则，默认标记为 `role_result`；同一来源单据只能生成一条积分流水。只有服务端允许的团队贡献任务类型，才使用对应的团队贡献规则和维度。
- `bug_fix_delivery` 和 `delegated_work_delivery` 按负责人、计划完成日期和实际关闭日期计算；未到期未关闭任务不提前扣分，到期仍未关闭或中止任务计入分母但不计入按期完成数。
- 角色结果指标使用分子/分母和实际适用范围计算，不以团队最高积分归一化；团队贡献使用配置的目标积分折算。

## 9. CIO 配置页面需求

### 9.1 角色评分规则配置

- 查看/新增/编辑角色评分档案；
- 选择角色类型、业务线/专业线/平台类型；
- 配置评分维度、权重、评分说明和证据来源；
- 同一角色启用维度权重必须合计 100%；
- 已发布周期使用历史规则快照，规则修改不重写历史结果；
- 支持设置默认规则和角色专属规则。

### 9.2 人员角色权重配置

- 按考核期查看 IT 员工、当前岗位、当前角色和所属服务线/专业线；
- 为每个员工配置业务角色权重和专业角色权重；
- 实时显示“业务角色权重 + 专业角色权重 + 团队贡献权重”；
- 不满足 80% + 20% 时禁止发布；
- 支持按岗位/角色生成默认值，再由 CIO 对个人覆盖；
- 重新取数仅在首次生成周期配置或显式恢复默认时生成自动权重；CIO/管理员手工调整后的周期权重必须保留；
- 角色、岗位或组织发生变化时，历史周期保持快照。

“人效评分 → 计分规则”页面只展示岗位职责结果规则：角色档案的维度/权重（每个角色合计 100%）、系统取数口径、流程/RACI 节点映射和人员角色权重矩阵（业务/专业角色合计 80%）。团队贡献固定 20% 的活动事件规则、六个贡献维度目标及满意度组合比例统一放在“活动积分 → 积分规则”，不在本页重复配置。系统管理员与 CIO 可编辑两类规则的对应页面，便于在正式发布前验证规则。

当前人效总览使用矩阵角色周期结果，不再按旧版 `perf_scheme` 的“默认方案”兜底或展示旧版岗位维度。读取未发布周期时，系统会将当前在岗 IT 人员的有效角色与周期快照对齐，因此新绑定的绩效角色无需等待手工重算即可显示；已发布/锁定周期保持不可变。需要新增一套非默认规则时，在“计分规则”点击“新增角色规则”创建角色档案；保存后，在周期员工详情中给员工分配该角色并设置业务/专业角色权重，角色职责权重合计必须为 80%，团队贡献固定为 20%。

### 9.3 评分工作台

- 按周期、业务服务线、专业线、角色和状态筛选；
- 显示业务角色分、专业角色分、团队贡献分、加分、扣分和最终展示分；
- 展开查看每个角色的 100 分维度、评分主体、系统参考值、核定值、说明和证据；
- 标记未评分、冲突、缺证据和待 CIO 核定；
- 支持导出明细 CSV/Excel。

### 9.4 分级评审工作台

评审工作台按评审阶段和评分范围分开呈现，服务端必须做字段级和范围级校验，不能只依赖前端隐藏按钮。

- 总览页按员工聚合为一行，展示角色概览、业务/专业角色贡献、团队贡献、常规绩效和当前总分；不再让同一员工因多个角色重复占用多行。
- 点击员工“评分明细”进入员工级详情页，集中展示该员工全部角色及每个角色的维度权重、系统参考分、负责人初评、CIO 终审/微调、生效分和修正说明；CIO/管理员可在详情页调整该员工角色权重，具备评审权限的负责人或 CIO 可逐维度评分。

| 评审人 | 可见范围 | 可修改内容 | 不可修改内容 |
|---|---|---|---|
| 业务服务线负责人 | 所负责业务域/服务线内人员 | 业务服务线角色的核定分、评价说明和证据 | 专业线分、团队贡献原始积分、外部原始数据、自己作为被评人的分数 |
| 专业线负责人 | 所负责专业资源池内人员 | 专业线角色的核定分、评价说明和证据 | 业务服务线分、团队贡献原始积分、外部原始数据、自己作为被评人的分数 |
| CIO | 全部 IT 成员及全部角色 | 全部角色分、平台角色专业维度、负责人分、外部数据折算结果和最终结果 | 不得将已发布版本静默覆盖 |
| 被评价者 | 自己已发布的最终结果 | 无 | 所有发布前初评、微调、评审人和外部评价明细 |

负责人提交初评后进入 CIO 终审；平台服务角色默认直接进入 CIO 评审。CIO 可以接受系统参考分、修改负责人初评或直接填写平台专业维度评分。每次提交都记录前后值、调整原因、证据和操作者。

### 9.5 外部原数据页面

提供独立的“外部评价与原数据”页面，供 CIO 或被授权的绩效管理员录入系统外业务负责人评分。页面支持按考核期、业务域、服务线和指标批量导入/填写，并展示原始分、满分、折算分、评价人、来源说明和附件。

- 录入、提交、核验、锁定分为不同状态；锁定后只能通过修订版本更正。
- 外部原数据页面不显示负责人内部微调内容；负责人评审页只显示经过规则折算后的参考数据。
- 外部原始数据和 ITSM 内部满意度分开存储、分开审计，CIO/系统管理员在“团队贡献与满意度组合规则”中维护两者比例，重新取数时写入周期快照。
- 页面上方必须展示当前启用规则引用的指标定义清单，明确指标编码、来源（系统自动/外部原数据/复合计算/人工评审）、取数方式、计算口径及使用角色；只有“外部业务满意度”这类外部原始指标进入本页录入，“内外部满意度”属于系统组合指标，不得直接录入。
- 外部业务满意度按业务服务域录入，目标必须选择业务域而不是手工输入人员 ID；该业务域评价只折算给该域 IT 侧负责人（BM）和 IT BP，不扩散给业务 BDO、其他业务部门成员或其他 IT 专业线人员。
- 外部原数据录入后，系统管理员和具备权限的 CIO 可在清单页直接编辑或删除；状态为“已锁定”的记录只读，必须通过生成修订版本调整，所有修改和删除均保留审计记录。

### 9.6 员工最终结果页

被评价者只能访问 `/api/my/performance` 对应的已发布结果。结果页展示角色名称、角色得分、团队贡献分、加扣分和最终展示分；不展示系统参考分、负责人核定分、CIO 调整前后值、外部评价人及外部评价原文。周期未发布时显示“结果尚未发布”，不得返回草稿或评审中数据。

## 10. 数据模型与接口建议

本节为 coding agent 的设计输入，实际表名可按现有模型风格调整。

### 10.1 建议数据对象

| 对象 | 用途 |
|---|---|
| `performance_period` | 考核期、版本、状态、发布时间和锁定信息。 |
| `performance_role_profile` | 角色档案、适用角色码、线类型、是否平台角色和说明。 |
| `performance_role_dimension` | 角色维度、权重、评分方式、证据配置和排序。 |
| `performance_role_assignment` | 周期内人员角色快照、业务/专业线类型、角色权重、评分范围、评分主体和 `review_mode`。 |
| `performance_external_input` | 系统外获取的原始业务评价、原始量表、评价人、证据、折算分和锁定状态。 |
| `performance_score_component` | 角色-维度的系统参考分、业务负责人初评分、专业负责人初评分、CIO 终评分和生效分。 |
| `performance_review_action` | 初评、终审、提交、退回、发布、解锁和修订的追加式审计记录。 |
| `performance_score` | 周期版本发布后的角色分、团队贡献分、常规绩效和最终展示分快照。 |
| `learning_growth_goal` | 员工按考核期填写的学习成长目标、完成比例、佐证、说明和折算积分。 |
| `point_entry` | 学习成长目标按周期写入 `learning_growth` 团队贡献维度的积分流水。 |

### 10.2 现有对象的演进

- `perf_scheme`：建议迁移为角色档案/角色维度，或增加 `binding_type=role`；保留旧方案读取能力，发布新周期时不再按岗位唯一匹配。
- `perf_override`：不再作为无范围的覆盖分使用；建议迁移为带阶段和角色范围的 `performance_score_component`，保留历史数据只读展示。
- `point_rule`：增加 `contribution_bucket`、`contribution_dimension`、目标积分适用范围和启停状态。
- `point_entry`：增加 `contribution_bucket`、`contribution_dimension`、考核期和幂等键；学习任务完成后写入来源任务和考核期。
- `PerfAdjustment`：保持现有加分/扣分逻辑，不进入团队贡献分。

### 10.3 接口建议

```text
GET/POST/PATCH /api/admin/performance/role-profiles
PUT /api/admin/performance/role-profiles/{id}/dimensions
GET/PUT /api/admin/performance/assignments?period=YYYY-Qn
GET /api/admin/performance/reviews?period=YYYY-Qn
GET /api/admin/performance/reviews/person/{person_id}?period=YYYY-Qn
PUT /api/admin/performance/reviews/{assignment_id}/components/{dimension_code}
GET/POST/PATCH /api/admin/performance/external-inputs
GET /api/admin/performance/external-inputs?period=YYYY-Qn
GET /api/admin/performance/metric-definitions
POST /api/admin/performance/{period}/recompute
POST /api/admin/performance/{period}/submit-manager-review
POST /api/admin/performance/{period}/submit-cio-review
POST /api/admin/performance/{period}/publish
POST /api/admin/performance/{period}/unlock
GET /api/my/performance?period=YYYY-Qn
GET/POST/PATCH/DELETE /api/team/learning-growth?period=YYYY-Qn&scope=mine|team
GET/PUT /api/point-rules/team-config
GET/PUT /api/admin/performance/contribution-rules  # 旧客户端兼容入口，规范入口为上行接口
```

所有写接口必须：

- 校验操作者权限和评审阶段：业务负责人只能修改业务角色，专业负责人只能修改专业角色，平台角色和负责人本人只能由 CIO 修改；
- 评审工作台接口返回内部明细，`/api/my/performance` 只返回已发布最终结果；
- 校验人员属于 IT 团队；
- 校验权重范围和总和；
- 校验外部原数据的原始分、满分、评价主体和附件，折算分由服务端计算；
- 写入审计日志；
- 发布后禁止静默修改历史分数；
- 对积分事件、学习任务完成事件和重新计算保持幂等；
- 同一来源事实只能落入 `role_result` 或 `team_contribution` 一个桶。

## 11. 验收标准

1. CIO 以外的在岗 IT 员工均能根据当前角色生成评分任务；无有效角色时明确显示“未配置角色”，不自动套用错误方案。
2. 角色评分档案中每个启用角色的维度权重合计 100%。
3. 每名员工当前有效业务/专业角色权重合计 80%，团队贡献固定为 20%。
4. 一人同时拥有业务角色和专业角色时，两条评分链路都能独立展示和追溯。
5. 业务服务线评分能够区分业务线负责人和 BP 的评分贡献，并禁止自评。
6. 产品、开发、运维、PMO 成员由对应专业线负责人评分；专业线负责人和平台角色由 CIO 评分。
7. 学习成长目标的进度由员工在周期内维护，系统自动产生积分并计入 `learning_growth`，同周期积分不超过 30 分。
8. 团队贡献分不再依赖“团队最高积分”，而是按配置目标积分折算，跨周期可比较。
9. 加分、扣分仍独立展示，且不会改变三部分常规绩效的权重结构。
10. 角色变更、评分主体替换、分数核定、发布、解锁和重新发布均有审计记录。
11. 历史周期的角色、权重、规则和评分结果可重现、可导出。
12. 业务服务线负责人只能修改其业务范围内的业务角色分，专业线负责人只能修改其专业范围内的专业角色分，且任何负责人不能评价自己。
13. CIO 可以调整全部人员评分，并能直接填写平台服务角色和各类负责人自己的专业/业务评分。
14. 系统自动计算结果、负责人初评、CIO 终审和最终生效分分别保存，能够展示调整前后值、原因和证据。
14a. 同一角色存在多个评审人时，各评审人独立保存评分、理由和佐证，按周期快照中的 `evaluator_weights` 加权生成负责人初评，不再覆盖为单一无来源分值。
15. 外部业务满意度等系统外原数据可独立录入、核验、锁定和修订，且与 ITSM 内部满意度分开保存。
16. 平台服务角色默认 `review_mode=cio_direct`，不生成普通负责人初评任务；系统已有客观数据只作为 CIO 参考分。
17. 被评价者在发布前无法访问任何评分明细；发布后只能访问自己的最终结果，无法看到微调页面和外部评价明细。
18. 工单、需求、项目和流程事实用于角色结果时，不会再次进入团队贡献 20%；团队贡献按目标积分折算，不使用团队最高值归一化。
19. 发布后解锁会生成新版本，旧版本保持只读且结果可重现。
