## 1. 产品概述

### 1.1 产品定位

ITOM 是一套面向 IT 团队的**轻量运营管理平台**，覆盖总览、ITSM 服务管理、项目管理、需求管理、流程引擎、团队管理，并以统一报表中心提供跨域分析与正式报告。

### 1.2 设计原则（全系统强制约束）

1. **极简录入**：任何创建表单必填项 ≤ 8（实际全部做到 ≤ 5）；进阶字段默认折叠；与生命周期后期相关的字段在对应阶段才出现。
2. **派生数据零录入**：一切可计算的数据（编号、SLA、进度、健康度、成本汇总、积分、排行、达成率）由系统自动生成，页面上没有录入入口。
3. **渐进披露**：表单只在需要时展开（如工单选"变更"类型才出现变更字段）。
4. **事件驱动**：关键动作统一产生领域事件，驱动通知（预留飞书）与积分。
5. **实时指标无预计算表**：看板和分析指标从领域事实实时聚合，不维护人工统计台账；只有用户明确生成并进入审核/发布链路的正式报告才保存不可变版本快照，用于审计和复现。

### 1.3 不做什么（明确排除）

- 组合治理独立域（阶段门/收益实现/能力地图/路线图）——组合仅作为项目的分组标签
- 数据治理域、组织成熟度评估、OCM
- ITSM 持续改进（CSI）、知识评审流、CAB 独立评审装置、ISO27001 安全事件字段
- 需求的版本快照、多人审批流、调研会话、三维打分
- 项目的干系人矩阵、基线管理、质量指标页、完整 EVM 录入
- 通用 AI Agent 注册市场、n8n 外部工作流引擎（流程能力内置实现，事件出口预留挂接点，见第 8 章）。已确认的飞书 Aily Agent + MCP Server 是员工服务入口而非通用 Agent 平台；飞书组织同步、扫码认证、工作台免登及账号绑定继续保留。
- 数据迁移（空库启动）

### 2.1a 矩阵式组织角色（M3.6，2026-07-11 增补，详见 docs/06 §六/§七）

- 内置角色定稿 **17 个**：包含 `admin`、`cio`、`it_bm`、`it_tm`、`it_pdm`、`it_pdm_leader`、`it_pm`、`it_pmo`、`it_dev`、`it_dev_leader`、`it_ops`、`it_op_leader`、`is_mgr`、`it_bp`、`auditor`、`bdo`、`requester`。**内置角色名称/描述可编辑**（代码/继承/删除锁定）。BDO 是业务用户的受控子集，业务部门手工指定，承诺投入 10%–30% 时间开展数字化协作。
- **功能权限矩阵**：系统模块 × 4 动作（可见/新建/修改/删除）按角色配置（系统管理→权限配置页）；admin 隐式全权不可配；自定义角色创建时复制模板角色矩阵。三层权限分工：功能矩阵管页面开关、数据范围规则代码内置、流程权限在状态机/流程定义页。
- 业务域=横向服务线：IT 侧负责人（BM）+ 服务团队成员 + 业务侧 BDO；用户组=纵向专业线资源池：负责人（TM）+ 组授予角色。BM 负责 IT 侧评审和服务协调，业务 BDO 负责本业务域的需求澄清、UAT 与业务闭环。

### 2.2 自定义角色与用户组（2026-07-10 增补，M3.5 扩展）

- **内置角色**（共 17 个）：承载系统功能权限，代码只读不可删改；名称和描述可维护。auditor = 全模块只读 + 审计日志查看，不能修改任何单据（仅持有 auditor 的用户受全局只读限制；auditor+其他角色不受限）。
- **自定义角色**：admin 可创建，必须**继承一个内置角色**（获得其系统权限，不允许继承 admin），同时可被状态机流转规则和流程步骤精确引用（如自定义"DBA"继承 it_ops，变更审批仅限 DBA）。被用户持有或被流程/状态机引用的角色不可删除。
- **用户组**：团队/派单单位（如"数据库组"），**可授予角色——人进组自动继承组的角色**（对齐 ServiceNow"角色挂组"最佳实践；admin 不允许经组授予）；同时用作流程步骤默认指派对象和状态机流转的授权对象（引用键格式 `group:组码`）。被引用的组不可删除。
- **有效角色 = 直接角色 ∪ 组授予角色 ∪ 自定义角色继承**；用户永远可持有多个角色，任何规则都不得将用户绑死在单一角色上。

### 2.2a 身份与组织（M3.5，详见 docs/06）

- **部门**：公司组织架构（一人一部门，树形，类型 it/business/audit），纯数据不带权限；飞书已作为人员与部门主数据源，本地记录仍支持过渡性手工维护。
- **账号开通（JIT）**：local 与飞书认证已实现（ad/sms/wechat 预留）；飞书新身份认证成功后，已同步且属于非 IT 范围的业务人员在邮箱合法、人员与用户名无冲突时自动创建账号，用户名取邮箱 `@` 前缀并初始化 `requester/业务用户`；其他身份仍创建待审批开通请求，由管理员从全公司有效人员主数据中关联人员、设置用户名/角色/语言后开通。账号覆盖 IT 与业务用户，不受数字化 IT 团队范围限制。自动开户只在首次创建时设置角色，冲突或无法匹配时不得自动接管现有账号。
- **业务域/服务线**：编码/名称/IT 侧负责人（BM）/业务 BDO/服务团队/服务部门——BM 与 BDO 都是字段，不以“负责人”字段替代角色。业务 BDO 必须是已启用、已授予 `bdo` 角色且归属该业务域服务部门范围内的业务人员；旧 `backup_owner_id` 仅为升级历史兼容保留，不再读写或用于新业务。

### 2.3 权限要点

- 登录后按角色渲染菜单；接口层同步校验（前端隐藏 ≠ 权限）。
- 流程引擎的步骤默认指派可引用：内置角色、自定义角色（含继承匹配）、用户组，如：需求评审→it_bm、方案评估→it_pdm_leader、项目节点→it_pm、变更申请/实施→it_ops、变更审批→it_op_leader、变更复盘→is_mgr、需求开发任务→it_dev_leader。
- 状态机每条流转规则可限定允许的角色/用户组（留空=不限）。
- 人效评审明细按业务/专业线负责人范围和 CIO 终审权限开放；被评价者只能查看已发布的本人最终结果，成员仍可查看自己的积分流水与排行榜。
- 岗位编制默认由 admin/cio 维护，岗位定义与招聘需求均具备查看、编辑、删除权限；页面清单支持行内编辑保存。
- 审计：所有写操作记录审计日志（操作人/时间/实体/动作/变更摘要）；admin 与 is_mgr 可查。

### 2.4 账号治理与个人中心（M36–M37）

- **账号删除**：具备用户删除权限的管理员可软删除账号并解绑关联人员；人员主数据、部门归属和历史单据不删除。内置 `admin` 与当前登录账号不可删除；删除后释放原用户名，允许后续重新开通。
- **账号与人员关联/解绑**：用户管理和飞书开通审批可从全公司未删除人员中选择关联对象；数字化 IT 团队范围只约束 IT 工作分派、资源池和绩效对象，不约束登录账号。用户列表直接返回关联人员姓名和部门，不能把内部 `person_id` 当显示名。管理员清空“关联人员”并保存后，账号的 `person_id` 必须置空；PATCH 未提交该字段时保持原关联不变。
- **飞书认证**：支持浏览器扫码 OAuth 与飞书工作台 JSAPI 免登；两者复用身份匹配、首次开通审批和正式登录逻辑。
- **Aily + MCP 身份入口（P0 已实现）**：Aily 首次注册自定义 MCP 时，`initialize`、`tools/list` 等只读协议发现请求只在 MCP 已启用且 Origin 命中白名单时开放，因为 Aily 在创建完成后才展示 `identityJWTSecret`；任何 `tools/call` 都必须通过 `x-aily-jwt` 的 HS256 签名、有效期和租户/Agent 白名单校验，再按提供方、租户、应用及外部用户标识映射到活动 ITOM 账号，最后执行 RBAC、数据范围和流程校验。服务端兼容官方文档的 `user_id` 和 2026-07-29 真实租户请求中的 `feishu_open_id`；不同飞书应用的 `open_id` 不视为天然相同。
- **Aily 业务用户边界（P1 已实现）**：普通业务用户只可通过 Aily 创建 IT 服务请求；仅业务部门指定的 BDO 可登记和查看本人 IT 需求。网页需求模块另按 BDO 职责提供“本人需求 + 其作为业务 BDO 的服务域全部需求”的数据范围，但不得据此扩大 Aily/MCP 本人数据边界。服务请求固定落为 `service_request`；IT 需求写入独立 `Requirement` 实体。业务用户和 BDO 均不获得需求评审、项目创建或内部流程管理权限。
- **写操作确认与审计（P1 已启用）**：写工具采用“预览 → 用户确认 → 确认凭证 + 幂等键提交”，凭证绑定用户、工具、规范化参数摘要和有效期；重复调用返回首次结果。App Secret、JWT Secret、内部备注或敏感组织信息不得进入模型上下文或工具审计。
- **个人中心**：用户可查看账号来源、有效角色、创建/最近登录时间及关联人员主数据；HR 字段只读，由飞书组织同步维护。
- **安全设置**：本地账号及已设置过密码的账号修改密码时必须校验当前密码；飞书开通账号的随机初始口令不可知，首次自设本地密码免验当前密码。新密码至少 8 位且同时包含字母和数字。
- **飞书绑定管理**：登录用户可绑定或换绑飞书身份；同一飞书身份不可绑定多个账号。解绑前必须先设置本地密码，确保仍有可用登录方式，且解绑不影响人员主数据关联。
- **初始密码治理（M44）**：管理员批准飞书登录申请时生成 12 位高强度密码，仅保存可恢复加密密文，不自动发送。用户详情默认隐藏，管理员点击眼睛后才解密查看，点击“邮件发送”才投递到关联人员邮箱；两项操作写审计。用户改密或管理员重置后清除初始密码密文。
- **系统集成（M44）**：系统管理下统一提供飞书、邮件服务器、AD/LDAP 三个标签页。SMTP 与 LDAP 绑定密码加密保存；LDAP 支持连接测试及同名 ITOM 活动账号的目录密码认证，角色权限继续由 ITOM 管理。
- **个人设置**：支持头像、个人说明、语言、通知分类偏好、浅色/深色/跟随系统主题、默认/紧凑内容密度；偏好按账号持久化并在登录后应用。方案 C 工作台与方案 F 门户均将当前主题状态直接绑定到应用壳层；深色主题统一采用画布、页头、模块三级深灰表面而非白色外壳或纯黑画布，导航、标签页、分段选择器及其他交互状态使用配套深色配色，并满足清晰可读的文字对比度。
- **帮助中心式操作手册**：当前重制期内，顶栏“操作手册”及 `/user-manual` 仅 `admin` 可见和访问；其他角色即使直接访问旧链接也重定向到自身首个授权页面。正式手册重做完成后再重新评估开放范围；内容与 `docs/用户操作手册.md` 同步维护。
- **个人操作记录**：用户仅能查看自己的审计记录，不暴露其他账号的审计数据。

## 3. 全局约定

**清单表头、横向访问、固定列、操作入口与可调列宽**：主页面统一清单组件必须把吸顶表头绑定到 `.app-content`。普通清单默认冻结前两个可见业务字段；复选框若存在也固定，但不计入两个业务字段，且保护字段不能在列设置中隐藏。WBS 继续使用专用前三列冻结、层级、选择和列宽/行高逻辑。普通清单与 WBS 共用一个横向滚动控制器；只有与 `.app-content` 横纵相交的活动宽表才显示一条浏览器原生悬浮横向滚动条，真实表体始终保留 `overflow-x:auto` 兜底。左/右固定单元格必须使用不透明表头、正文和悬停背景及边界阴影，屏幕外字段不得透出或拦截操作。每个可见表头分隔线支持鼠标拖拽和键盘微调；拖动中必须同步更新吸顶/普通表头、固定列和全部数据行对应的 `colgroup`，不得出现表头与表体错位。滚动宽度取当前显示列宽之和，禁止 `max-content` 按长文本固有宽度再次放大；容器多余宽度只分配给标题、描述等内容列，编号、状态、负责人、年份等短字段保持配置宽度。列宽和可见性按账号、路由、列集合保存。操作列按当前结果集最大可见操作数压缩到 64–176px并保留 Tooltip/`aria-label`；勾选后才显示带文字的上下文批量操作。

### 3.1 单据编号与主键

- 所有实体主键为 26 位 GLID（系统生成）。
- 业务编号自动生成，规则：`前缀-年月-序号`，如 `TK-202607-0012`（工单）、`PJ-202607-003`（项目）、`RQ-202607-021`（需求）、`PB/KB/ID` 等。用户永远不手填编号。

### 3.2 状态机

每类单据的状态流转由状态机配置驱动（admin 可调整），非法跳转被后端拒绝。各实体默认状态机见对应章节。

### 3.3 通知

- 统一事件出口：工单创建/指派/SLA 临期/升级、变更待审批、里程碑逾期、需求阶段流转、建言被采纳等事件写入通知发件箱。
- 进入统一 `notifier.notify()` 出口的 ITOM 通知同时支持站内通知和可靠飞书机器人文本消息。消息按 `work`、`workflow`、`system` 三类通知偏好过滤，并按 ITOM 账号入队；事件、实体和账号生成稳定幂等键，消息在业务事务内写入 `notification_outbox(channel=feishu_aily)`。账号尚未建立活动、已验证的 Aily 机器人身份时，发件箱仍保留 `pending`，payload 只保存内部 `auth_user_id`，并以 `AILY_IDENTITY_NOT_MAPPED` 作为可观测原因；后台工作器在发送前重新解析身份，映射补齐后再投递，不伪造收件人、不消耗身份等待期间的重试次数。已开通账号通过 ITOM 配置的飞书 OAuth 正常登录后，系统使用验真响应中的 `tenant_key + user_id` 自动建立机器人应用出站映射；未取得 `user_id` 时回退 `union_id`。首个经正常 OAuth 和审计建立的机器人应用映射作为唯一租户锚点；后台发送其他在岗、已关联飞书同步人员的待发消息时，可用登录应用 `open_id` 查询通讯录的租户级 `user_id`，按需自动建立同一机器人应用映射并立即投递，因此不要求每名员工分别重新登录或由管理员逐人绑定。Aily MCP JWT 的租户白名单只约束 MCP 入站调用，不再错误阻断已验真的出站通知映射。不同应用的 `open_id` 仍不作为机器人收件标识，停用、冲突、离职、未关联人员或多租户歧义映射不会被自动覆盖。机器人未启用时不新增待发记录，配置不完整时保留 `pending`。服务请求受理、解决、重开、关闭和评价仍由专用订阅发送交互卡片或回退文本，通用出口跳过 `ticket.resolved`，避免重复消息；普通业务通知使用文本，不绕过 ITOM 领域权限、审计和流程。MCP 本身不承担后台主动唤醒。
- **单据删除与历史通知**：删除流程驱动单据时，系统先将未完成流程任务以“单据已撤回或删除”完成收尾，再把流程实例、任务和单据软删除并保留审计。已经投递到飞书/Aily 的历史文本不能远程撤回；其中的详情链接若被点击，系统返回明确的 `TICKET_DELETED` 提示，不泄漏已删除单据内容，也不继续显示运行中的待办。
- M34 起，未关联人员档案的管理员账号也可通过账号 ID 接收开通申请等管理通知；铃铛定时轮询新通知并按 `work`、`workflow`、`system` 三类个人偏好过滤。
- 通知弹窗提供“一键已读”和“清除已读”：前者只更新当前账号可见通知的 `read_at` 回执，后者以软删除方式清理当前账号已读通知；两者都不影响源业务单据。

## 5. 域二：ITSM 服务管理

### 5.1 工单（核心，单表多类型）

ITOM 内部工单类型仍为 **事件 incident / 服务请求 service_request / 变更 change**，问题是独立实体（5.2）。普通业务用户在网页和 Aily 中只能创建服务请求；事件仅限 IT 人员登记或监控系统通过专用集成身份创建，变更仅限授权 IT 角色。单个用户的软件、设备、网络访问、账号权限和使用异常均归为服务请求，不归为 IT 事件。

### 5.1a IT 员工分流、单据说明与跨单据关联（阶段 A/B/C 已实现）

普通业务员工的入口保持为飞书 Aily：普通业务用户只能创建服务请求，业务部门指定的 BDO 才能登记 IT 需求；本节不得改变 Aily 的 MCP 工具、查询、确认、重开和评价边界。IT 员工**和系统管理员**网页均提供全局“创建单据指引”入口，以 2–4 个**不落库**的临时问题给出可改选的规则推荐，最终仍进入目标单据现有创建表单。服务端根据当前用户实际创建权限过滤可访问入口。推荐优先级为：大范围影响→事件；反复/根因→问题；计划生产修改且涉及风险、回退或窗口→变更；新系统/功能/优化/重构→IT 需求；其他已有能力的个人故障、协助或申请→服务请求。

六类单据的列表、详情和创建表单已提供默认一行的“适用场景 + 正例”说明和“查看示例”入口；详细案例库包含定义、适用/非适用场景、典型例子与常见误选去向。不得增加持久化的分类问卷字段或不必要选填项。

需要升级或转出的场景采用“**创建目标单据 + 关联 + 保留原单据**”：服务请求→事件（`upgraded_to_incident`）、服务请求/事件→问题（`root_cause_of`）、事件/问题→变更（`remediated_by_change`）、IT 需求→项目（`converted_to_project`）。阶段 B 已上线通用关系的增量模型、不可变审计、幂等与双方可见性裁剪，并在服务请求/事件/变更、问题、需求、项目详情显示双向关系；既有专用关联不迁移或覆盖。作为后来加入既有详情页的独立面板，“关联单据”统一放在原有可见业务内容之后的页面底部；需求和工单详情同时存在投入台账时，两者组成底部新增内容区，不穿插原有详情流程。阶段 C 已提供“准备 → 补齐目标表单 → 创建并关联”的四条提交路径：先复核来源查看范围与目标 `create` 权限；再调用目标领域服务的真实字段校验、流程、通知和审计；最后在同一事务写关系。来源行锁与提交摘要令同一操作者、来源、目标类型和幂等键的重试返回首次目标，同键异参返回冲突。源单据不得改类型、删除、强制关闭或覆盖。详见 `docs/superpowers/specs/2026-07-31-it-staff-intake-and-record-relations-design.md`。

#### 创建表单

#### 生命周期与状态机

```text
事件/服务请求：新建 → 处理中 → 已解决 → 已关闭
                ↘ 挂起 ⇄ 处理中          ↘ 重开 → 处理中
变更：新建 → 待审批 → 已批准 → 实施中 → 已解决 → 已关闭
              ↘ 已拒绝(终态)                ↘ 已回退 → 已关闭
```

**当前已发布的变更流程定义（运行时基线）**：以流程中心中激活的 `change_flow` 为准，当前为四步，不把代码种子或旧版文档当成运行时事实：

`变更申请（it_ops，处理） → 变更审批（it_op_leader，审批；知会 it_bm） → 实施与验证（it_ops，处理） → 变更复盘(PIR)（is_mgr，处理；知会 cio）`

其中，变更申请和实施任务由 IT 运维处理；审批节点的默认任务处理人是 IT 运维负责人，不等同于状态机允许的全部审批角色。状态机当前允许 `cio`、`it_tm`、`it_op_leader` 对 `pending_approval` 执行批准/拒绝。运行时流程定义、状态机配置和已发布版本优先于 `seed_itsm.py` 的新环境初始化种子；如需修改节点，必须在流程中心另存新版本，历史实例继续使用原版本快照。

- **解决时**填写：解决方案（必填）、根因（可选）。
- **解决与关闭**：IT 人员提交解决方案后工单进入 `resolved`（待用户确认），不自动等同于关闭。提交人确认已解决后进入 `closed`；确认未解决则回到 `processing` 并增加重开次数。重开后的下一次解决必须以本轮最新有效处理任务说明刷新面向用户的解决说明，已软删除的历史任务不参与选择。关闭后 Aily/网页发起 1–5 星评价，可带标签和文字意见；每张工单仅一条有效评价，修改留审计。
- 变更审批：当前已发布的 `change_flow` 将“变更审批”任务默认指派给 `it_op_leader`；状态机 `pending_approval → approved/rejected` 的 `allowed_roles` 为 `[cio, it_tm, it_op_leader]`（可在状态机配置中调整）。审批附意见并记录审批人与时间；流程任务守卫与状态机授权需同时通过。
- 升级：P1/P2 工单超 SLA 目标 80% 未解决时产生升级通知。

### 5.3 服务目录

两层结构：**目录**（分类，Gold/Silver/Bronze 分级）→ **服务项**。

- 服务项基础字段：名称✔、所属目录✔、服务类型、负责人、描述、SLA 响应/解决时限、服务对象、状态和自动编号。P1 已增加搜索关键词/同义表达、典型场景、排除场景、当前表单版本、绑定流程、分层派单规则和默认优先级；管理员/CIO 可在服务目录页通过“表单/派单”可视化维护并发布新版本。派单分为**受理**与**实施交付**两个阶段：受理规则保持原有服务项→目录→全局解析；实施规则同样按该顺序解析，但仅在首个受理节点完成、且受理人明确选择“自动分配”时生效。是否审批由绑定流程的审批节点实时计算，不另存一份易漂移布尔值。
- 服务项表单版本化。P1 已支持文本、长文本、单选、多选、数字、日期/日期时间、人员、部门和布尔项；附件及资产/CI 字段后续扩展。字段可定义必填、长度/范围、选项、人员范围和条件规则。历史工单保存答案和表单定义快照，服务项改版不重写历史语义。
- 服务对象为结构化范围：可选“全体员工”或“自定义范围”；自定义范围从组织架构中选择部门和在岗员工，服务项保存时校验引用有效，并保留可读摘要兼容列表、搜索和历史记录。业务用户服务门户和服务请求创建接口均按范围进行后端校验；管理员及 IT 内部角色不受该业务用户范围过滤影响。
- 服务项年度工单量为实时统计展示，不录入。
- 管理员/CIO可在目录与服务项清单中直接上架或下架（上下箭头按钮）；目录下架不会删除历史服务项，服务项下架后不再出现在业务用户服务门户。
- 服务项清单支持关键字搜索、按上架状态筛选（全部/上架中/已下架）、点击任意业务字段表头排序，并提供目录浏览前进/返回操作；左侧目录同时展示每个目录的上架中/已下架服务项数量；系统所有表格统一支持可点击表头排序。
- 服务目录管理卡片的目录名称保持单行并在空间不足时省略；编号/数量/状态元数据单行省略，行级操作位于底部单行工具栏，不得把中文名称压缩成逐字竖排或形成高卡片。
- 删除目录时，管理员可在二次确认后级联软删除该目录下的服务项；历史工单、项目和配置项保留原服务项引用，不因目录清理而破坏审计链路。
- **统一表格交互标准**：凡展示业务记录的表格，必须提供关键字搜索、按核心字段及其值筛选、点击表头排序；行级操作使用图标按钮及悬停说明。支持批量写操作的清单在左侧提供复选框和表头全选；未勾选时不占用顶部空间，勾选后在顶部显示该页面原本具备且当前所选记录允许的批量删除、暂停、关闭、重启等动作。已接入批量写入的可编辑主数据（服务目录/服务项、CMDB、供应商、合同、需求、岗位定义、招聘需求、WBS）提供 Excel 模板下载、填写后批量导入及逐行错误反馈。其余系统配置与事务单据仍使用详情表单逐条维护；只读审计、流程运行态和计算结果表提供当前结果导出，但不允许反向导入覆盖系统计算结果。

- 维护权限由权限矩阵控制（默认 cio/admin）；全员可浏览（作为报单入口参考）。

### 6.3 WBS 任务

- 创建 4 必填：任务名、负责人、开始/结束日期；可选：描述、交付物、前置任务。
- WBS 层级编码自动生成（按树位置）；完成度提供 0%/50%/100% 预设下拉，同时支持录入 0-100% 的自定义整数，状态按完成度与计划结束日自动计算（0% 未开始、100% 已完成、其余为进行中/已延期）。显式将任一父项设为 100% 时，所有后代任务自动设为 100%；修改子项后，父项按直接子项完成度的算术平均值逐级回算，项目整体进度仅对末级任务按工期加权，避免父子重复计权。
- 编辑 WBS 时，填写不晚于当天且不早于实际开始日的实际结束日期会自动把任务完成度更新为 100%，状态显示“已完成”；实际结束日期禁止选择或提交未来日期。当前完成度为 100% 时，实际开始和实际结束均锁定；必须先用一次独立请求把完成度调低到 100% 以下完成“重新打开”，系统清空 `actual_end`、保留首次完成审计时间 `completed_at`，之后才可另行修改实际日期。同一请求同时降低完成度和修改实际日期时拒绝并提示“请先重新打开任务，再修改实际日期”。
- 项目进度在甘特图上方增加“项目阶段进展”横向节点线，节点取 WBS 一级任务名称并显示完成度与状态；阶段数据实时派生，不新增第二套项目阶段主数据。
- WBS 宽表提供 Excel 式冻结窗格：纵向滚动时表头固定，横向滚动时左侧前三列固定；它复用全局唯一的浏览器原生底部悬浮横向滚动条及表内原生兜底，不得再创建第二条滚动条或第二份同步状态。用户可拖拽表头分隔线调整列宽、拖拽行底边调整行高，布局按项目保存在当前浏览器。
- WBS 表格底部提供“显示行数”50（默认）、100、200、全部，并显示“当前显示 X / 总计 Y”。50/100/200 模式同时提供页码和前后翻页；页码按 WBS 深度优先顺序中的目标行计算，例如总计 75、每页 50 时，第 2 页以第 51–75 行为目标。若目标行包含子任务，当前页必须额外补齐其全部祖先，补齐行不占分页名额，因此 X 可以略大于页大小。切换页码或行数不得破坏树形展开、跨页选择/全选、批量操作、列设置、固定表头或横向滚动。
- 所有主页面业务清单纵向滚动时表头保持在内容区顶部可见；默认列宽必须同时容纳表头与当前已加载数据的真实渲染内容，自动宽度下表头和数据均不得换行、截断或显示省略号，当前列全为空时以表头完整单行宽度为下限。短表按自然宽度紧凑展示，不把容器余量分摊到列内；宽表按当前可见列宽之和形成横向范围。所有超出内容区宽度的表格仅在当前活动宽表实际进入 `.app-content` 可视区时显示全局唯一的浏览器原生底部横向滚动条，即使尚未滚动到清单最后一行也能访问屏幕外字段。悬浮条与正文双向同步，正文不得切换为 `overflow:hidden`；表内原生横向能力必须始终作为兜底。表头使用 `.app-content` 作为定位容器；普通清单默认冻结前两个业务列，WBS 额外保留专用前三列冻结。用户拖拽后的列宽覆盖自动宽度，“恢复默认”清除手工覆盖并按当前数据重新测量。
- WBS 清单左侧提供逐行勾选与表头全选；勾选父任务会联动选择其全部可操作后代，取消任一分支后祖先显示半选/未选，选择结果跨页保留。无删除权限或当前完成度为 100% 的任务禁用复选框且不进入联选结果。勾选后顶部显示受控“批量删除”，逐项复用单条删除校验并回显部分成功和拒绝原因。拖动未选行时移动该行及其完整子树；拖动已选行时按当前树序原子移动全部选中根（父子同时选中只保留最高层根），目标行提供“之前/作为子任务/之后”三个落点；原“调整层级”窗口继续作为键盘和精确选择的兜底。当前完成度为 100% 的任务不可删除、增加子任务或调整层级/排序；`completed_at` 只保留首次确认完成的审计事实，不作为永久锁。经授权把完成度纠正到 100% 以下后，页面必须重新读取服务端能力并立即恢复该任务允许的删除、增加子任务和结构调整操作。结构调整仍不得移动任何当前已完成任务或包含已完成后代的子树，也不得破坏已完成同级的既有编码；服务端在同一事务重新校验权限、项目范围、引用、完成锁、目标层级和循环关系，任一根无效则整批回滚，成功后原子重算受影响同级顺序及 WBS 编码并逐根保留审计。
- WBS 的“阶段”和“操作”列按最小可用宽度展示，操作按钮使用紧凑图标并提供悬停说明；统一业务清单的操作列按当前结果集中最大可见操作数动态确定宽度，不得保留无意义的大面积空白。右固定操作区必须完全遮挡已横向滚动到其下方的普通列。
- 任务按期完成产生积分事件。

## 7. 域四：需求管理（评估漏斗 · M10 升级）

### 7.1 五阶段生命周期

M10 起：在「登记」与「分析」间插入「评估」门——六维加权评分 + 四象限决策。**M16 定稿完整分流闭环**：登记即进入评审（评审任务按业务域自动指派 IT 侧负责人 BM）；“通过”必须六维评满且不得落入「重新评估」象限；“搁置”和“驳回”在任意评分状态均可选择，评分落「重新评估」象限时只禁用“通过”。驳回不是关闭或取消：默认退回当前审批节点的上一个实际到达节点，审批人也可选择任一已经实际到达的前序节点；若明确选择“登记人补充”，则需求进入“待登记人补充”，由原登记人修改非路由字段、补充附件并在同一需求及同一流程实例上重新提交。通过后转专业线（产品 leader 主责/开发 leader 知会，可配置）做**方案评估与路径判定**——已有系统二次开发且人天<阈值(默认 20，可配)→需求开发实现（任务清单排期，优先级=六维加权总分）；新购系统 或 人天≥阈值→**转项目管理**（指派 PM→PM 备章程建项目并关联需求）。**闭环（M16.5/M95）**：项目验收关闭→提醒 PM 回需求完成「实现交付」步骤→「验收与闭环」任务优先自动指派该业务域业务 BDO，未配置 BDO 时回退 BM（组织业务部门验收）→流程完成时需求自动关闭（验收标准未全勾则提醒该处理人手动关闭）。决议保存即自动流转（评审动作一步到位）。登记页还可填写“其他补充信息”，并通过按钮上传或直接粘贴剪贴板中的图片/文件；每条需求最多 10 个图片、PDF 或常见办公文档，单个不超过 50MB。文件先进入当前账号的临时区，只有需求、流程和审计同时创建成功才原子绑定，取消或 24 小时过期的草稿不可读取。

**需求驳回/退回规则（M108）**：只有当前审批任务的实际处理人或管理员可执行驳回，必须填写不少于 5 个字的理由。候选目标只来自当前流程实例已经生成过任务的前序节点，未来节点和从未到达的节点不可选择；不显式选择时取最近的前序节点。退回流程节点时，系统在目标节点生成新的待办并优先交还该节点上次实际处理人，保留原任务、处理意见、RACI 快照和审计，不覆盖历史。选择“登记人补充”时流程实例进入 `returned`、需求状态进入 `supplementing`，不生成伪待办；原登记人或管理员补充后调用重新提交，流程在原实例重新激活首个评审任务。退回到需求评审或登记人时撤销当前共识评分及主表决议，但历史评分行保留为非共识记录。关闭需求和取消需求仍是独立终止动作，不得以“驳回”替代。升级时只对旧版误写成 `process_instance.status=rejected`、且需求本身未关闭、未取消、未搁置的**最新有效实例**做幂等恢复：首节点驳回回到登记人补充，后续节点驳回回到最近已到达前序节点；同一需求的旧流程实例不得复活，不删除存量单据、任务、附件或审计，也不在修复时批量补发通知。

**路径执行守卫（M96）**：评分通过只允许完成当前的「需求评审」步骤；若该步骤已由业务域负责人完成，后续补评分只补齐评分并停留在「方案评估与路径判定」，不得越过该节点。选择“转需求开发实现”时，系统从需求评分规则中配置的 `dev_leader` 取得唯一开发负责人，不允许按单据临时改选；选择“转项目管理”仍由操作人选择项目经理。执行路径一经确认即写入 `Requirement.implementation_route`，后续评分阈值调整不改写已执行路径。开发路径的「实现交付」节点必须先在该需求“实现”区域创建至少一条开发任务才能完成；项目路径不受该开发任务前置条件约束。该守卫只适用于写入路径快照后的新流转，既有记录不回填、不改写。

阶段 C 的“转项目”已使用 `record_relation(relation_type=converted_to_project)` 统一审计；项目仍通过项目领域服务独立创建并启动自身流程，原需求不改类型、不自动关闭；同一需求已有项目挂接时拒绝重复创建。

```text
登记 → 评估 → 分析 → 实现 → 关闭（可从任意在办阶段转“搁置/取消”；审批驳回可退回已到达前序节点或登记人补充）
```

| 阶段 | 谁 | 填什么 | 系统做什么 |
| --- | --- | --- | --- |
| ① 登记 | bdo/it_bp/任意团队成员/管理员 | 标题✔、类型✔（业务/功能/数据/集成/合规）、所属业务✔、描述✔；来源/期望完成时间/期望效果/运营价值 可选 | 编号、提出人、登记时间自动；通知 it_pdm；普通 requester 不授予需求模块权限 |
| ② 评估 | it_pdm + 评审（CIO/it_bm 知会） | 六维评分 D1-D6（1-5）、决议（通过/搁置/驳回）、退回目标、备注 | **自动算加权总分与四象限**（不手填）；通过需评满且不在重新评估象限；驳回理由必填，默认退上一实际到达节点，也可选已到达前序节点或登记人补充；进入评估时间打点；评估门校验 |
| ③ 分析 | it_pdm | 负责人、排期目标日期、解决方案、验收标准（清单式）、PRD/开发人天；MoSCoW 降级为可选辅助标签 | 进入分析时间打点 |
| ④ 实现 | 负责人 | 任务分解（可登记多行任务：任务名/负责人/计划日期/计划·实际工天）、可选挂接项目 | 进度=已完成任务/总任务；任务完成产生积分 |
| ⑤ 关闭 | 负责人 | 逐条勾验收标准；**一键转出**：遗留问题→ITSM 问题、经验→知识库（自动带需求上下文） | 完成日期打点；交付周期计算；关闭产生积分 |

实现阶段任务权限：需求处于“实现中”时，所有内置 IT 类角色（`cio`、`is_mgr` 和 `it_*`）均可登记、编辑该需求的开发任务完整字段；需求负责人仍保留兼容的单据范围维护权，任务负责人在不具备上述维护权时仍只能更新自己任务的状态和实际工时。任务删除采用软删除：非“进行中”任务由具备开发任务维护权的 IT 人员删除，“进行中”任务仅系统管理员可删除。任务列表和需求详情分别返回 `can_manage_tasks`、逐行 `can_edit`/`can_delete` 标记，前端按钮只作为提示，服务端每次写入仍重新校验权限、需求阶段和示例数据保护；不改写、不迁移既有需求或任务数据。

需求开发候选只依据真实“实现中”状态、非示例标记、当前用户 `can_manage_tasks` 和已冻结的 `implementation_route` 判定；只有 `implementation_route=转项目管理` 才排除。普通 `project_id` 项目关联不等于已转项目，不得据此隐藏需求或拒绝批量导入。需求详情加载任务负责人候选依据 `can_manage_tasks`，不能被当前流程节点的单据编辑权 `can_edit` 锁定；因此具备开发任务维护权的 IT 人员即使不是当前流程处理人，也能在实现区域选择在岗 IT 负责人。

### 7.1a 任务管理（M82）

任务管理独立于需求管理，一级菜单下分为“开发任务”和“委派任务”。开发任务页包含“需求开发”“Bug 修复”和“项目开发”三个标签：需求开发继续使用 `RequirementTask`，允许先独立登记、后续补充关联需求；Bug 修复使用独立 Bug 及修复子任务模型，不与 ITIL 问题单据混用；项目开发使用独立 `ProjectDevelopmentTask`，项目必填、WBS 可选，用于项目 WBS 未拆到开发活动粒度时补充管理。

项目开发任务以 `ProjectDevelopmentTask.status` 为唯一状态口径，清单列名称为“任务状态”；原“最新进度”列改为“完成度”，从追加式进度记录的最新有效百分比派生，文字批注仅在详情“进展说明”时间线显示。待处理任务第一次写入有效进度时自动进入“进行中”；普通进度只允许 0–99%，不得用 100% 或直接编辑状态暗示完成。负责人、登记人或管理员必须通过显式“完成任务”并填写完成说明，服务端才在同一事务写入 `status=已完成`、100% 进度记录、`completion_note` 和 `done_at`。已完成任务不可继续追加进度或通过普通编辑重新打开。历史进度记录保持原样；若旧记录曾写 100% 而主任务仍未完成，清单兼容显示为 99%，以免出现两个相互矛盾的完成信号。

网页入口为“任务管理 → 开发任务”（可通过 `?tab=requirement|bug|project` 定位标签）和“任务管理 → 委派任务”。历史 `/requirements/tasks` 与 `/requirements?tab=tasks` 地址保留重定向，原需求任务主键、状态及软删除数据不变。

“需求开发”提供“下载模板”和“批量导入”。模板列为关联需求编号（可空）、任务名称、任务描述、处理人、计划完成日期、计划/实际人天和任务状态；只接受 `.xlsx`（最大 5MB）。空关联行创建独立开发任务，可在编辑时补充需求；填写关联编号时，目标必须是未明确转项目、非示例且处于“实现中”的真实需求，普通项目关联不影响选择和导入。处理人按数字化团队在岗人员姓名精确匹配；每行分别校验并返回行号/原因，合法行立即创建，不合法行不阻断其他合法行，也不更新或覆盖既有任务。三类开发任务清单均显示登记人：页面直接登记取当前登录人员；由需求转化的任务取需求原登记人；由项目/WBS 转化的任务取项目经理；Bug 修复任务取 Bug 登记人。系统管理员无人员映射或历史数据无快照时可为空，但账号审计仍保留。

三类开发任务还必须显示可排序的“任务编号”和“登记时间”。需求开发任务编号为 `RT-YYYYMM-NNNN`，项目开发任务编号为 `PT-YYYYMM-NNNN`；Bug 修复以 `BG-YYYYMM-NNNN` 表示缺陷父单，以 `BT-YYYYMM-NNNN` 标识每条实际开发/测试修复子任务。月份取任务原始登记时间，编号是持久化业务标识而不是前端临时序号。升级时仅为缺少编号的存量需求开发和 Bug 修复子任务按原登记月份、`created_at + id` 稳定顺序补齐编号，不改写任务 ID、登记时间、关联需求/Bug、处理人、状态、工时或软删除数据。

Bug 闭环固定为：**登记 Bug（IT 团队成员）→ Bug 确认（所属系统产品经理，审批）→ 生成修复任务（开发负责人）→ 开发修复（开发负责人在修复任务中指定的开发/测试人员执行）→ 验证关闭（所属系统产品经理，审批）**。登记时从 CMDB 配置项读取产品经理并保存快照；一个 Bug 可生成多行开发/测试子任务，全部子任务关闭后才进入产品经理验证。登记后可通过通用附件上传截图、日志或其他证据（单个文件最大 50MB）。Bug 编号可进入详情；在流程回改窗口内可编辑所属系统并重新读取产品经理快照，创建人仅在下一节点尚未查阅处理时可删除，管理员始终可删除。确认驳回、验证不通过和重新打开必须记录原因并保留审计。流程第 4 节点不再把开发负责人作为默认执行人，实际执行人以修复子任务负责人为准。

“所属系统”不是前端固定枚举，选项来自 CMDB 中未下线的配置项；任务管理提供只读引用接口，CMDB 仍是维护入口。所有选项和产品经理快照仍由服务端从 CMDB 取得。

委派任务覆盖工单、问题、事件、技术研究和其他非项目级工作，状态采用轻量化的“登记 → 排期 → 执行 → 关闭”，并支持“暂停/中止”。每次进度批注写入追加式时间线，包含作者、时间、状态快照、可选完成度和正文，历史批注不得被覆盖。登记且未分配时登记人可删除；一旦分配，在关闭前仅管理员可删除；管理员可在清单页编辑、暂停、中止和关闭。委派任务、需求开发任务和项目开发任务在指派负责人时通知负责人；负责人更新状态、工时、完成说明或显式进度时通知登记人，站内通知与飞书消息共用可靠 Outbox。各任务资源使用独立权限和记录级范围，不能由前端按钮代替授权；历史需求任务、问题、绩效和积分数据保持原样可读。

绩效归属固定为：Bug 修复子任务和普通委派任务默认进入岗位结果，分别计入 `bug_fix_delivery`、`delegated_work_delivery` 交付指标，并通过幂等积分规则保留完成证据；只有登记时明确选择团队贡献且类型为“技术研究”“跨团队支持”或“知识分享”的委派任务，才进入对应团队贡献维度。

### 7.2 六维加权评分与四象限

依据《需求评分与优先级细化标准》（麦肯锡战略价值-执行可行性双轴）。权重/阈值/分档在**需求管理→「需求评分规则」标签页**配置（admin 可编辑，其他角色只读参考分档说明），年度可调（默认见下）。需求评估页以紧凑提示链接至该页，避免重复展示完整规则。

| 维度 | 默认权重 | 说明 |
| --- | --- | --- |
| D1 战略对齐 / D2 业务价值 / D3 技术可行性 | 0.2 / 0.2 / 0.2 | 战略价值 + 技术 |
| D4 组织就绪 / D5 风险等级(反向) | 0.1 / 0.1 | 风险按 (6−D5) 反向计入 |
| D6 价值速度 | 0.2 | Time-to-Value |

`加权总分 = 0.2·D1 + 0.2·D2 + 0.2·D3 + 0.1·D4 + 0.1·(6−D5) + 0.2·D6`（服务端计算）。
四象限（横轴战略价值 (D1+D2)/2，纵轴总分，默认阈值 total 3.5 / strategic 4 / viable 3）：⭐战略下注、⚡速赢项目、📋低优先级、🔄重新评估。
评审治理：M10 起步为**单人共识评分**（`requirement_score.is_consensus` 回填需求六维分），多方独立评分+共识为后续增强（表已预留 reviewer_role/role_weight）。

### 7.3 需求列表、导出与导入

- 按阶段分栏（看板，含「评估中」栏）+ 表格视图切换；筛选：业务线/优先级/**决议**/负责人/提出人；卡片展示加权总分与象限。表格横向滚动时固定左侧“编号、标题”两列；无论筛选结果多少行，宽表都必须保留全局底部横向滚动条以访问隐藏字段和操作列。
- **清单导出**：具有需求查看权限的用户可从需求总览导出 Excel。导出严格复用当前关键词、业务域、MoSCoW、状态、决议和“只看我的”筛选及服务端数据范围，包含全部匹配记录而不是当前分页页；看板视图不带入仅表格可见的隐藏状态/决议条件。导出不包含复选框和操作列，也不因用户没有新建权限而隐藏。
- **模板导入**：新下载的 Excel 模板只包含登记阶段字段（标题、类型、业务域、描述、来源、期望完成时间、期望效果、运营价值），登记人与编号由系统生成；六维评分、决议、PRD/开发人天等下游字段不进入新登记模板。上传接口按表头识别旧版 19 列模板并继续兼容历史评分导入，旧数据不迁移、不删除。

**需求处理时效口径**：统计队列固定为“登记时间落在所选周期内、未删除且当前用户在需求域可见”的需求。已关闭需求的处理时长为关闭时间减登记时间；未关闭需求只进入阶段停留/在途数量，不伪造完成时长。报表展示完成量、平均处理天数、P50、P90、各阶段当前停留天数和按期完成率；按期以需求目标日期为准。没有完成样本或没有目标日期分母时显示 `N/A`，真实计数为零时显示 `0`。业务域筛选必须同时受当前账号需求数据范围约束。

### 7.4 验收标准

- [ ] 评估门：六维未评满或决议非「通过」时不允许进入分析
- [ ] 验收标准未全部勾选时不允许关闭（有遗留时必须转出问题或说明）
- [ ] 转出的问题/知识自动携带需求编号反向链接
- [ ] 全域中英双语；权重/阈值/分档 admin 可配
- [x] Aily 通过真实需求登记表单只追问缺失字段，确认后写入 `Requirement` 而不是服务请求工单

## 8. 域五：流程引擎（简化版）

**定位**：为工单/变更/需求/项目提供可配置的步骤化流程与自治级别标注，不做重装置。

- 三层模型：**流程定义**（含步骤：名称/顺序/节点类型〔处理/审批〕/默认角色/知会角色/L1-L4 自治级别/SLA 时限）→ **流程实例**（单据触发）→ **流程任务**（步骤实例，指派到人）。审批节点支持右上角同意（理由可选）或驳回（理由必填），处理节点使用“完成此步骤”推进。
- 自治级别：L1 全自动 / L2 系统建议人确认 / L3 人做系统辅助 / L4 纯人工。用于流程监控展示与后续人效分析，不控制执行。
- 初始内置 6-8 个流程：事件处理、服务请求交付、变更审批实施、问题分析、需求交付、项目关键节点。
- 派单规则：按步骤默认岗位角色指派（如需求评审→it_bm、方案评估→it_pdm_leader、项目节点→it_pm、变更申请/实施→it_ops、变更审批→it_op_leader、变更复盘→is_mgr、开发任务→it_dev_leader）。当前待办处理人或管理员可在实例中转派给另一名在岗且具有有效系统账号的人员；转派不推进节点、不改变单据状态，必须记录原/新处理人、可选理由和审计，并通知新处理人。

**当前已发布运行时的七条内置流程快照（2026-07-24 本地运行时核对，Bug 流程于 M82 纳入）**：下表是流程中心中激活版本的实际节点，不是泛化的 ITIL 示例，也不是旧版种子说明。流程中心后续发布新版本后，以新版本为准；历史实例保留原快照。

| 流程 | 实际步骤（默认处理人；括号内为节点语义/知会） |
| --- | --- |
| `incident_flow` | 受理定级（it_op_leader，审批）→ 诊断与处理（it_ops）→ 解决与用户确认（it_ops，审批）→ 关闭复盘（it_op_leader） |
| `sr_flow` | 受理确认（it_ops）→ 实施交付（it_ops）→ 用户确认关闭（requester，审批） |
| `change_flow` | 变更申请（it_ops）→ 变更审批（it_op_leader，审批；知会 it_bm）→ 实施与验证（it_ops）→ 变更复盘(PIR)（is_mgr；知会 cio） |
| `problem_flow` | 问题确认（专业线负责人动态指派，审批）→ 根因分析（负责人指定处理人）→ 解决与验证（延续处理人）→ 解决确认与关闭（专业线负责人，审批） |
| `requirement_flow` | 需求评审（it_bm，审批）→ 方案评估与路径判定（it_pdm_leader，审批）→ 实现交付（需求开发路径固定为需求评分规则 `dev_leader`；项目路径为所选项目经理；开发路径须先建≥1任务）→ 验收与闭环（it_bm，审批） |
| `project_flow` | 立项启动（it_pm，审批；知会 cio、it_bm）→ 执行监控（it_pm）→ 收尾复盘（it_pmo，审批；知会 cio、it_tm） |
| `bug_flow` | 登记 Bug（自动完成登记节点）→ Bug 确认（所属系统产品经理，审批）→ 生成修复任务（it_dev_leader）→ 开发修复（指派开发人员）→ 验证关闭（所属系统产品经理，审批） |

服务请求流程不新增 Aily 人工分流节点：Aily 只负责意图理解、字段收集和用户确认，MCP 创建正式单据后立即由 ITOM 按服务项绑定流程和**受理派单**执行。首个受理节点完成时，当前受理人可在 ITOM 选择“由我实施”“指定在岗 IT 同事”或“按实施派单规则自动分配”；自动规则按服务项→目录→全局兜底匹配。全局实施兜底仅系统管理员/CIO 可维护；`manual_queue` 保留未指派任务供下一节点合格角色认领；完全未命中规则时才回退该节点的 `default_role`。实施选择只允许当前节点处理人或管理员执行，必须记录选择人、时间、来源和命中规则；它不是 M92 上游更正可修改的路由字段，Aily/MCP 也不接受该输入。IT 人员完成处理后工单只进入 `resolved`，必须等待提交人通过网页或 Aily 确认；未解决回到 `processing`，确认后才进入 `closed` 并评价。出站消息只包含用户可见进展，内部备注和审批信息不得进入 Aily 上下文。

需求“方案评估与路径判定”节点优先使用需求评分规则配置的产品负责人；若尚未配置该人，系统将通过评审决议的人员作为本节点兜底处理人，避免新租户出现无人可处理、而其他角色又不应绕过流程直接修改方案路由的死锁。

- **流程节点标准（M3.8，后续所有流程功能强制）**：每个节点可配置**处理人**（审批/执行，产生任务、阻塞流程）与**知会人**（仅站内通知，不产生任务、不阻塞，可多个角色/用户组）；流程定义页展示**流程示意图**（处理人蓝标/知会人灰标），编辑器实时预览。已有实例的版本仍锁定节点顺序/类型、处理人、自治级别和 SLA；仅知会人允许原地维护，变更只在后续节点激活时生效，既有任务和已发通知保留其历史快照。详见 docs/06 §十。
- **上游更正窗口（M92）**：所有流程定义单据（服务请求、事件、变更、问题、需求、项目、Bug）在下一节点**首次实际查阅或处理前**允许有限回改。首节点仅创建人可编辑内容且可删除；后续节点仅上一节点的实际完成人可编辑内容，不能删除。页面详情打开由当前节点处理人确认查阅；仅浏览清单、通知、管理员仅查看详情或管理员尚未处理前的改派不会锁定窗口。回改不得修改当前处理人、项目经理、业务域、服务项等会改变派单/路由的字段，也不得重置流程、状态、SLA 或历史任务；管理员保留系统级编辑/删除权。上线时既有待处理任务不追溯放权。
- 页面：流程定义管理（admin，含启停/编辑步骤）、流程监控（实例列表、卡点步骤、超时任务）。
- 单据详情页展示流程条（当前步骤高亮）。

**流程事实一致性增量约定**：单据详情、流程图、待办和可操作表单必须以当前运行流程实例的“最新待处理任务”判定当前节点；`ProcessInstance.current_step_seq` 与业务单据阶段字段是兼容投影，不得覆盖活动任务事实。历史评分、分析结果和审计记录可以继续展示，但只能以只读方式显示，不能重新打开已经结束的评估编辑入口。需求阶段投影只允许向前同步，不能覆盖关闭/取消/搁置等终态；评分接口在流程已进入实现或验收后必须拒绝写入。旧实例若任务关系已陈旧，详情接口必须直接读取任务表并按节点使用最新任务，避免出现“详情停留六维评分、流程条已到验收”的矛盾。

**个人待办与清单交互**：个人中心新增“待办事项”标签，聚合当前账号按流程授权可处理的服务请求、变更、事件、问题、需求、项目和 Bug 任务，点击后进入对应单据详情/流程处理页。待办聚合只读流程任务和领域详情，不改变权限。主要清单支持每个账号独立保存可见字段和列宽；编号、标题及操作列等上下文/操作字段不可隐藏，宽表始终保留横向访问能力。鼠标靠近任一可见表头分隔线时出现调整光标，无初始宽度的字段同样可调整，且调整后的宽度必须立即反映在表格中。需求清单显示提出人并固定编号、标题。新需求入口不再收集“渠道部门”，历史字段仅作兼容展示。

**关于 n8n**：流程引擎内置于后端代码，不引入 n8n。Aily 通过内嵌 MCP 调用 ITOM，主动消息通过通知发件箱的飞书机器人适配器发送；跨系统编排仍可在未来订阅发件箱事件，但不得成为 ITOM 业务状态来源。

**验收**：新建工单自动创建对应流程实例；流程监控可见每个实例进行到哪一步；改派生效。

## 9. 域六：团队管理

**统一统计边界（M40）**：本模块只统计和展示 IT 团队成员，不使用全公司人员口径。IT 团队以组织架构中 `dept_type=it` 为主；未标部门的存量账号按 `cio`、`it_*`、`is_mgr` 等 IT 角色兼容识别。业务部门人员及仅持 requester/auditor 的人员不进入团队总览、工作负载、积分排行、人效、活动发放和岗位在岗数；团队页面的人员选择器同样只返回 IT 成员。

**团队总览负载清单**：`/api/team/overview` 返回全部在岗 IT 成员的未完成工单、项目任务和需求任务聚合，按合计降序。其中“项目任务”同时汇总项目计划中的未完成 WBS 工作包，以及任务管理模块中状态非“已完成”的项目开发任务；软删除、示例数据、无负责人记录不计入。网页端在本地每页展示 20 人并提供翻页、搜索、排序和导出；不得以“Top 20”截断接口结果，工具栏数量与同一 IT 团队口径的在岗人数可核对。

### 9.1 人效管理（分级评审）

- **矩阵角色评分**：CIO 以员工当前业务服务线角色、专业线角色和团队贡献配置评分；业务角色权重 + 专业角色权重固定为 80%，团队贡献固定为 20%。
- 每个角色独立 100 分制；业务服务线由业务线负责人/BP 初评，产品/项目/开发/运维专业线由对应负责人初评，平台服务角色由 CIO 直接评分；CIO 不纳入本套常规评分。
- 负责人只能修改自己管理范围内对应条线的角色分，不能修改另一条线、团队贡献原始积分或外部原始数据；负责人不得评价自己。CIO 查看全部系统参考分和负责人初评，并进行终审、微调以及负责人本人的评分。
- 评分状态为 `draft → auto_scored → external_input → manager_review → cio_review → published → locked`。系统初评、负责人初评、CIO 终审和最终生效分分开保存，发布后重新调整必须建立新版本。
- 业务满意度等系统外事实通过独立的外部原数据页面录入、核验、锁定和修订，记录评价人、原始分、量表、折算分、说明和证据；外部业务满意度与 ITSM 工单满意度分开保存。
- 发布前评审明细仅对有范围权限的负责人和 CIO 可见；被评价者只能访问发布后的最终结果，不显示系统参考分、负责人/CIO 微调和外部评价明细。
- 团队贡献由专项活动、学习成长、培训知识分享、建言改进、知识复盘、跨团队支援六个维度构成，满分 100 后按固定 20% 计入。
- 工单、需求、项目和流程事实若已用于角色结果指标，标记为 `role_result`，不得再次计入团队贡献；只有职责之外的活动、学习、分享和跨团队支援等 `team_contribution` 进入固定 20%。活动积分排行榜、个人活动积分和团队总览积分排行只读取 `team_contribution` 桶；岗位结果流水仍保留在台账中用于角色结果取数和审计。
- 评分周期沿用 `YYYY-Q1/Q2/Q3/All`；角色、权重、评分主体和规则均生成周期快照，发布后可审计、可复现。
- 详细角色维度、权重、评分主体、学习成长任务和数据模型见 [IT 团队角色绩效评分 PRD](08-IT团队角色绩效评分PRD.md)。
- “人效评分 → 计分规则”以矩阵角色档案为当前生效设计：展示角色维度权重、系统/外部/人工取数方式，以及当前考核期员工的业务角色/专业角色 80% + 团队贡献 20% 权重矩阵；系统管理员与 CIO 可进入并验证规则。旧版 `perf_scheme` 接口保留作历史兼容，不再作为页面主设计。
- “人效评分 → 总览”读取矩阵角色周期结果，按员工展示角色职责结果、团队贡献 20%、加减分和当前总分；页面不再展示旧版“默认方案”或旧版岗位维度列。当前模型没有全局默认方案：新增规则使用“计分规则 → 新增角色规则”，再在周期员工详情中分配角色和权重。
- “人效评分 → 分级评审”总览按员工聚合为一行；点击员工的“评分明细”进入独立详情页，查看并按权限调整该员工全部角色权重、评价维度、系统参考分、负责人初评、CIO 终审/微调、生效分及修正说明。

### 9.2 成长积分

**核心机制：积分零录入，事件自动计分。**

| 来源 | 事件（分值全部可配，支持负分） |
| --- | --- |
| 服务贡献 | 工单解决、SLA 双达成、满意度 ≥4 星、问题根因定位 |
| 项目贡献 | WBS 任务按期完成、里程碑交付 |
| 需求贡献 | 需求任务完成、需求关闭 |
| 培训贡献 | 主讲/组织培训、参与培训 |
| 知识贡献 | 发表文章、文章被点"有用" |
| 建言献策 | 提出建言、被点赞、被采纳 |
| 任务贡献 | Bug 修复任务完成、委派任务完成；技术研究/跨团队支持/知识分享等明确选择团队贡献时进入对应团队维度 |

- 积分流水：人/事件/分值/来源单据/时间，可追溯到触发单据；管理员手工加减分同样走流水（需填理由）。
- 当前考核期的排行榜、个人积分、团队总览和 Dashboard 只读取 `team_contribution`。其中由活动积分规则驱动的自动事件，读取时按当前规则分值计算；规则停用显示为 0，专项活动和手工流水仍使用台账原始分值。`role_result` 岗位结果流水不进入活动积分排行榜。原始台账、已结束历史周期和已发布/锁定绩效不被规则修改回写；它不是人效总览中的归一化活动相对分数。
- 页面：排行榜（月/季/年/累计）、个人积分明细、活动积分→积分规则（团队贡献活动规则，仅 admin/CIO 可修改；所有修改写入审计日志）。当前积分页面和团队总览每 30 秒自动刷新，并提供手动刷新。岗位职责结果的取数、角色维度、RACI/流程节点映射和权重在团队管理→人效评分→计分规则维护，两者不可混算。
- 积分作为 9.1 人效评价输入源之一。

### 9.3 岗位编制

- 人员主数据：姓名✔、部门、岗位（关联岗位定义）、团队分组、状态（在岗/离职）、入职日期、技能标签。
- 岗位定义：岗位名✔、岗位编码、岗位族/序列、服务业务域、主责角色、职级/能力框架、办公地点、关键技能、是否允许外包、启停状态、分工职责描述和正式编制数；页面实时呈现“正式编制 vs 正式在岗 vs 缺口”。
- 正式编制只统计 IT 团队正式在岗人员，外包/实习人员不计入正式编制；岗位与人员通过 `position_id` 关联，飞书组织同步不覆盖本地岗位关系。
- 招聘需求：岗位✔、级别（高级/中级/初级）、人数✔、任职资格✔、状态（待招聘/面试中/已到岗/取消）、进度备注；一个岗位可有多条分级、分批招聘需求。
- 岗位定义和招聘需求均支持“导出 Excel / 下载模板 / 批量导入”：导出文件带字段说明行，可修改后回导；按岗位编码/名称匹配，支持新建与更新，失败行返回行号和原因并写入审计日志。可恢复的非法列宽会自动清洗；其他损坏文件、超长字段、编码/名称冲突和已删除岗位编码等异常均转换为可读的逐行导入结果，不以 500 中断请求。
- 岗位定义与招聘需求的编辑、删除权限默认授予 `admin` 和 `cio`；列表页提供行内编辑、保存、取消和删除，修改不必进入详情弹窗。删除采用软删除，仍被人员或招聘需求引用的岗位会先阻止删除。

### 9.4 培训提升

- 活动登记 5 项：类型✔（内部交叉培训/外部技术交流/新技术研究）、主题✔、日期✔、主讲/组织人、参与人（多选）+ 可选产出链接。参与人按部门目录折叠展示，部门和人员节点均提供复选框；勾选部门会级联勾选其全部 IT 团队成员，仍可单独增减人员。整部门选择由服务端冻结部门 ID、显示名与当时覆盖的人员 ID；清单显示部门名称及范围外个别参与人，积分始终按人员快照计算，不因之后调岗、部门改名或新增成员而改变。旧活动不回填部门快照，继续按原人员名单展示。
- 登记完成自动为主讲人与参与人计积分，并保存登记人。管理员、CIO 或登记人可编辑、删除；服务端按记录范围复核，不能只依赖页面按钮。存量记录优先从创建审计回填登记人，无法回填者仅管理员/CIO 可维护。
- 当前未发布、未锁定考核期内，变更主讲或参与人会软删除旧培训积分流水并按当前规则重新登记；删除同样撤销活动对应积分。历史周期以及已发布/锁定周期禁止影响积分的修改和删除，主题、日期、产出链接、备注等不改变积分对象的资料仍可编辑并审计。

### 9.5 团队文化

## 9A. 统一报表中心（B2）

**目标**：在不复制业务主数据、不维护人工统计台账的前提下，把需求、建设、运维的费用、人力与交付事实连同 ITSM、任务和流程统一呈现为管理分析、周期报告和可追溯明细。

- **分析首页**：按周、月、季度、半年、年度或自定义日期查询；系统时区默认 `Asia/Shanghai`，周一至周日，财年默认 1 月开始。支持项目、项目组合、业务域、工单类型、优先级、服务项、CI、合同、需求和归属对象白名单筛选。项目页展示预算、已发生/已承诺成本、投入人天、标准费率成本和财务预算执行率；需求页展示完成量、平均/P50/P90、阶段停留和按期率；运维页展示预算、已承诺/已发生/已支付费用、费用构成、实际人天、标准人力成本、管理总投入、工单工时覆盖率和单已解决工单费用；人力页展示总人天、需求/建设/运维投向、角色构成与标准费率覆盖率；综合页同时展示 ITSM、任务与流程指标。
- **统一投入台账（B-OPS）**：预算、费用、实际工时和分摊以统一事实表保存，并标记生命周期 `demand/build/run` 与投入目的 `run/grow/transform`。归属对象支持项目、需求、服务项、CI、工单、问题、合同、业务域、工作任务及共享运维成本池。费用区分已承诺、已发生、已支付和 CAPEX/OPEX、一次性/持续性；工时记录人员、实际日期、人天、角色、活动类型与登记时角色标准费率快照，单人单日累计不超过 2 人天且禁止未来日期。标准费率是管理估值，不是个人薪酬。需求详情和 ITSM 工单详情中的投入台账统一位于全部既有业务内容之后的页面底部，不打断原详情阅读和处理流程。
- **防重复口径**：已支付是已发生费用的子集，不能再次相加；合同总额只作为合同事实，不自动生成费用；工单处理时长只用于时效，不自动生成人天；共享费用/工时按显式比例分摊且同一来源合计不超过 100%。财务实际投入为已发生费用；管理总投入为已发生费用加标准工时估值，但存在未分类人力费用时返回 `N/A` 并提示先分类，避免双计。
- **兼容与迁移**：旧项目预算、成本和人天表幂等回填统一台账，使用唯一来源键防重复；旧表保留一个回滚周期但停止新写入。项目原有接口和页面继续兼容，由统一台账提供数据；`project.budget_10k` 仅在没有显式预算分项时作为兜底。
- **指标目录**：每个指标公开编码、中英文名称、单位、领域、公式版本和数据质量。计数型指标没有记录时返回 `0/ok`；比率、平均值、分位数等没有有效分母时返回 `null/no_data`，前端显示 `N/A`，禁止把缺数渲染为 0%。
- **穿透**：有明细能力的指标可打开受控明细表；服务端重新校验报表权限、源模块权限、敏感权限和当前记录数据范围，最多返回 200 行，不接受任意字段/SQL/排序表达式。
- **正式报告**：内置综合运营、项目投入、需求时效、运维投入、IT 人力容量与投向等模板，也允许有权限角色维护自定义模板。创建报告时固化周期与受控筛选；“生成版本”才保存指标快照、说明、公式版本、数据质量、生成者/时间和 SHA-256 校验和。相同操作者和幂等键的相同请求返回原版本，不同请求冲突。
- **审核发布**：状态为 `草稿 → 审核中 → 已批准 → 已发布/锁定`。提交审核启动 `report_flow`；批准后仅具有 `reports_publish` 的角色可发布。发布时设定用户/角色/组受众，当前版本锁定不可改写；后续更新必须回到草稿并生成递增新版本，旧版本保持可审计。当前阶段不启用自动调度执行，周报/月报等由模板和周期手工生成。
- **访问控制**：`reports` 管报表入口和草稿操作；实时指标还必须具备对应源模块查看权。`reports_finance` 控制预算/成本/标准费率成本，`reports_people` 控制人员投入明细，`reports_platform` 控制跨域平台指标，`reports_publish` 控制批准后发布。已发布报告还需命中用户/角色/组受众；发布后若敏感权限被撤销，敏感指标和明细立即不可见，不以历史受众绕过。
- **导出**：正式报告按当前可查看版本导出 `.xlsx`，包含报告摘要、周期、版本、校验和、指标/单位/质量/公式版本和管理说明；导出不扩大在线可见范围。

验收：需求、项目和运维投入按人民币元、人天及分摊比例可核对；已支付不与已发生重复、合同额不冒充实际费用、工单时长不冒充人天；未分类人力费用阻止管理总投入出数；需求时效与原始记录一致；无数据语义区分 `0` 与 `N/A`；跨域撤权和穿透明细均失败关闭；迁移与重复生成均幂等；发布版本及校验和不可变；中英文页面和 Excel 均可用。

## 10. 支撑：系统管理（admin）

菜单结构（8 入口）：

1. **组织管理**：「组织架构」标签页（公司→部门→人员三级树 + 右侧主数据面板；**飞书为 Source of Truth**；管理员在同步完成后配置“数字化团队范围”）。范围由所选部门成员（可包含下级部门）与单独指定人员组成并集，因此可从 Test 等混合供应商组织中只纳入需要参与 IT 业务和绩效考核的外包人员，而不纳入同部门其他人员。该口径统一驱动团队统计、绩效对象及 IT 工作人员选择器。「业务服务域」标签页维护 IT 侧负责人（BM）、服务团队、服务部门和业务 BDO；BDO 选择器只显示已启用、已获 BDO 角色且处于该域服务部门范围内的业务人员。项目经理、项目任务负责人、需求负责人/评审人/开发负责人、工单/问题/服务项/配置项/合同负责人、用户组负责人及成员等下拉选择均只展示该数字化团队范围；前端通过 `scope=it` 获取，后端在已配置范围后再次校验，不能依赖前端过滤。业务域支持管理员删除；存在有效需求引用时必须拒绝删除并提示先迁移需求。飞书集成配置支持独立启停自动组织同步，并提供每 1/6/12/24 小时的同步频率。
2. **用户与组管理**：「用户」（账号/角色/认证源/开通默认角色）+「用户组」（专业线资源池：负责人 TM/组授予角色/成员）。
3. **角色与权限**：「角色定义」（内置 12 个可改名 + 自定义复制模板）+「预分配规则」（部门→首次开通默认角色）+「权限配置」（角色×系统模块×4 动作矩阵）。
4. **数据字典**（业务线/关闭代码/类别等下拉项 + 公司名等系统配置）。
5. **状态机配置**（每类单据的状态与流转规则可视化编辑，含在用状态删除保护）。
6. **系统集成**（飞书、SMTP、AD/LDAP 等外部连接）。
7. **审计日志**（admin/is_mgr/auditor 可查）。
8. **界面与品牌**（admin）：系统中英文名称/简介、横版与方形 Logo、Favicon、登录门户、主色/主题/密度/侧栏、角色默认首页、顶部公告及环境标识。图片选择后先进入可拖动、缩放、旋转的裁剪器；横版 Logo 使用 4:1、方形 Logo/Favicon 使用 1:1、登录背景使用 16:9，确认后仅上传裁剪结果。登录后按角色采用两套明确区分的应用壳层：仅持 `requester` 角色的业务用户使用方案 F「模块化服务门户」（顶部导航、帮助搜索、快捷入口和卡片式服务目录）；其余角色使用方案 C「精密高密度工作台」（216px 浅色紧凑侧栏、全局工作条、低圆角高信息密度画布；一、二级导航保持协调的浅色层级）。侧栏宽度以 Logo/系统名称区域及最长导航文字单行显示为约束，仅保留必要的左右留白。内部工作台展开侧栏的横版 Logo 独占一行，置于系统名称上方；横版 Logo、系统名称及英文副标题沿同一中轴线居中对齐，折叠后改用方形 Logo。侧栏菜单区在展开项超出视口时独立纵向滚动，品牌区与顶部账户入口保持可见；侧栏底部不重复展示当前用户及角色，账户入口统一位于顶部栏。配置采用“草稿 → 预览 → 发布”，保留发布历史并支持回滚。

另：SLA 策略在 ITSM-SLA 看板页维护；通知发件箱后台保留。

**流程定义管理**（流程中心）：流程/步骤全量可配置——稳定节点编码、步骤名称、节点类型（处理/审批）、默认指派（角色/用户组）、知会人、L1-L4 自治级别、步骤 SLA、触发条件（同类单据下激活流程的触发条件必须唯一）。任务生成时写入流程版本、节点编码和 RACI（主责/知会）快照；已有实例的版本锁定节点顺序/稳定编码、节点类型、默认指派、自治级别和 SLA，须通过**另存新版本**演进；只有知会关系可原地维护，并且仅用于保存后首次激活的后续节点。老任务继续显示创建时快照，既有通知不补发、不回写。

### 10.1 ITOM 网页智能体（设计已确认；WA0 Task 1–8 已实现）

采用“网页登录入口 + Aily MCP 入口身份隔离、下层领域能力复用”的方案。普通业务用户在网页智能体中仍只处理本人服务请求；BDO 增加本人 IT 需求登记与跟进；IT 员工按有效角色、功能权限、数据范围、记录状态和当前流程任务获得模块解释、查询、草稿与分阶段开放的受控操作。管理员可配置模型、智能体档案、知识范围和最高能力等级，但模型配置只能收紧能力，不能授予权限。

能力分为 L0 解释导航、L1 授权查询、L2 草稿预览、L3 预览后明确确认的写操作和首期禁止的 L4 高风险管理操作。所有能力必须由服务端注册并调用领域服务；不提供通用 SQL、HTTP、Shell 或直接写表。WA0 Task 3 的 L2/L3 模型资格要求认证基础响应、流式终止、强制工具调用和严格 JSON Schema 四项独立探测全部通过；提供商请求绑定到当次校验的公网 IP，审计由独立事务写入且成功审计落库前不发送流完成事件。现有“创建单据指引”保留为模型故障时的确定性降级。完整契约见 [`docs/superpowers/specs/2026-08-01-itom-web-agent-design.md`](superpowers/specs/2026-08-01-itom-web-agent-design.md)。

WA0 Task 4 已提供仅 `admin_ai` 可访问的提供商和四类固定档案管理 API。密钥只写加密、空值保留旧密文；提供商启用和档案发布均以近期真实探测为门禁。首次配置、配置或密钥变更后必须由管理员手动探测；已启用且配置未变更的提供商由后端每 10 分钟自动复探，以覆盖 15 分钟有效期，失败即自动停用并写入系统触发的脱敏审计。所有提供商治理变更及档案发布/回滚形成的活动提供商引用由 PostgreSQL 事务 advisory lock 跨 Pod 串行化，并按 ID 锁行后重新校验；探测只在前后两个短事务持锁，中间异步网络 I/O 不持数据库事务，并以配置修订号拒绝变化/删除后的旧结果。档案只能选择代码注册能力并受固定受众、风险和知识范围收窄；名称、默认提供商、启用、保留期等发布控制字段只写带 schema 标记的完整版本草稿，成功发布才原子应用活动配置并创建不可变递增版本，失败发布不污染当前活动档案。回滚只复制可证明完整的历史快照；迁移前 `{}` 或不完整快照确定性拒绝且不修改活动档案/版本，不以当前设置补齐历史。健康和动作审计只返回聚合/脱敏白名单；用量在默认 30 天、可选 1–90 天窗口内由 SQL 聚合。

WA0 Task 5 已提供当前登录账号的会话 bootstrap、创建、列表、详情和归档 API。会话和列表/详情/归档始终按数据库中的 `auth_user_id` 限定，未归属 ID 以同一非泄漏 404 返回；管理员也不获得用户会话浏览权。浏览器上下文只接受规范化站内路径、有限页面/实体/标签标识和最多 20 个 GLID 选中项，拒绝客户端角色、权限、DOM/HTML、提示词、Cookie、头部、外部/协议相对/穿越式路径和所有额外字段。bootstrap 仅返回启用状态、档案标识/版本、最高风险、建议问题、保留期和确定性降级可用性；只有完整 schema 版本快照、双语提示、能力/风险、健康兼容提供商及活动档案一致才启用，否则失败关闭。保留期仅由会话创建时捕获版本的完整快照决定，不能由活动档案或 `expires_at` 推断：捕获 0 永不保存普通 user/assistant 正文（包括失败路径），后续再发布为正值也不改变；捕获 1–90 天保留其稳定 `expires_at`，但当前档案停用、删除、未发布、受众不一致或运行时校验失败时不写新正文。消息仅在持久化前递归脱敏。`fallback_available` 只反映认证用户现有、权限感知的“创建单据指引”安全载荷可用性，不代表 WA1；列表页码为 1–10,000。归档只从归属用户的活动列表隐藏会话，不删除 `ai_action` 或其他安全/业务审计。

WA0 Task 6 已实现通用 L3 动作边界。准备阶段只按代码注册的 Pydantic 输入模型规范化参数；若递归脱敏会改变任何规范化值，则统一拒绝且不占用幂等键，只有安全原值可计算稳定摘要和持久化。幂等范围固定为“真实账号 + 能力 + 幂等键”，PostgreSQL 竞态只恢复命名约束 `uq_ai_action_user_capability_idempotency` 的赢家：同键同参返回既有状态且不重发 Token，同键异参拒绝，其他完整性错误不吞掉。L3 固定 handler 必须实现 `authorize_preview`、`preview` 和 `authorize_record`；准备先做非泄漏记录级预览授权，再在独立且最终回滚/关闭的 Session 中，以独立加载的 actor 上下文和 `ReadOnlyActionData` 只读门面生成 `status=prepared` 的权威预览。该门面不暴露 Session-like 属性，并递归校验查询 AST：只允许单个直接映射表的显式标量列、同表安全条件/排序和编译期非负有界 limit/offset，返回递归冻结的 `FrozenActionRecord`；实体/关系/eager、join/alias/subquery/CTE、聚合/窗口/函数、text/raw SQL、prefix/suffix、statement/table hint、跨表表达式、任意层级行锁、动态/负数/超限分页和超限读取均失败关闭。PostgreSQL 额外设置事务只读，handler 的写入、DML、flush、commit 或 rollback 均失败关闭。预览结束后存在两条顺序化路径：已有 key 先无锁探测，再按 `AiAction → active 会话` 顺序锁定/重检并比较摘要；新动作则先锁定并重检所属 active 会话，再无锁复查同 key，只有仍不存在才插入；命名唯一约束竞态会整笔 rollback 后以同样的 `AiAction → active 会话` 顺序恢复赢家。原始确认 Token 仅首次响应返回，数据库只保存 SHA-256；Token 绑定动作、账号、会话、能力、规范化摘要和 10 分钟有效期。本人通过 `POST /api/assistant/actions/{id}/confirm|cancel` 操作；确认先锁 `ai_action`，再锁定并刷新所属 active 会话，之后才按 Task 4 治理 advisory/provider/profile 锁序证明会话捕获档案仍是当前完整发布版本、提供商仍启用/健康/兼容，随后重新计算当前能力，并仅通过 `ActionUnitOfWork.lock_one()/update_locked()`、`FrozenActionRecord` 快照和不暴露真实 ORM 身份的 `LockedActionRecord` 让固定 handler 复核数据范围、记录状态、归属和流程任务。每个锁定句柄绑定精确签发 UoW、Session、外层事务和 savepoint；成功更新会消费旧句柄并返回合并全部变更的新冻结快照，伪造、跨 UoW/Session/事务、事务结束后及重复使用均失败关闭。领域变更、`AiAction.succeeded`、结果实体和通用审计在嵌套 savepoint 内形成同一成功事务；处理器不得自行提交/回滚/flush，也不得获得原始事务控制或通用表写入口。处理器或成功审计失败只回滚 savepoint，在不释放动作行锁的外层事务把同一行提交为不含原始载荷/Token/异常正文的有界 `failed`；该失败状态提交本身失败时显式返回持久化失败，绝不伪称已有持久终态。处理器代码是受信任的进程内扩展代码，不是针对恶意 introspection/import hack 的沙箱；支持接口只保证正常用法下没有 Session 逃逸。取消、过期、错误 Token、重复确认、撤权、档案/版本/提供商失效、状态/处理人变化和仅 auditor 写入均失败关闭。Task 6 未注册具体业务能力；消息 SSE/工具循环已由 Task 7 实现，管理 UI 已由 Task 8 实现；领域能力处理器仍待 WA1+。当前 SQLite 自动化只验证调用顺序、归档与 prepare/confirm 竞争、回滚结果、竞态注入和 savepoint 语义；Task 9 IDC 仍须补充 PostgreSQL 只读预览、同键同参/异参双 Session 准备竞态、归档竞争及确认失败后等待会话不执行第二次 handler 的真实证据。

WA0 Task 7 已实现 `POST /api/assistant/conversations/{id}/messages` 的受控 SSE 编排。请求只接受正文、客户端消息幂等键和 Task 5 白名单页面上下文；流式事件固定为 `meta|delta|message|action|error|done`，响应使用 `Cache-Control: no-store, private`、`Vary: Authorization` 和禁用代理缓冲，完成轮恰好一个 `done`，错误后不再产生成功事件，JSON 单行编码避免 SSE 注入。认证和请求校验完成、endpoint 已接受后，归属、幂等和运行时错误均在 HTTP 200 流内以 `error → done` 表达；请求体 422、认证失败等尚未接受的错误仍使用普通 HTTP 错误。提示层把平台安全指令、不可变已发布档案、当次授权能力 schema 与明确标记为不可信的页面/知识/业务/用户正文分开，浏览器角色、权限和工具结果永不进入系统权威。泄漏检测的紧凑路径先在原始 code point 阶段只接纳 Unicode 字母/数字（`L*`/`N*`）并剔除名称或显式表中的 Hangul `FILLER`，再执行 NFKC/casefold 并再次只保留 `L*`/`N*`；原始 Mark、Control、Separator、Punctuation、Symbol（`M*`/`C*`/`Z*`/`P*`/`S*`）、零宽字符和兼容分解符号因此不能“洗成”字母切断紧凑指纹，合法全角字母/数字仍可归一。完整规范化行至少 12 字符、强片段至少 24 字符，或命中两个不同的 12–23 字符片段时拒绝输出；空串、短公共词不参与且计算受既有文本预算约束，原样、逐字符插入、标点和跨 delta 拼接均使用同一终态检测。WA0 不承诺完美识别所有视觉同形但编码不同的字符。

每次工具调用按固定 code 从注册表重新授权并用注册 Pydantic 模型校验；模型自报 handler/risk/role/result、未知/禁用 code、非法参数、重复调用及超过四轮全部失败关闭。非 L3 handler 只接收 `ReadOnlyActionData`、不可变 `ActionActorContext` 与合作式 `CapabilityExecutionContext`，不得取得 SQLAlchemy Session、`AuthUser` ORM、Connection/Engine、事务控制、raw text/DML、Core UPDATE 或可变 ORM 实体；每次调用使用独立短 Session，PostgreSQL 在读取前设置事务只读和本轮 `statement_timeout`，最终始终 rollback/close。同步 handler 由专用有界执行器运行：worker 只允许 1–32、排队只允许 0–256；调用先非阻塞预留容量，再创建能力发现/重授权 Session，满载时不查询权限、不创建 Session、不运行 handler，未知能力、非法参数、L3 prepare 完成和异常路径都释放预留。工具 deadline 只允许 0.1–60 秒，statement timeout 只允许 10–59,000 毫秒且必须严格短于工具 deadline。客户端断开或 deadline 后协程立即停止等待且不再发事件，并向合作式 handler 发出取消信号。Python 线程不能安全强杀，非合作式阻塞可能在后台继续到自身返回，但其短 Session 仍在 finally 中 rollback/close；如需硬终止任意 handler，必须使用进程隔离。已开始的 L3 prepare 可能完成为到期前的 `prepared`，但绝不执行业务变更。

Task 7 流内不存在 committed mutation result。L3 只调用 Task 6 `prepare_action()`，丢弃模型对执行成功的自由文本，由服务端生成 `authority=server_preview`、`operation_status=prepared_not_executed` 的预览消息；其他模型正文只能保存为 `authority=advisory`、`operation_status=not_executed` 的建议，不能作为 ITOM 操作或状态结果。原始规范化正文与 page context 只参与服务端密钥 HMAC 幂等摘要，密钥和原文不进入摘要字段、日志或响应，持久化正文仍先脱敏；因此同一 `client_message_id` 的同一原始请求可重放，`token=AAA` 与 `token=BBB` 等脱敏后相同但原始不同的请求仍冲突。流式路由鉴权在有界 DB worker 中创建并关闭短 Session，只返回活动账号 ID 标量；`StreamingResponse` 不持有请求 Session 或 ORM。`_TurnState` 仅保存不可变标量快照；开始/幂等、能力发现、原生降级、Gateway 提供商选择/审计、最终完成和失败清理也只使用有界 DB worker，短 Session 在 worker 内创建/关闭，不阻塞 async SSE 事件循环且不使用默认无界 executor。Provider DNS 在专用有界 DNS/IO 执行器中调用同步 `socket.getaddrinfo`，准入与等待受请求剩余 deadline 约束；生产路径不调用 `loop.getaddrinfo`、`asyncio.to_thread` 或默认 executor，满载和超时安全失败且不削弱 SSRF、DNS rebinding 与 TLS 地址绑定。`stream_turn()` 入口只创建一个 monotonic absolute deadline；fallback、start、provider/Gateway、每次 DB/工具调用和 finalization 的全部 pre-commit 工作共享剩余预算，不会按阶段重置。业务 work deadline 最多提前预留 250ms（总预算的 25%）给失败占位清理；工具、provider 和 PostgreSQL statement timeout 均取自身配置上限与本轮剩余预算的较小值。最终 worker 新事务锁定并刷新活动账号、本人 active 会话、精确当前发布档案/版本和仍为 `streaming` 的助手占位消息；权威 commit 必须在 deadline 前、锁齐并最后一次合作式检查取消后开始。commit 前超时/断流则 rollback 且不提交完成消息；一旦进入权威 commit，调用方为保持 durable `completed` 与客户端终态一致会等待 commit 和 Session 收尾，允许小幅越过 deadline，而不把已落库完成态改报超时。Gateway 取消审计以既有有界 DB executor 后台 best effort 提交，不阻塞断流；满载时不创建 Session，只记录脱敏本地告警，正常成功/可处理错误仍等待审计持久化后才输出。该护栏不承诺消除真实 socket/线程调度的所有微小竞态。归档、停用、撤回/换版、缺失或状态冲突均失败关闭且不发送成功消息。提供商不可用、超时、非法/截断协议和断流不把 partial/provider error/secret 保存为完成回答；保留期 0 只保存无正文幂等元数据。确定性降级路径通过当前账号真实权限调用“创建单据指引”计算，无授权时回退 `/`。Task 7 不注册具体领域能力且不改变 Task 6 的确认原子性；真实 PostgreSQL 双 Session 幂等竞争、锁等待和 ASGI 断连证据延期至 Task 9。

Task 7A 进一步固定最终化权威：只有 `db.commit()` 成功返回才设置线程安全 durable-success；之后的 Session close 异常只记录脱敏异常类型，不重查数据库猜测提交结果，也不能把 durable `completed` 转成 `error → done`。若 commit 已开始后观察到断流，取消语义优先并且不再发送后续 SSE 终态，即使清理同时失败；commit 自身失败不属于 durable success，必须 rollback、保留失败占位清理并返回安全错误。本修复本身不新增能力、字段、迁移、配置或前端。

WA0 Task 8 完成网页前端闭环：业务门户和内部工作台共用顶栏启动器与响应式助手抽屉；页面上下文仅从受控路由、允许的标签及显式选中 GLID 构造，不抓取 DOM、表单或浏览器凭据。POST-SSE 客户端严格限制帧/缓冲并仅接受 `meta|delta|message|action|error|done`，未知事件、非法/截断 JSON、错误后的非 `done` 或 `done` 后数据均失败关闭，认证与语言行为沿用现有 API 客户端。消息和服务端预览只按 React 文本渲染，不执行 HTML。L3 卡片覆盖待确认、确认中、取消中、成功、取消、过期、冲突和失败；Token 不展示且终态清除，只有确认 API 的服务端 `succeeded` 结果可标为权威成功。系统管理新增 `admin_ai` 路由/菜单守卫及提供商、固定档案、健康、用量、动作审计五页签控制台；提供商密钥只写、编辑不回填。Task 8 不新增后端、数据字段、WA1 领域能力或部署验收，真实 IDC 角色、动作与断流证据仍属于 Task 9。

独立 Task 8B 补齐前端消费与后端 L3 动作之间的确认桥，但不扩大 Task 8/WA0 业务能力。浏览器只新增接受启动前 `error → done(error)` 与元数据后 `meta → error → done(error)`；一旦已出现 delta、action 或 message，再出现 error，或错误终态混入成功数据，仍失败关闭且不向用户展示 provider/model 原始错误。`meta → message → done(replay)` 重放同时接受 `advisory` 与 `server_preview` 权威，但重放预览只作说明，不生成卡片、不携带 action/Token，也不能表示 mutation 已准备或可确认。仅首次同属主 L3 action SSE 通过后端固定窄投影一次性交付原始确认 Token；通用脱敏器继续将任意普通 `confirmation_token` 字段处理为 `[REDACTED]`。凭证不进入模型、消息、持久化、日志、审计或 REST 响应；只有同一属主的首次合法确认成功，重复、跨用户、过期、取消、脱敏占位和畸形值全部失败关闭。Task 8B 不新增数据字段、迁移、领域能力或部署验收。

Task 8C 不增加业务能力、迁移或部署验收。公开 action 载荷中的 `confirmation_expires_at` 和首次 action SSE 的 `expires_at` 必须是显式 `Z` 的 RFC 3339 UTC，浏览器拒绝无偏移值，故 UTC 存储语义不再被本地时区误读。实时流和 completed replay 的 `server_preview.action_id` 均须通过同一 26 位 ULID 校验，非法值在展示前失败关闭。确认经过属主、Token、期限和运行时校验后，先提交内部、不可确认/不可取消的 `executing` 声明，handler 才可开始；声明提交失败不执行 handler。后续已知 handler/审计失败可提交 `failed`，但 handler 或终态持久化不确定时保持不可重试状态并只返回安全的结果待核实，不得恢复 `prepared`、重发 Token 或把未成功提交的领域结果说成成功。Task 9 IDC UAT 尚未完成。

Task 8C Round 1 进一步规定：有效原始确认 Token 与非空、可解析、显式 `Z` 的期限是实时 action SSE 不可分割的契约；缺失、`null`、无偏移或畸形期限在 `prepared` 卡片创建前失败关闭。无 Token 的信息 action 不会因缺少期限变成可确认状态。`AI_ACTION_OUTCOME_UNKNOWN` 在卡片中只能映射为不可重试的 `executing/结果待核实`，清除 Token、禁用双按钮且不得宣称“尚未执行任何业务变更”；唯一成功文案仍仅对应服务端 `succeeded`。
