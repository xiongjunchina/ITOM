# New_AOM 系统改造建议

> 基于 SN-AOM（/Users/xjun/Gitrepo/SN-AOM）的简化重构设计基线。
> 依据：2026-07-09 产品决策 —— 保留域 1/2/3/4/6/7+9，删除域 5(Portfolio 独立域)/8(数据管理)/10(组织治理)。
> 核心目标：功能减法、大幅减少页面录入字段、派生数据一律自动计算。

---

| 新域 | 对应 SN-AOM | 处理方式 |
| --- | --- | --- |

## 二、逐域改造建议

### ① 总览 Dashboard

原系统：KPI 总览 + 跨域活动流 + 告警 + 月度趋势 + 成熟度评估（Accenture 4 级模型）。

**新版设计**：单页四板块，全部服务端实时计算，**无任何录入入口**。

| 板块 | 关键指标（计算来源） |
| --- | --- |
| 服务 | 未关闭工单数、SLA 达成率、变更成功率、问题关闭率、合同到期预警 |
| 项目 | 在建项目数、健康度分布、里程碑逾期、预算执行率 |
| 需求 | 各阶段需求数量（登记/分析/实现/关闭）、平均交付周期 |
| 团队 | 人员负载、绩效评分 Top/Bottom、成长积分排行榜、培训活动数、招聘进度 |

**砍掉**：成熟度评估（随 #10 治理域删除）、`kpi_snapshot`/`*_monthly_stats` 等预计算表（改为实时聚合，规模小无性能问题；这也顺带解决旧系统 issue #85 的 20 次串行查询问题——新版一次聚合查询出全部指标）。

### ② ITSM 服务管理（9 子模块）

| 子模块 | 原表(字段数) | 改造建议 |
| --- | --- | --- |
| 工单 | `ticket`(51) | **保留单表多类型设计**（incident/service_request/change/problem 共用一表）。创建必填 ≤8：标题、类型、优先级、描述、服务项、受理人。SLA 时限/编号/响应时间自动生成。root_cause、closure_code、满意度等移到生命周期后续阶段填写 |
| 变更 | `ticket` 内 change 字段 | 作为工单类型条件展示：选 change 类型时才出现变更窗口/回退方案/风险评估 3-4 个字段 |
| 问题 | `problem`(11) | 保留独立表（本来就轻），承接工单升级 + 需求遗留问题转入 |
| 服务目录 | `service_catalog`(13) + `service_item`(19) | 保留两层结构和 Gold/Silver/Bronze 分级，item 字段砍到 ~10（SLA 定义保留） |
| CMDB | `application`(31) + 8 张 `asset_*` 表 + `ci_relationship`(6) | **8 张资产表合并为 1 张 `ci` 表**：公共字段（名称/类别/状态/负责人/环境）+ 类别专属属性放 JSONB。application 31→~12 字段。`ci_relationship` 保留（影响分析依赖它） |
| SLA | `sla_policy`(18) + `sla_stats`(16) | `sla_policy` 简化保留（P1-P4 响应/解决时限）；**`sla_stats` 删除**，达成率实时计算 |
| 供应商 | `vendor`(9) | 原样保留（已经很轻） |
| 合同 | `contract`(11) | 原样保留 + 到期自动预警进 Dashboard |
| 知识 | `knowledge_article`(14) | 表不动，**前端表单从 38 个 Form.Item 砍到 4 个**：标题/正文/标签/关联工单。承接需求经验沉淀转入 |

**砍掉**：CSI（`csi_improvement` 17、`improvement` 14）、`itsm_governance_record`(20)、`application_deployment_history`/`application_release_history`、`sla_stats`。

### ③ 项目管理（5 标签页，原 11 个）

| 标签页 | 改造建议 |
| --- | --- |
| 项目概述 | `project` 23 字段保留核心 ~12（编码/名称/PM/起止/预算/健康度/状态）。**新增轻量 `portfolio` 表（~6 字段：名称/描述/负责人/年度）承接组合定义**，project 挂 portfolio_id 建立对应关系。健康度自动计算不录入 |
| 进度管理 | 甘特图（前端渲染，无独立表）+ WBS（`wbs_task` 19→~10：名称/负责人/起止/状态/工时/父任务/依赖）+ 里程碑（`milestone` 8 保留） |
| 成本管理 | 预算/实际成本录入极简（项目级+可选 WBS 级），SPI/CPI 自动计算展示。**不做完整 EVM 8 指标录入页** |
| 风险管理 | `risk`(7) 保留（本来就轻：概率/影响矩阵 + 缓解措施） |
| 文档管理 | 简单附件表 + **移植 `project_charter_import.py`**（上传章程自动生成项目/WBS/里程碑/风险草稿——"少录入"的支柱功能） |

**砍掉**：干系人矩阵、基线（`scope_baseline`）、质量指标页、gate review 三张表（`project_gate_*`）、`project_monthly_stats`、`risk_snapshot`、`process_gate_signal`。原 51 个 Form.Item 的项目详情页预计降到 ~15。

### ④ 需求管理（轻量协同，4 阶段生命周期）

原 `requirement` 41 字段 + 10 张周边表，重构为按阶段渐进录入：

| 阶段 | 录入内容 | 说明 |
| --- | --- | --- |
| 1. 需求登记 | 标题/类型/提出人/所属业务/描述（**5-6 字段**） | 30 秒完成登记 |
| 2. 需求分析 | 优先级(MoSCoW)/解决方案/资源排期/验收标准 | 验收标准复用 `acceptance_criterion` 简化为清单 JSON |
| 3. 实现过程 | 任务分解（新增轻量 `requirement_task` 表）/进度控制/验收闭环 | 进度按任务完成度自动计算 |
| 4. 关闭收尾 | **一键转出**：遗留问题 → ITSM `problem`；经验沉淀 → ITSM `knowledge_article` | 新增跨域联动（SN-AOM 没有），转出时自动带需求上下文 |

**砍掉**：版本快照（`requirement_version`）、多审批人工作流（`requirement_approval`）、追溯矩阵（`traceability` 降为简单的关联项目/工单字段）、调研会话（`elicitation_session`）、验证问题（`requirement_validation_issue`）、`requirement_monthly_stats`。

### ⑤ 流程引擎（保留骨架，砍重装置）

**保留**：`process_definition` → `process_instance` → `process_task` 三层 + `process_step`，L1-L4 自治级别（AOM 特色，人效管理的评分规则未来也可能用到自治级别数据）。

**简化**：

- 初始只 seed 新系统实际用到的流程（工单处理、变更审批、需求交付、项目关键节点，约 **6-8 个流程 vs 原 36 个**）
- **砍掉 72 种文档类型自动生成**（`process_document_type`/`process_step_document`/`process_document_instance` 3 张表）
- 砍掉价值流编排（`value_stream_rule`）、`process_step_skill`
- 自动派单从"n8n 按 cell/技能/负载解析"降级为"按流程步骤配置的默认角色/人员指派"（不依赖 n8n）

### ⑥ 团队管理（新域 = Workforce + Growth 合并重构）

| 子模块 | 设计 | 对应旧表处理 |
| --- | --- | --- |
| 人效管理 | 新增 `performance_rule`（评分规则，规则内容由产品后续定义，引擎按规则聚合数据）+ `performance_score`（周期评分结果，计算态）。数据源：工单（解决量/SLA/满意度）、项目（任务完成/里程碑）、需求（交付周期）、**成长积分（作为输入源之一）** | 删除 `cell_performance`(20)/`kpi_snapshot`/`growth_monthly_stats`（全是预计算表） |
| 成长积分 | 新增 `point_rule`（积分规则可配置：事件类型→分值）+ `point_entry`（积分流水，**由各域事件自动产生，用户不录积分**）。积分来源：服务贡献（工单解决/SLA 达成/满意度好评）、项目贡献（WBS 任务完成/里程碑交付）、需求开发任务完成、培训贡献（主讲/组织/参与）、知识库贡献（发表/被点有用）、建言献策（提出/被采纳/被点赞）。排行榜实时聚合流水，无预计算表；管理员可手工加减分（走流水留痕） | 替代 `growth_record`(27) 的手工录入模式和 Leaderboard 预计算 |
| 岗位编制 | `org_master`(13) 保留为人员主数据核心；新增 `position`（岗位定义/分工职责）、`hiring_need`（招聘需求与进度） | `skill`/`person_skill` 简化保留（岗位分工需要）；`ops_resource` 负载表删除改计算 |
| 培训发展 | 新增 `development_activity`（~10 字段：类型[内部交叉培训/外部技术交流/新技术研究]/主题/参与人/日期/产出链接），完成登记即触发培训积分 | 替代 `growth_record`(27) |
| 团队文化 | 新增 `team_charter` 单页内容管理（愿景/目标/工作行为准则，富文本）；新增 `idea`（建言献策：标题/内容，2 项即可提交）+ `idea_like`（点赞记录，防重复），点赞/采纳自动触发积分 | `innovation_idea`(10) 简化重构为建言献策 |

**砍掉**：AI Agent 注册表（`agent` **70 字段**、`agent_evaluation` 24）、编排路由（`orchestration_rule`）、升级规则（`escalation_rule`/`escalation_log`）、异常聚类/模型反馈（`knowledge_feedback`）、Cell 组织（降维为 org_master 上的 `team` 分组字段）。

> ⚠️ 依赖提示：流程引擎的"自动派单/升级"原本依赖 agent/cell/escalation 这套装置。按上述简化（默认角色指派）后可以安全砍掉；如果未来要恢复 AI Agent 参与工作流，再加回极简版 agent 注册表。

## 四、复用与技术栈

沿用 SN-AOM 技术栈（FastAPI + SQLAlchemy + React，便于代码移植）。直接移植的资产：

1. `project_charter_import.py` — 文档导入自动回填（少录入支柱）
2. GLID 26 位主键生成 — 沿用同一主键规范（保持团队习惯，与迁移无关）
3. `workflow_status`/`workflow_transition` 状态机 — 防非法状态跳转
4. 统一响应 `{success,data,total,page}` 约定
5. 流程引擎三层模型（简化 seed）

**数据迁移：不做。** 旧数据全部废弃，New_AOM 空库启动，业务数据由用户重新录入（2026-07 产品决策）。

**初期不做**：n8n 工作流、飞书集成、MCP servers、GitHub 集成（后续按需接 sn_feishu/sn_maestro 共享 spine，与 SN-AOM epic #51 方向一致）。

### 通知能力预留（为后续飞书集成设计）

初期无外部通知渠道，但架构上预留：

- **领域事件出口**：所有关键动作（工单创建/升级/SLA 临期、审批请求、里程碑逾期、需求转出）统一走 `notification_service.notify(event)` 单一入口，业务代码不直接发通知
- **通道适配器模式**：`NotificationChannel` 抽象接口 + `notification_outbox` 表（事件落库，含 event_type/payload/channel/status）。初期只实现 `InAppChannel`（站内消息/Dashboard 告警），后续加 `FeishuChannel` 适配器即接通，业务层零改动
- 事件 payload 遵循旧系统 `fire_workflow_event()` 的结构约定，未来对接 sn_feishu spine 时开箱即用

## 五、产品决策记录（2026-07-09 已确认）

1. **项目管理标签页** — "进度管理"重复为笔误，定稿 5 个标签页：项目概述/进度管理/成本管理/风险管理/文档管理。
2. **人效评分规则** — 框架按"规则可配置"搭建，具体规则由产品后续定义。
3. **数据迁移** — 不做，全新空库，重新录入。
4. **飞书** — 初期不接，但按上文"通知能力预留"设计。
5. **成长积分** — 保留并融入团队管理域：积分来源覆盖服务贡献/项目贡献/需求开发任务/培训贡献/知识库贡献/建言献策点赞；积分流水由各域事件自动产生（规则可配置），并作为人效评价的输入源之一。
