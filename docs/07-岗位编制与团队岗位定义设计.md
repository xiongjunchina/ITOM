# 岗位编制与团队岗位定义设计

> 状态：设计基线（2026-07-22）
> 适用范围：团队管理 → 岗位编制 → 岗位定义
> 设计目标：为 IT 团队从约 30 人扩充到 60 名正式员工、另配 10–20 名外包团队提供可执行的岗位与编制基线。

## 1. 设计原则

1. **岗位与角色分离**：岗位描述职责、能力和编制；内置角色描述系统权限。岗位可映射一个或多个角色，但岗位不自动等于权限。
2. **矩阵式组织**：横向按市场运营与销售、供应链与生产、产品研发、财经与综合服务四个业务域配置服务责任；纵向按产品、开发、运维三条专业线管理资源池。
3. **平台服务独立治理**：PMO、数据治理、AI、信息安全、架构和服务台属于跨业务域的平台/专业能力，不挂靠单一业务域。
4. **编制只统计正式员工**：岗位 `headcount` 是正式员工目标编制，外包人员不计入；外包以服务合同、交付范围和服务质量管理。
5. **先建立最小可运行骨架**：第一版岗位定义以职责边界和编制为主，后续再增加职级、技能、在岗数、地点、外包属性等字段。

## 2. 内置角色与岗位的使用边界

当前系统实际使用的内置角色包括：

| 角色码 | 角色名称 | 主要用途 |
|---|---|---|
| `admin` | 系统管理员 | 系统配置与平台维护，不作为独立业务岗位 |
| `cio` | CIO（IT 总负责人） | IT 总体治理和管理决策 |
| `it_bm` | IT 业务线负责人 | 横向业务域服务责任 |
| `it_tm` | IT 专业线负责人 | 纵向专业资源池负责人 |
| `it_pdm` | IT 产品经理 | 需求、产品和方案交付 |
| `it_pdm_leader` | IT 产品负责人 | 产品体系与产品经理团队负责人 |
| `it_pm` | IT 项目经理 | 项目交付管理 |
| `it_pmo` | IT PMO | 项目组合、流程和治理 |
| `it_dev` | IT 开发 | 开发、数据和技术实现 |
| `it_dev_leader` | IT 开发负责人 | 开发团队管理和技术交付 |
| `it_ops` | IT 运维 | 服务台、基础设施和运行维护 |
| `it_op_leader` | IT 运维负责人 | 运维团队、事件、变更和 SLA |
| `is_mgr` | 信息安全管理员 | 信息安全、风险和审计 |
| `it_bp` | IT 业务合作伙伴 | 业务对接、需求澄清和服务线协同 |
| `auditor` | 审计员 | 全局只读和审计，不作为 IT 岗位 |
| `requester` | 业务用户 | 普通员工的默认业务使用角色，不作为 IT 岗位 |

说明：一个人允许同时拥有岗位职责和多个系统角色。例如开发负责人可以同时持有 `it_dev_leader` 与 `it_tm`；业务域负责人可以同时承担某一服务线的 `it_bm` 和项目审批职责。`admin` 只授予极少数系统管理员，不应通过岗位编制批量授予。

## 4. 编制口径与外包边界

### 4.1 正式编制

岗位定义中的编制数为目标正式员工数量，当前约 30 人可逐步映射到上述岗位；岗位缺口由“编制数 − 在岗人数”计算。

### 4.2 外包团队

10–20 名外包人员不进入正式岗位编制，建议集中用于：

- 存量系统维护和专项开发；
- 测试、数据清洗、ETL 和数据迁移；
- 工厂现场支持和 L1 服务台；
- 网络、设备、实施和短期项目交付。

不建议外包团队独占企业架构、主数据责任、安全决策、变更审批、产品路线、业务需求优先级和系统最终所有权。

## 5. 对岗位编制数据模型的建议

当前岗位定义最小字段为：

| 字段 | 建议 |
|---|---|
| `name` | 岗位名称，必填，建议唯一（未删除范围内）。 |
| `duties` | 职责边界；第一版可同时记录服务域、主角色和外包边界。 |
| `headcount` | 正式员工目标编制，整数，非负。 |

为支持团队治理，本轮已实现并落地以下字段：

- `position_code`：稳定岗位编码；
- `position_family`：治理、产品、项目、开发、数据、AI、运维、安全等岗位族；
- `service_domains`：服务的业务域或专业线，多选；
- `primary_roles`：建议角色码，多选，仅作为配置建议，不直接授予权限；
- `level_framework`：初级/中级/高级/负责人等职级框架；
- `location_scope`：广州、佛山、印尼、阿曼、美国或全球；
- `skills`：岗位所需技能标签；
- `contractor_allowed`：是否允许外包承接，及外包边界；
- `status`：启用/停用；
- `onboard_count`：在岗人数建议继续计算，不要手工存储；
- `gap`：`headcount - onboard_count`，计算字段；
- `sort`：岗位展示顺序。

岗位定义与招聘需求应保持一对多：一个岗位可以有多条不同级别、不同批次的招聘需求；招聘需求单独记录级别、人数、任职资格、状态和进度。

## 6. 后续治理建议

1. 人员主数据中的 `position_id` 继续关联岗位定义；飞书同步只更新 HR 主数据，不覆盖本地岗位关联、技能和备注。
2. 角色授权继续通过用户、用户组和权限矩阵完成，不由岗位表直接写入 `auth_user.roles`。
3. 数据治理、AI、服务台等横向能力优先通过用户组表达资源池，岗位定义表达个人职责。

## 7. 本轮实现状态（2026-07-22）

以上建议已落地到“团队管理 → 岗位编制”页面：

- 岗位定义已补齐岗位编码、岗位族/序列、服务业务域、主责角色、职级/能力框架、办公地点范围、关键技能、是否允许外包、启停状态和排序字段；岗位表单支持维护这些字段。
- 正式编制仍只统计 IT 团队中的正式在岗人员（历史未填写用工类型的在岗人员按正式员工兼容），`正式在岗` 与 `编制缺口` 均为实时计算字段，不落库。
- 岗位定义列表支持服务端分页、岗位名称/编码检索、编制/在岗/缺口展示；`position_id` 仍由人员主数据维护，组织同步不会覆盖本地岗位关联。
- 岗位定义支持“导出 Excel”（带说明行，可直接修改回导）、“下载导入模板”和“批量导入”。导入按岗位编码优先、岗位名称兜底匹配，支持新建和更新，并返回逐行失败原因。
- 招聘需求继续与岗位一对多关联，支持级别、人数、任职资格、状态和进度备注；同样支持数据导出、模板下载和批量导入。导入可按导出的需求 ID 更新，也可按岗位编码/名称创建新需求。
- 系统管理员与 CIO 默认拥有岗位定义、招聘需求的编辑和删除权限；两个清单均支持行内修改、保存、取消和删除。岗位仍被人员或招聘需求引用时，系统会阻止删除并提示先处理关联。
- Excel 导入统一限制 `.xlsx` 和 5MB，成功行入库、失败行保留行号与原因；导入和批量变更写入审计日志。可恢复的非法列宽（部分在线表格导出器会写入超大列号）会自动清洗后继续导入；其他损坏/非标准 Excel、字段超长、岗位编码与名称冲突、已删除岗位编码等情况会作为逐行导入错误返回，不再以 500 中断整个请求。

接口约定：`GET /api/positions/template`、`GET /api/positions/export`、`POST /api/positions/import`；招聘需求对应 `/api/hiring-needs/template`、`GET /api/hiring-needs/export`、`POST /api/hiring-needs/import`。
