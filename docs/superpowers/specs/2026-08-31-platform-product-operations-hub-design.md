# 平台产品运营中枢设计（方案 B）

> 状态：**P0 已形成并通过本地验证的候选版本；P1/P2 尚未实施**
>
> 批准日期：2026-08-31
>
> 权威版本：本文为中文权威版本；英文镜像见 [`docs/en/superpowers/specs/2026-08-31-platform-product-operations-hub-design.md`](../../en/superpowers/specs/2026-08-31-platform-product-operations-hub-design.md)。
>
> 架构决策：[`ADR-0001：以可选扩展档案与受控观测台账建设平台产品运营中枢`](../../adr/0001-platform-product-operations-overlay.md)

## 1. 背景与目标

数字化团队转型后，一部分人员以 FDSE 方式贴近业务域，平台产品与赋能组集中承担平台产品组合、需求统筹、容量承诺、赋能资产和经营分析。流程设计、数据、AI、集成与架构治理分别由专业系统承载，ITOM 不替代这些系统。

本设计把 ITOM 定位为**平台产品与赋能组的运营管理控制台**，目标是：

1. 复用现有服务目录、需求、项目、ITSM、投入和报表能力，避免建立第二套主数据；
2. 管理平台服务、需求、容量、承诺、投入、采纳、可靠性和管理决策；
3. 通过受控引用和指标观测接入专业系统，只汇聚管理摘要、承诺、证据和同步状态；
4. 让管理者可以从平台服务穿透到需求、投入、承诺、采纳和可靠性事实；
5. 保持现有 Aily、MCP、Web Agent、领域服务、RBAC、审计与幂等边界不变。

## 2. 产品定位与边界

### 2.1 定位

ITOM 是平台产品与赋能组的运营管理控制台，负责平台服务、需求、容量、承诺、投入、采纳、可靠性及管理决策；专业流程、数据、AI、集成和架构系统继续保存专业执行事实，ITOM 只汇聚其管理摘要、承诺、证据和同步状态。

### 2.2 系统记录边界

| 信息 | 权威记录系统 | ITOM 的职责 |
|---|---|---|
| 服务目录、需求、项目、工单、统一投入 | ITOM | 保存领域事实并执行自身业务校验 |
| 流程分类、流程设计与执行细节 | 专业流程系统 | 保存外部引用、状态摘要与管理观测 |
| 数据、AI、集成、架构治理细节 | 各专业系统 | 保存外部引用、承诺、证据、同步状态和指标观测 |
| 平台容量计划与承诺 | ITOM | 版本化计划、审批、容量占用和例外审计 |
| 管理报表 | ITOM | 按公式版本和数据质量生成、审核、发布和锁定 |

### 2.3 非目标

- 不在 ITOM 内复制 APQC、数据治理、模型治理、集成开发或架构设计功能；
- 不建立通用 HTTP、SQL、Shell 或任意数据库写入能力；
- 不把外部系统的专业记录批量复制为 ITOM 业务主记录；
- 不把平台服务组合扩展为完整项目组合治理、阶段门、企业能力地图或路线图执行系统；
- 本阶段不新增 Aily/MCP/Web Agent 工具，也不授权智能体直接写表。

## 3. 角色与责任

| 角色 | 主要责任 | 关键限制 |
|---|---|---|
| FDSE | 在授权业务域登记需求、补充业务结果、查看服务与承诺进展 | 不审批容量计划，不查看未授权业务域或敏感跨人员明细 |
| 专业平台团队 | 更新本人/本团队承诺、交付证据和专业系统引用 | 不改变已批准容量基线，不替代平台产品负责人决策 |
| 平台产品经理 | 维护平台服务档案、需求池、目标、赋能资产和优先级建议 | 不自行批准超容量承诺 |
| 平台负责人 | 审核平台服务组合、批准容量计划与常规承诺 | 超容量需 CIO 例外批准 |
| CIO/数字化负责人 | 批准超容量例外、正式报告发布和重大组合决策 | 必须留下理由、审批与审计证据 |
| 系统管理员 | 配置权限、外部系统、同步策略和技术运行参数 | 管理员身份不替代业务审批人 |

责任分配沿用现有用户、角色、用户组、部门和数据范围模型，不新建第二套身份或组织体系。

## 4. 可复用基线与差距

### 4.1 当前可复用能力

- `ServiceItem` 已承载服务项，可作为平台服务的基础记录；
- `Requirement` 已承载需求，可通过可选档案增加平台分类和服务归属；
- 项目、WBS、ITSM 工单与通用关联关系可以承载实施和运营穿透；
- 统一投入台账已支持预算、费用、工时、分摊及 `demand/build/run`、`run/grow/transform` 口径；
- 统一报表中心已支持指标查询、模板、正式版本、受众、穿透与 Excel 导出；
- 现有权限服务、审计、工作流、示例只读和数据范围机制继续复用。

### 4.2 主要差距

1. 服务项缺少平台产品负责人、价值主张、生命周期和管理范围；
2. 需求缺少目标平台服务、业务域、预期结果、容量类别和目标季度；
3. 没有季度容量计划、正式承诺、版本锁定和超容量控制；
4. 没有赋能资产、服务目标和外部专业记录的标准化管理摘要；
5. 报表中心尚无平台服务组合、容量、采纳、赋能和可靠性指标；
6. 外部来源缺少同步运行、数据新鲜度、公式版本、冲突和质量状态审计。

## 5. 产品范围与用户故事

### 5.1 平台服务

- 作为平台产品经理，我可以在现有服务项上启用平台服务档案，而不复制服务项；
- 作为管理者，我可以查看负责人覆盖、生命周期、目标、需求、投入、承诺和运行表现；
- 作为服务负责人，我可以维护管理属性，但不能绕过服务目录的原有权限。

### 5.2 平台需求池

- 作为 FDSE，我可以把授权业务域的需求关联到目标平台服务并说明预期结果；
- 作为平台产品经理，我可以按服务、业务域、需求类别、季度和容量类别统筹需求；
- 作为需求负责人，我仍在现有需求流程中推进状态，不创建第二条需求生命周期。

### 5.3 容量与承诺

- 作为平台负责人，我可以建立季度容量计划，扣除不可用时间、日常运维预留和风险缓冲；
- 作为平台产品经理，我可以把需求、路线图、可靠性和赋能工作转为容量承诺；
- 作为 CIO，我可以在提供理由并留下审计时批准超容量例外；
- 已批准计划不可原位修改，调整必须形成新版本。

### 5.4 赋能与分析

- 作为平台团队，我可以登记模板、脚本、指南、沙箱、培训和自服务资产；
- 作为管理者，我可以在现有报表中心查看平台组合、需求、容量、投入、采纳、赋能和可靠性；
- 作为审计人员，我可以从报表指标穿透到内部记录或外部来源、同步运行和观测证据。

## 6. 总体架构与集成

```text
服务目录 ─┐
需求管理 ─┼─> 平台运营域 ─> 统一报表中心（平台分析域/模板）
项目/WBS ─┤       │
ITSM ─────┤       ├─ 平台服务档案、容量计划、承诺、赋能资产
统一投入 ─┘       └─ 外部引用、同步运行、指标观测
                         ▲
流程/数据/AI/集成/架构专业系统 ── 受控只读接入 ──┘
```

### 6.1 集成原则

1. 外部专业系统继续是其专业事实的 System of Record；
2. 第一阶段接入默认为只读，连接器按具体系统和接口逐个批准；
3. 外部记录使用稳定来源标识和链接引用，不冒充 ITOM 主记录；
4. 每次同步必须记录水位、数量、结果、错误和执行时间；
5. 指标观测必须保留来源时间、接收时间、公式版本、质量和来源证据；
6. 不提供可由界面配置任意 URL、SQL、请求头或数据库语句的通用连接器。

### 6.2 Aily/MCP/Web Agent 边界

ITOM 领域服务和 API 继续是 ITOM 数据的唯一写入边界。MCP 工具不得直接写数据库，也不得绕过业务校验、工作流、RBAC、审计和幂等。本设计不新增智能体能力；未来如需开放，只能在独立批准的后续阶段通过代码注册、用户授权和风险分级实现。

## 7. 领域与数据设计

所有新模型均为增量设计，现有记录不受影响。平台档案采用显式启用，不通过批量回填推断业务含义。

| 目标模型 | 关系与用途 | 关键字段（概要） |
|---|---|---|
| `platform_service_profile` | 与 `service_item` 1:1 的可选平台产品档案 | `service_item_id`、`owner_id`、`lifecycle`、`value_proposition`、`management_scope`、审计字段 |
| `platform_demand_profile` | 与 `requirement` 1:1 的可选平台需求档案 | `requirement_id`、`service_item_id`、`business_domain_id`、`demand_class`、`expected_outcome`、`target_quarter`、`capacity_class` |
| `platform_capacity_plan` | 按平台服务/团队/季度建立的版本化容量计划 | `period`、`version`、`status`、`gross_days`、预留与缓冲、`net_days`、批准信息 |
| `platform_capacity_commitment` | 容量计划内对具体工作的正式承诺 | `plan_id`、对象类型/ID、`commitment_type`、`capacity_days`、投入分类、负责人、状态 |
| `platform_enablement_asset` | 赋能资产目录 | 类型、名称、服务、负责人、版本、状态、目标受众、外部引用 |
| `platform_service_objective` | 服务采纳、可用性、自服务或交付目标 | 服务、周期、指标键、目标值、单位、公式版本、状态 |
| `external_system` | 外部来源登记 | 来源代码、类型、负责人、同步模式、新鲜度阈值、启停状态；不保存明文密钥 |
| `external_work_reference` | ITOM 实体与外部工作/设计/流水线记录的关联 | 内部对象、外部系统、外部 ID/URL、记录类型、同步摘要 |
| `external_sync_run` | 同步执行审计 | 外部系统、开始/结束、水位、读入/成功/失败数量、结果、错误摘要 |
| `platform_metric_observation` | 外部采纳、使用和 SLO 等周期观测 | 指标键、服务、周期、数值、单位、来源时间/接收时间、公式版本、质量、来源引用/同步运行 |

### 7.1 兼容性

- 不重命名、不复制 `ServiceItem` 或 `Requirement`；
- 未启用平台档案的现有服务项和需求保持原有行为；
- 统一投入继续是预算、费用、工时和分摊的唯一内部台账；
- 通用关联关系继续用于 ITOM 内部记录；外部引用使用独立模型，避免误用内部外键；
- 正式报告保存所引用观测 ID，后续纠正生成新版本，不改写历史报告。

## 8. 状态、流程与业务规则

### 8.1 平台服务生命周期

`candidate → pilot → active → retiring → retired`

退役不删除历史需求、投入、承诺、观测或报告证据。跨越状态或恢复为活动态必须按权限记录原因。

### 8.2 容量计划

`draft → review → approved → superseded`

- 已批准基线不可修改；修订创建新版本，旧版本进入 `superseded`；
- 净容量 = 总容量 − 计划不可用 − BAU 预留 − 风险缓冲；
- 承诺容量合计默认不得超过净容量；
- 超容量必须由 CIO/数字化负责人提供理由并留下审批和审计；
- 承诺工作使用现有 `run/grow/transform` 与 `demand/build/run` 分类。

### 8.3 外部观测质量

质量状态至少包括 `ok`、`stale`、`error`、`conflict`、`no_data`。没有有效分母时比率显示为 `N/A`，不得显示为 `0%`。冲突、过期和错误数据不得以正常状态进入管理结论。

## 10. 指标目录与数据质量

| 主题 | 代表指标 | 主要来源 |
|---|---|---|
| 服务组合 | 活跃服务数、负责人覆盖率、SLA 覆盖率、生命周期分布 | 服务目录 + 平台服务档案 |
| 需求 | 待办量、承诺率、平均/P50/P90 时效、业务域/类别分布 | 需求 + 平台需求档案 |
| 容量 | 可用/承诺人天、利用率、预留、超容量、缺口 | 容量计划与承诺 |
| 投入 | 服务成本/人天、投入分类、活跃用户单位成本 | 统一投入 + 观测 |
| 采纳 | 可覆盖/活跃用户、采纳率、自服务率、使用量 | 外部指标观测 |
| 赋能 | 有效资产数、使用量、入门周期、完成率 | 赋能资产 + 外部观测 |
| 可靠性 | SLO 达成、事件量、MTTR、错误预算 | ITSM + 服务目标 + 外部观测 |

每个指标必须声明：指标键、名称、业务定义、公式版本、单位、时间粒度、来源、过滤口径、质量规则、敏感级别和穿透目标。来源按“现有内部可计算”“需新增内部事实”“依赖外部观测”标识，界面不得把三者混为同等成熟度。

## 11. 权限、安全与审计

计划新增权限模块：

- `platform_portfolio`：平台服务档案与需求池；
- `platform_capacity`：容量计划、承诺、审核与例外；
- `platform_enablement`：赋能资产和服务目标；
- `platform_integrations`：外部系统、引用、同步和观测管理；
- 继续使用 `reports_platform` 保护平台分析，`reports_publish` 控制正式发布。

权限采用现有 `AuthUser`、`RolePermission`、`UserGroup`、自定义角色和数据范围框架。管理员可以配置系统，但不能冒充业务审批。外部凭据不得出现在 URL、日志、报表、提示词、测试数据或响应中；连接配置只能返回是否已配置等非敏感状态。

## 12. 信息架构与交互

计划新增顶层“平台运营”菜单组：

1. 平台服务；
2. 平台需求池；
3. 容量与承诺；
4. 赋能资产。

外部系统配置放入“系统管理”。“报表中心”继续位于侧边栏最底部，并在内部增加“平台分析”领域、指标和报告模板，不新增重复的顶层报表入口。

列表沿用共享表格规范：前两列冻结、表头单行、内容默认单行、按内容计算初始列宽、横向滚动、列设置、分页和可访问图标操作。详情页的新增平台信息作为独立附加区放在原有业务内容底部，避免打断既有流程。

## 13. 迁移与兼容策略

1. 通过增量表和可选外键发布，不修改既有业务记录语义；
2. 首次上线不自动把全部服务项标记为平台服务，也不推断需求分类；
3. 由平台产品经理分批启用档案并完成业务确认；
4. 外部系统先登记来源和引用，再逐个批准连接器；
5. 指标先显示来源与质量，再逐步开放正式报告；
6. 所有迁移均需提供回滚和兼容读取方案，现有 Aily/MCP/ITSM/项目/需求/报表流程不得回归。

## 14. 决策与备选方案

采用方案 B/T2：**可选扩展档案 + 受控观测台账**。

| 方案 | 结论 | 原因 |
|---|---|---|
| T1：直接向服务项、需求增加大量字段 | 不采用 | 耦合高、迁移风险大，所有记录被迫承担平台语义 |
| T2：可选扩展档案 + 受控观测台账 | 采用 | 最大化复用现有领域，增量、可审计、可分阶段实施 |
| T3：新建完整平台管理子系统 | 不采用 | 重复服务、需求、投入和报表能力，建设与维护成本过高 |

详细后果与风险见 ADR-0001。

### P1：管理闭环

1. P1-1 赋能资产；
2. P1-2 外部系统和工作引用；
3. P1-3 外部观测、同步运行和数据质量；
4. P1-4 采纳、可靠性和单位投入指标；
5. P1-5 周报、月报、季报等平台运营模板。

1. P2-1 经单独批准的具体专业系统连接器；

连接器必须等具体来源系统、接口契约、身份、数据范围和错误恢复方案明确后再实施。

## 16. 验收标准与非回归

- **P0 已验证**：不产生第二个服务项或需求主实体；平台档案仍以现有主记录为事实来源；
