# IT 员工单据分流与跨单据关联设计基线

> 状态：**阶段 A/B/C 已实现；阶段 D 待实施**
> 确认日期：2026-07-31
> 中文为权威版本；英文镜像见 `docs/en/superpowers/specs/2026-07-31-it-staff-intake-and-record-relations-design.md`。

## 1. 背景与目标

ITOM 同时管理服务请求、事件、问题、变更、IT 需求和项目。普通业务员工未来以飞书 Aily 为主要入口；他们不应理解或选择 ITIL 单据类型。IT 团队则需要一个轻量、可解释的网页分流入口，以降低近乎零 ITIL 基础时的误建单率，并让单据在需要时可审计地关联和转出。

本设计只解决 IT 员工的网页分流、页面解释、单据推荐和跨单据关联；不改变 Aily 的现有业务用户入口、MCP 工具范围、任何既有单据的真实类型、历史数据或既有流程实例。

## 2. 已确认范围与边界

### 2.1 两类入口严格分离

| 使用者 | 入口 | 可创建范围 | 本设计影响 |
| --- | --- | --- | --- |
| 普通业务员工 | 飞书 Aily（后续通常不登录 ITOM） | 服务请求、IT 需求 | **不变**。Aily 仍不创建事件、问题、变更或项目，也不提供转单。 |
| IT 员工、系统管理员 | ITOM 网页全局“创建单据指引”入口 | 由实际创建权限决定 | 新增轻量决策向导、推荐和跳转。 |
| 管理员/CIO | ITOM 网页 | 由权限矩阵决定 | 可管理相关权限、审计和后续统计。 |

统一入口只在 IT 员工可访问的网页中展示，不新增给业务用户的 Web 入口，也不改变 Aily 的服务请求创建、需求登记、查询、确认、重开和评价路径。

### 2.2 单据定义不变

| 单据 | 何时使用 | 不应误用为 |
| --- | --- | --- |
| 服务请求 | 单个用户对既有 IT 能力的故障、协助、访问、安装、配置或咨询 | 大范围 IT 事件；新系统/新功能需求 |
| 事件 | 网络、服务器、应用等大范围影响或监控自动发现的中断 | 单人“软件打不开”等服务请求 |
| 问题 | 已知错误、反复发生的故障或需根因分析的事项 | 单次服务请求本身 |
| 变更 | 有计划、需风险控制/审批/实施窗口的生产环境修改 | 普通故障处理或新功能需求本身 |
| IT 需求 | 新系统、新功能、优化、重构等需评估的想法 | 直接替代生产变更 |
| 项目 | 需章程、WBS、里程碑、资源/成本/风险管理的交付，通常人力投入达到项目门槛 | 普通临时任务 |

## 3. IT 员工轻量分流体验

### 3.1 入口与向导

全局按钮命名为“创建单据指引”。点击后打开抽屉或弹窗，不新增持久化的“分类问卷”字段。向导以 2–4 个临时问题给出推荐，用户可改选；最终仍进入目标单据的现有创建表单。

推荐问题与初始规则如下：

1. 是否影响多名用户、一个服务或核心系统？是，优先推荐“事件”。
2. 是否是反复发生、已知错误或需要定位根因？是，优先推荐“问题”。
3. 是否需要在生产环境按计划修改，并考虑风险、回退或窗口？是，优先推荐“变更”。
4. 是否是新系统、新功能、优化或重构想法？是，优先推荐“IT 需求”。
5. 其他已有能力的个人故障、协助或申请，推荐“服务请求”。

规则只输出“推荐单据类型、推荐理由、反例和目标创建入口”；不保存回答、不产生新业务字段、不替代最终人工选择，也不改变目标表单的权限、必填项和流程校验。

### 3.2 页面解释与案例库

每个六类单据列表/详情/创建页面在标题旁展示一行紧凑说明：“适用场景 + 一个正例”，并提供“查看示例”入口。默认不展开长文，避免页面头重脚轻。

“IT 单据速查”案例库以服务请求、事件、问题、变更、IT 需求、项目六类组织，至少提供：定义、适用情形、非适用情形、典型例子、常见误选后的正确去向。它是帮助内容和决策向导的共享来源，首期使用可版本化的规则/静态配置，不使用 LLM 自动判定。

## 4. 转单与关联：创建目标单据，不改变原单据类型

### 4.1 不可突破的原则

1. **原单据永不改类型**：不得把 `service_request` 直接改写为 `incident`，不得删除、强制关闭或覆盖原单据。
2. **先创建目标，再建立关系**：目标单据须完成自己的必填字段、权限、领域校验和流程启动；关系只在目标创建成功后写入。
3. **双向可见、全过程可审计**：源/目标详情都显示关系类型、对方编号、创建人、创建时间、转出理由及跳转入口；写入审计日志。
4. **各走各的生命周期**：原单据与目标单据保留各自状态、SLA、流程实例、权限和关闭规则，不因建立关系自动关闭或推进对方。
5. **失败不留半成品**：目标创建、关系写入和审计应在一个事务边界内；失败时不创建关系。重复提交必须幂等。

### 4.2 首期支持的关系类型

| 源单据 | 目标单据 | `relation_type` | 业务语义 | 继承与补充 |
| --- | --- | --- | --- | --- |
| 服务请求 | 事件 | `upgraded_to_incident` | 多用户/广域影响升级处理 | 可带标题、描述、CI、影响线索；补事件级别/影响范围等必填项 |
| 服务请求、事件 | 问题 | `root_cause_of` | 需要根因分析或已知错误管理 | 可带现象、时间线、关联 CI；补问题分类/负责人等必填项 |
| 事件、问题 | 变更 | `remediated_by_change` | 修复需要受控生产修改 | 可带根因/处置建议/CI；补风险、回退、窗口和实施方案 |
| IT 需求 | 项目 | `converted_to_project` | 评估后进入项目化交付 | 可带需求背景、目标、验收标准；补章程和项目必填项 |

现有 `problem_ticket` 仍保留，继续承担问题与工单的既有专用关系；新通用关系不能删除或重写这张表。实现时必须避免对同一业务关系重复展示。

### 4.3 权限、幂等与通知

- 发起人须同时具备源记录查看权限与目标单据创建权限；可见范围按现有 RBAC/数据范围/流程授权复核。
- 不能借“转单”绕过目标单据的创建、审批、流程或字段校验；前端隐藏从不是授权。
- 每一次提交携带 `idempotency_key`。同一操作者、同一源、同一目标类型、同一请求键重试返回首次结果；相同键但不同参数拒绝。
- 关系创建写入不可变审计事件，并按目标领域既有通知策略通知目标责任人；首期不因关联自动通知普通业务提交人，除非目标领域已存在用户可见通知规则。
- 首期不提供普通用户解除关系；避免破坏审计。若未来确有治理需求，只能由管理员以软删除、原因和审计方式处理。

## 5. 通用关系模型（方案 A）

新增 `record_relation`，作为跨域、双向可查询的通用关联模型；它使用实体类型 + 实体主键，不建立跨多表的多态数据库外键。完整性由领域服务在同一事务中验证。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `source_entity_type` / `source_entity_id` | 源实体类型与主键 |
| `target_entity_type` / `target_entity_id` | 目标实体类型与主键 |
| `relation_type` | 上表定义的受控枚举 |
| `reason` | 转单/关联理由；必填且有最小长度 |
| `created_by` / `created_at` | 创建审计 |
| `idempotency_key` / `request_digest` | 同一操作者、来源、目标类型的重复请求返回首个结果；同键异参拒绝 |
| `deleted_at` / `deleted_by` / `delete_reason` | 预留软删除审计字段；首期不开放删除 UI/API |

约束与索引：

- 联合唯一约束：活动关系的 `(source_entity_type, source_entity_id, target_entity_type, target_entity_id, relation_type)`。
- 源、目标和关联类型均建立组合索引，支持任一详情页的双向查询。
- 不允许同一实体记录自关联；允许同为 `ticket` 的服务请求→事件关系。实体组合由服务端白名单控制，不由客户端传入任意类型。
- 不迁移、不回填、不重写现有 `Ticket.problem_id`、`problem_ticket`、`Requirement.project_id`（如已有）及历史流程/审计数据。

## 6. API 与前端边界（阶段 B/C 已实现）

这些端点均已上线：

```text
POST /api/staff-intake/recommend
  # IT 员工；输入临时答案，返回推荐类型、理由、反例和可访问目标入口；不落库

GET  /api/it-document-guide
  # 已登录用户；返回六类紧凑说明与案例库；前端按权限决定可见创建入口

POST /api/record-relations/prepare
  # 源记录 + relation_type；复核源查看/目标创建权限，返回可安全继承字段与目标必填字段

POST /api/record-relations/submit
  # 目标表单数据 + relation_type + reason + idempotency_key；来源行锁与摘要幂等，调用目标领域服务创建记录、写关系和审计

GET  /api/records/{entity_type}/{entity_id}/relations
  # 已实现：受数据范围约束的双向关系列表；源记录和对端都须对当前用户可见
```

阶段 B 已实现 `record_relation` 的 PostgreSQL 增量迁移、活动关系/幂等唯一约束、不可变审计、读接口及服务请求/事件/变更、问题、需求、项目详情页的双向安全展示；既有专用关联保持不变。阶段 C 已实现 `prepare/submit` 和详情页“创建并关联”抽屉：服务端不信任客户端目标类型，而是从白名单推导；在 PostgreSQL 来源行锁下先用 Pydantic 规范化目标表单和关联说明求摘要，再复核同一操作者/来源/目标类型/幂等键。相同请求返回首个目标、同键异参拒绝；未命中才调用事件、问题、变更、项目领域服务，在同一事务写目标、流程、关系和审计。每个领域服务仍负责自身字段、状态、流程、审批、RBAC、审计和事件发布。

## 7. 分期实施与验收

| 阶段 | 交付 | 关键验收 |
| --- | --- | --- |
| A（已实现） | IT 员工入口、临时决策向导、六类紧凑说明、案例库 | Aily 普通用户路径无变化；问题不落库；推荐可解释且可改选；页面说明不超过一行默认高度 |
| B（已实现） | `record_relation` 模型、迁移、读接口、详情双向关联区、审计/权限/幂等 | 现有数据和专用关系无丢失；无权限用户看不到关系；重复提交不产生重复关系 |
| C（已实现） | 四类“创建目标 + 关联”路径 | 目标流程独立启动；原单据类型/状态不被改写；失败无半成品；每条关系可追溯理由 |
| D | 推荐命中率/改选率、误建单反馈和案例库维护 | 基于真实 IT 员工使用数据优化规则，不改动 Aily 权限边界 |

每一阶段均需：后端迁移/单元与 API 回归测试、前端构建、中文权威文档和英文镜像同步、IDC Kubernetes 发布及真实 IDC 用户流程验证。Aily/MCP 无须为本设计新增工具；任何后续 Aily 范围扩展必须另行设计确认。

## 8. 非目标与后续决策

- 不以 AI 自动替代 IT 员工对事件、问题、变更或项目的专业判断。
- 不给普通业务用户网页入口增加 ITIL 分流负担。
- 不增加持久化的分类问卷字段或无必要的选填项。
- 不在首期处理“解除/反转已建关系”、复杂多级关联图或跨单据自动闭环。
- 智能推荐若将来采用 LLM，必须单独确认模型、数据边界、人工确认、审计与降级规则。
