# 用户身份与组织模型设计（M3.5 / M3.6）

> 2026-07-10/11 产品决策定稿。设计对标 ServiceNow 的用户/组/角色/组织四轴模型。
> 三条铁律：**用户永远可持多角色，绝不绑死**；**归属是字段不是角色**；**角色优先挂组**。

## 一、四轴模型与页面定位

| 概念 | 表 | 回答的问题 | 页面 | 权限语义 |
| --- | --- | --- | --- | --- |
| 账号 | `auth_user` | 你怎么登录、直接持有哪些角色 | 用户管理 | 直接角色 |
| 人员 | `org_member` | 你是谁（中英文名/部门/岗位/联系方式/技能） | 人员主数据 | **无** |
| 部门 | `department` | 你在公司组织架构的哪里（一人一部门，树形，类型 it/business/audit） | 部门管理 | **无**（仅作开通规则匹配依据） |
| 用户组 | `user_group` | 你和谁一起干活、单子派给谁 | 用户组 | **组授予角色**：人进组自动继承 |
| 角色 | `role` | 你在系统里能做什么 | 角色管理 | 10 内置 + 自定义（继承内置） |
| 业务域 | `business_domain` | 服务哪条业务线、谁负责 | 业务域 | **无**（owner 是字段不是角色） |

**有效角色 = 直接角色 ∪ 所属组授予的角色 ∪ 自定义角色继承的内置角色。** 登录响应的 `roles` 即有效角色（前端菜单以此渲染），`direct_roles` 为直接角色。

## 二、第 10 个内置角色：auditor 审计员

- 权限边界：**全模块只读 + 审计日志查看**，不能修改任何单据（全局只读中间件强制，例外：登录、通知已读回执）。
- 多角色不受限：auditor + it_ops 的用户可正常写（只读限制仅对"只持有 auditor"的用户生效）。
- **不自动授予**：审计部门用户开通默认也是 requester；auditor 由管理员手工授予（直接授予，或拉入带 auditor 角色的组）。

## 三、账号开通（JIT Provisioning）

```text
认证源适配器(AuthProvider) → 认证成功返回用户画像(ProvisionProfile)
  → provision_user(): find-or-create 账号+人员档案
      - 首次创建：按开通规则(provision_rule)赋默认角色
      - 再次登录：仅同步档案（姓名/部门/联系方式），角色绝不重置
```

- **开通规则**（admin 可配，仅首次生效）：按部门类型（it/business/audit）或具体部门匹配 → 默认角色列表；具体部门规则优先，sort 小者优先，命中即停。种子默认：三类部门都 → `requester`。
- **认证源**：`auth_user.auth_source`（local/ad/feishu/sms/wechat）+ `external_id`。当前仅 local；AD 域/飞书/短信/微信在上线前实现各自适配器注册进 `PROVIDERS`，业务层零改动。
- 管理员手工建账号不选角色时，同样按规则取默认（依据关联人员的部门）。

## 四、组织数据来源：飞书是 Source of Truth（M3.9 定稿）

**公司人员主数据存于飞书，以飞书为准**（2026-07-11 产品决策）。落地为三层：

1. **同步引擎已实现**（`services/org_sync.py`，与提供方无关、可测试）：`apply_org_snapshot()` 按 `(external_source, external_id)` 幂等 upsert；**外部赢**（飞书值覆盖本地）；两遍建部门父子与人员上级关系；外部消失的人员→标记**离职**（保留档案与历史单据关联），消失的部门→停用；本地手工记录（external_source 为空）不受同步影响。飞书 API 客户端上线前注册进 `SYNC_PROVIDERS`，触发接口 `POST /api/admin/org-sync`（未配置时 501）。
2. **已同步记录本地锁定**：人员的 HR 基础字段（姓名/工号/性别/出生日期/用工类型/上级/办公地点/部门/联系方式/入职/状态）与部门结构字段后端拒改（SYNCED_READONLY）；**本地仅维护 IT 扩展**——人员的岗位/技能/备注、部门的 it/business/audit 分类。飞书管 HR，New_AOM 管 IT 扩展。
3. **开发期手工录入是过渡**：同一套字段，接入后被同步接管。

**字段映射（飞书通讯录 → org_member）**：name→name、en_name→name_en、employee_no→employee_no、gender→gender、employee_type→employment_type、leader_user_id→supervisor_id（经 external_id 二遍解析）、city→work_location、mobile/email 直映、department_ids[主部门]→department_id、open_id→external_id；部门 open_department_id→department.external_id、parent→parent_id。公司名为本地配置（master_data sys_config/company_name）。

## 五、迁移记录

M3.5 启动迁移（`services/migrate.py`，幂等）：

1. 为存量表补新列（create_all 不加列）：org_member 5 列、auth_user 2 列、user_group.roles。
2. `org_member.dept`（文本）→ 按名 find-or-create `department`（名含"IT"→类型 it）并回填 `department_id`，然后删列。
3. `org_member.team`（文本）→ find-or-create `user_group` 并建成员关系，然后删列。

## 六（M3.6）、矩阵式 IT 组织映射

IT 内部矩阵式管理（2026-07-11 产品输入）在模型中的表达：

| 组织概念 | 系统承载 |
| --- | --- |
| 横向·服务线（业务域，BM 带领 BP/开发服务某业务域） | `business_domain`：owner=BM（字段）+ `business_domain_member` 服务团队 |
| 纵向·专业线（资源池，TM 统一管理某技术方向人员） | `user_group`：owner=TM（字段）+ roles 组授予角色（如开发资源池授予 it_dev）+ 成员 |
| 专业身份 | 角色：it_pdm/it_pm/it_dev/it_ops/is_mgr/it_bp + 自定义补充（数据治理、AI 等） |
| 管理层 | cio（IT 总负责人）/ it_bm / it_tm 三个内置角色（manager 已于 2026-07-11 移除） |
| 一人多角色 | 铁律保障；权限取所持角色矩阵的并集 |

内置角色定稿 **12 个**：admin、cio、it_bm、it_tm、it_pdm、it_pm、it_dev、it_ops、is_mgr、it_bp、auditor、requester（manager 已移除，无存在必要）。**内置角色名称/描述可改**（代码、继承关系、删除锁定）。

## 七（M3.6）、功能权限矩阵

- **粒度**：模块（30 个，与菜单页面对齐）× 动作（view 可见含查看 / create / edit / delete）。存储 `role_permission`（role_code × module → actions）。
- **判定**：用户权限 = 直接角色 ∪ 组授予角色 的矩阵**并集**；admin 隐式全权不入矩阵、不可配置（防锁死）。登录响应携带 `permissions`，前端菜单/按钮以此渲染，后端 `require_perm(module, action)` 强制。
- **边界**（三层权限各管一段，互不冗余）：
  1. 功能矩阵：页面可见与增删改开关（本节）
  2. 数据范围：如 requester 仅见自己的工单、知识草稿仅作者可见——业务代码内置，不进矩阵
  3. 流程权限：状态机流转 allowed_roles、流程步骤 default_role——在状态机配置/流程定义页管理
- **自定义角色**：创建时**复制**所选模板角色（base_role）的矩阵为初始值，之后独立编辑；base_role 同时保留"流程引用继承匹配"语义（流转规则写 it_ops 时，继承 it_ops 的自定义角色也匹配）。
- 默认矩阵编码在 `services/permissions.py`（DEFAULT_MATRIX），仅首次启动种子写入，之后以库内配置为准。

## 九（M3.7）、ITIL 对齐的预置流程 v2（2026-07-11 重配）

| 流程 | ITIL 实践 | 步骤 → 默认角色 |
| --- | --- | --- |
| 事件处理 | Incident Management | 受理定级(it_ops) → 诊断与处理(it_ops) → 解决与用户确认(it_ops) → 关闭复盘(it_tm) |
| 服务请求交付 | Service Request Mgmt | 受理确认(it_ops) → 实施交付(it_ops) → 用户确认关闭(it_bp) |
| 变更管理 | Change Enablement | 变更登记与风险评估(is_mgr) → 变更审批(cio) → 实施与验证(it_ops) → 变更复盘 PIR(it_tm) |
| 问题分析 | Problem Management | 问题确认(it_ops) → 根因分析(it_ops) → 解决与验证(it_ops) → 关闭复盘(it_tm) |
| 需求交付（预配置，M5 挂接） | — | 需求登记与业务对齐(it_bp) → 需求分析与方案(it_pdm) → 排期与资源协调(it_bm) → 开发实现(it_dev) → 验收与关闭(it_pdm) |

状态机：变更审批/拒绝流转 allowed_roles = **[cio, it_tm]**；审批通知按 allowed_roles 动态解析接收人（含组与继承）；SLA 临期升级通知 → 受理人 + cio/it_tm 持有者。全部可在状态机配置/流程定义页继续调整。

## 十（M3.8）、流程节点标准：处理人 / 知会人（后续所有流程功能强制遵循）

对齐 RACI：每个流程节点两类参与者，配置页必须同时支持且以**流程示意图**直观呈现——

| 参与者 | 字段 | 语义 | 行为 |
| --- | --- | --- | --- |
| **处理人**（R/A） | `process_step.default_role`（单值：角色码或 group:组码） | 审批或执行 | 产生待办任务、阻塞流程推进；自动指派解析（受理人优先→角色/组内在岗成员） |
| **知会人**（I） | `process_step.cc_roles`（列表：角色码/group:组码） | 仅被通知 | 节点激活时发站内通知（事件 `process.step_cc`，通道适配器将来同步到飞书）；**不产生任务、不阻塞流程**；自动排除与处理人同人 |

- 配置校验：知会键必须是有效角色或用户组，否则 INVALID_STEPS。
- 流程定义页每个流程展示**流程示意图**（节点卡片：步骤名 + 处理人蓝标 + 知会人灰标 + 自治级别/SLA），编辑器内实时预览。
- 单据详情流程条同步展示知会人。
- 种子示例：变更管理流程四步分别知会 it_tm / it_bm / is_mgr+it_bm / cio。
