# 用户身份与组织模型设计（M3.5–M3.9 / M34–M37 / Aily-MCP）

> 2026-07-10/11 产品决策定稿。设计对标 ServiceNow 的用户/组/角色/组织四轴模型。
> 三条铁律：**用户永远可持多角色，绝不绑死**；**归属是字段不是角色**；**角色优先挂组**。
> 2026-07-29 增补的 Aily + MCP 身份模型已在 P0 实现；P1/P2 业务工具复用现有功能权限并强制本人数据范围，已通过自动化协议、权限、跨用户隔离、确认/重开和评价测试。冻结版 Helpdesk 身份链路已从新分支运行路径移除。

## 一、四轴模型与页面定位

| 概念 | 表 | 回答的问题 | 页面 | 权限语义 |
| --- | --- | --- | --- | --- |
| 账号 | `auth_user` | 你怎么登录、直接持有哪些角色 | 用户管理 | 直接角色 |
| 人员 | `org_member` | 你是谁（中英文名/部门/岗位/联系方式/技能） | 人员主数据 | **无** |
| 部门 | `department` | 你在公司组织架构的哪里（一人一部门，树形，类型 it/business/audit） | 部门管理 | **无**（仅作开通规则匹配依据） |
| 用户组 | `user_group` | 你和谁一起干活、单子派给谁 | 用户组 | **组授予角色**：人进组自动继承 |
| 角色 | `role` | 你在系统里能做什么 | 角色管理 | 17 内置 + 自定义（继承内置） |
| 业务域 | `business_domain` | 服务哪条业务线、谁负责 | 业务域 | **无**（owner 是字段不是角色） |
| 外部身份 | `external_identity` [P0 已实现] | 某租户/应用中的飞书标识映射到哪个 ITOM 账号 | Aily/飞书集成 | **无**（只建立身份，不授予角色） |

**有效角色 = 直接角色 ∪ 所属组授予的角色 ∪ 自定义角色继承的内置角色。** 登录响应的 `roles` 即有效角色（前端菜单以此渲染），`direct_roles` 为直接角色。

## 二、内置角色：auditor 审计员（17 个内置角色之一）

- 权限边界：**全模块只读 + 审计日志查看**，不能修改任何单据（全局只读中间件强制，例外：登录、通知处理，包括通知弹窗“一键已读”和“清除已读”）。
- 多角色不受限：auditor + it_ops 的用户可正常写（只读限制仅对"只持有 auditor"的用户生效）。
- **不自动授予**：审计部门用户开通默认也是 requester；auditor 由管理员手工授予（直接授予，或拉入带 auditor 角色的组）。

## 三、账号开通（JIT Provisioning）

```text
认证源适配器(AuthProvider) → 认证成功返回用户画像(ProvisionProfile)
  → provision_user(): find-or-create 账号+人员档案
      - 首次创建：按开通规则(provision_rule)赋默认角色
      - 再次登录：仅同步档案（姓名/部门/联系方式），角色绝不重置
```

- **开通规则**（admin 可配，仅首次生效）：按部门类型（it/business/audit）或具体部门匹配 → 默认角色列表；具体部门规则优先，sort 小者优先，命中即停。种子默认：三类部门都 → `requester`。
- **认证源**：`auth_user.auth_source`（local/ad/feishu/sms/wechat）+ `external_id`。local 与飞书已实现：飞书支持扫码 OAuth、工作台应用免登、首次开通审批及登录后绑定/换绑；AD/短信/微信仍为预留适配器。
- **业务用户自动开通**：飞书工作台登录时，若身份已由通讯录同步到 ITOM、属于非数字化/IT 范围、邮箱本地部分合法且没有人员/外部身份/用户名冲突，系统幂等创建或绑定账号，用户名取邮箱 `@` 前缀，初始化 `requester`（业务用户）角色并激活登录；初始化密码只使用部署配置并以加密形式保存，绝不写入日志或接口响应。IT 范围人员仍进入管理员开通审批，不能因自动分支获得业务用户权限；对尚未完成部门类型标注的同步树，路径中明确标注“信息技术/信息化/数字化/IT”的人员也按 IT 处理。条件不满足时保持原有待审批链路。
- 管理员手工建账号不选角色时，同样按规则取默认（依据关联人员的部门）。

## 四、组织数据来源：飞书是 Source of Truth（M3.9 定稿）

**公司人员主数据存于飞书，以飞书为准**（2026-07-11 产品决策）。落地为三层：

1. **同步引擎与飞书提供方已实现**（`services/org_sync.py` / `services/feishu.py`）：`apply_org_snapshot()` 按 `(external_source, external_id)` 幂等 upsert；**外部赢**（飞书值覆盖本地）；两遍建部门父子与人员上级关系；外部消失的人员→标记**离职**（保留档案与历史单据关联），消失的部门→停用；本地手工记录（external_source 为空）不受同步影响。触发接口 `POST /api/admin/org-sync` 未配置时返回 501。
2. **已同步记录本地锁定**：人员的 HR 基础字段（姓名/工号/性别/出生日期/用工类型/上级/办公地点/部门/联系方式/入职/状态）与部门结构字段后端拒改（SYNCED_READONLY）；**本地仅维护 IT 扩展**——人员的岗位/技能/备注、部门的 it/business/audit 分类。飞书管 HR，ITOM 管 IT 扩展。
3. **开发期手工录入是过渡**：同一套字段，接入后被同步接管。

**M35 异步同步协议**：管理端触发后由后台线程和独立数据库会话执行，接口立即返回；`feishu_config.last_sync_stats.status` 记录 `running/done/failed`，运行中重复触发返回 `SYNC_RUNNING`。前端轮询状态，完成或失败后向触发账号/人员发送站内通知。

## 四-A、账号生命周期与个人身份（M36–M37）

- `auth_user` 与 `org_member` 生命周期分离：删除账号只做软删除、停用和人员解绑，人员档案与历史业务引用保留；内置 admin 和当前账号禁止删除。
- 账号开通面向全公司人员：用户管理和飞书开通审批使用不带 `scope` 的人员列表，可关联任一未删除 `org_member`。数字化 IT 团队范围只约束 IT 工作负责人、用户组和绩效对象，不能阻止业务人员绑定登录账号；列表响应返回可读人员姓名和部门，禁止把内部 GLID 作为显示名。
- 用户编辑接口区分“未提交 `person_id`”与“明确提交 `person_id: null`”：前者保持现有关联，后者解除账号与人员档案的关联；解除关联不会删除人员主数据、部门、用户组成员关系或历史业务记录。
- 浏览器扫码和飞书工作台免登共用同一身份处理：已绑定活动账号直接登录；未开通身份进入 `login_request` 审批流程。
- 组织架构管理页默认展示公司及其一级部门名称；点击部门或展开箭头可逐级展开下级部门，直到人员节点。完整部门树和人员数据仍由后端保留，继续用于人员选择器、数据范围、同步和权限校验，不删除或裁剪存量组织数据。
- 账号可在个人中心绑定/换绑飞书身份；一个飞书 open_id 只能占用一个活动账号。解绑要求先设置本地密码，防止解绑后失去登录方式，且不解除账号与人员档案的关系。
- Aily 调用不再沿用 Helpdesk guest 身份或交接令牌。MCP 验证 `x-aily-jwt` 后，根据 provider、tenant_id、app_id、subject_type、subject_id 查询 `external_identity`，映射到唯一活动 `auth_user`；映射失败、账号停用或租户/Agent 不在白名单时拒绝调用。
- 现有 `auth_user.external_id` 继续兼容登录/绑定，但不能承载多个应用的全部身份。OAuth/组织同步应用与 Aily 机器人应用可能生成不同 `open_id`，必须分别保存外部身份记录；只有经过验证的映射才能授权用户级工具。
- MCP Secret、机器人 App Secret 和 JWT 不进入浏览器 URL、前端状态、提示词、工具结果或普通审计正文。机器人主动消息只使用服务端保存的加密凭据，并把收件标识限制为已验证身份。
- M44 起批准时生成 12 位初始密码并加密保存，不自动发信；管理员可在用户详情按需查看或手工邮件发送，两者均审计。用户改密或管理员重置后清除可恢复密文。
- `preferences` 承载语言、头像、个人说明、通知分类、主题、内容密度等账号级设置；个人审计视图按当前账号 actor 隔离。

**字段映射（飞书通讯录 → org_member）**：name→name、en_name→name_en、employee_no→employee_no、gender→gender、employee_type→employment_type、leader_user_id→supervisor_id（经 external_id 二遍解析）、city→work_location、mobile/email 直映、department_ids[主部门]→department_id、open_id→external_id；部门 open_department_id→department.external_id、parent→parent_id。公司名为本地配置（master_data sys_config/company_name）。

## 六（M3.6）、矩阵式 IT 组织映射

IT 内部矩阵式管理（2026-07-11 产品输入）在模型中的表达：

| 组织概念 | 系统承载 |
| --- | --- |
| 横向·服务线（业务域） | `business_domain`：owner/backup_owner + 服务团队均使用 `org_settings` 配置的数字化团队范围（部门成员 ∪ 单独指定人员）；服务部门可覆盖下级部门；无需求引用时管理员可删除 |
| IT 工作人员选择口径 | 项目/需求/工单/问题/服务项/配置项（技术负责人及应用产品经理）/合同/用户组等工作下拉使用 `GET /api/members?scope=it`；账号关联不在此范围，必须可选择全公司未删除人员 |
| 纵向·专业线（资源池，TM 统一管理某技术方向人员） | `user_group`：owner=TM（字段）+ roles 组授予角色（如开发资源池授予 it_dev）+ 成员 |
| 专业身份 | 角色：it_pdm/it_pm/it_dev/it_ops/is_mgr/it_bp + 自定义补充（数据治理、AI 等） |
| 管理层 | cio（IT 总负责人）/ it_bm / it_tm 三个内置角色（manager 已于 2026-07-11 移除） |
| 一人多角色 | 铁律保障；权限取所持角色矩阵的并集 |

绩效评审不直接把 `auth_user` 的角色当作评分主体。每个考核期生成 `performance_role_assignment` 快照，记录人员的业务/专业角色、业务域或专业资源池范围、评审人和 `review_mode`。读取未发布考核期的人效总览、评审列表或员工明细时，系统会检测当前在岗 IT 人员的有效角色与快照是否偏离，并自动补齐/软删除角色分配；已发布或锁定周期保持历史版本不变。业务服务线负责人只初评其业务范围内的业务角色，专业线负责人只初评其专业范围内的专业角色；平台角色默认 `review_mode=cio_direct`，由 CIO 直接评分。任何负责人不得评价自己，负责人本人的角色分由 CIO 终审。

内置角色定稿 **17 个**：admin、cio、it_bm、it_tm、it_pdm、it_pdm_leader、it_pm、it_pmo、it_dev、it_dev_leader、it_ops、it_op_leader、is_mgr、it_bp、auditor、bdo、requester（manager 已移除，无存在必要）。**内置角色名称/描述可改**（代码、继承关系、删除锁定）。

`bdo` = **Business Digital Owner（业务数字化经理）**，由业务部门指定，是业务侧的 Business PO 与 Data Steward：收集和过滤一线痛点、定义业务规则、对 UAT 保有业务否决权、推动内部推广培训，并维护业务术语和数据质量。BDO 属于业务用户的受控子集，初始仅获得服务请求、知识查询以及 `requirements.create/view`；本人需求数据范围仍受 `requester == 当前 auth_user.id` 约束，不能因此取得评审、项目、流程或 IT 内部任务权限。普通 `requester` 不再拥有需求模块权限，历史 `requester → requirements` 权限行会在启动时幂等移除，不改写历史需求数据。

## 七（M3.6）、功能权限矩阵

- **粒度**：模块（与菜单页面对齐，包含 `learning_growth`）× 动作（view 可见含查看 / create / edit / delete）。存储 `role_permission`（role_code × module → actions）。
- **判定**：用户权限 = 直接角色 ∪ 组授予角色 的矩阵**并集**；admin 隐式全权不入矩阵、不可配置（防锁死）。登录响应携带 `permissions`，前端菜单/按钮以此渲染，后端 `require_perm(module, action)` 强制。
- **边界**（三层权限各管一段，互不冗余）：
  1. 功能矩阵：页面可见与增删改开关（本节）
  2. 数据范围：如 requester 仅见自己的工单、知识草稿仅作者可见——业务代码内置，不进矩阵
  3. 流程权限：状态机流转 allowed_roles、流程步骤 default_role——在状态机配置/流程定义页管理
- **流程单据有限回改（M92）**：功能 `edit/delete` 权限不是运行中流程的绕过通道。首节点待办未被处理人首次实际查阅前，创建账号可编辑内容并删除；后续节点待办未被首次查阅前，只有上一节点 `completed_by` 对应的实际完成人可编辑内容。当前处理人首次打开详情、完成、同意或驳回都会持久化 `process_task.viewed_at/viewed_by` 并关闭窗口；列表、通知、管理员仅查看详情和管理员的未处理改派不关闭窗口。上游回改不能修改派单人、实施交付人、项目经理、业务域、服务项等路由字段；管理员仍为系统级例外。既有流程待办保持不启用，不追溯扩大权限。
- **任务管理权限模块**：`task_development`（开发任务）、`task_bug`（Bug 修复）、`task_delegated`（委派任务）独立于历史 `req_tasks`（需求实现任务）。IT 团队成员默认可登记 Bug 和委派任务；开发负责人可维护开发任务、Bug 及委派任务；Bug 所属系统产品经理具备 Bug 确认/验证所需的 `task_bug` 权限。具体单据编辑、分派和删除仍由任务服务按登记者、负责人、流程节点和管理员数据范围校验，不能仅凭前端按钮或功能矩阵放行。
- **人效权限模块**：建议将 `performance_result`（结果查看）、`performance_review`（分级评审）、`performance_external`（外部原数据）、`performance_admin`（规则/周期/发布）作为独立模块。功能矩阵决定页面和动作，`performance_role_assignment.review_scope` 再限制业务域、专业资源池和可编辑的评分条线。
- **人效可见性**：业务/专业负责人可见授权范围内的系统参考分和初评字段；CIO 可见全部内部明细并进行终审；被评价者只有 `performance_result.view`，且接口只返回已发布最终结果，不返回任何微调页面数据。
- **人效字段权限**：负责人不得修改团队贡献原始积分、外部原始数据或另一条线的评分；平台角色、业务/专业负责人本人的评分由 CIO 直接填写。外部原数据锁定后只能通过新版本修订。
- **学习成长权限**：IT 员工可维护自己的学习成长目标；系统管理员、CIO 和 IT 团队负责人可查看团队目标，进度变更自动回算 `learning_growth` 团队贡献积分。
- **培训活动记录权限**：创建时记录 `development_activity.created_by`。培训活动的编辑、删除仅允许 admin、CIO 或该登记人，且后端按活动记录重新校验；存量无登记人且无法从创建审计回填的记录仅 admin/CIO 可维护。变更主讲/参与人或删除会改变培训积分时，只允许当前未发布、未锁定周期；非计分资料编辑仍保留审计。
- **积分规则权限**：团队贡献活动规则属于 `ideas` 活动积分页面，读取使用 `ideas.view`，修改硬规则仅允许 admin（隐式全权）和 CIO。岗位职责结果规则属于 `performance_admin` 的人效评分→计分规则页面，由角色档案、维度、取数口径和流程/RACI 节点映射维护。当前考核期活动读模型按最新有效团队规则展示自动事件积分，规则停用显示为 0；原始 `point_entry`、历史周期和已发布/锁定周期不回写。每次修改写入对应审计实体。
- **自定义角色**：创建时**复制**所选模板角色（base_role）的矩阵为初始值，之后独立编辑；base_role 同时保留"流程引用继承匹配"语义（流转规则写 it_ops 时，继承 it_ops 的自定义角色也匹配）。
- 默认矩阵编码在 `services/permissions.py`（DEFAULT_MATRIX），仅首次启动种子写入，之后以库内配置为准。

## 九（M3.7）、ITIL 对齐的预置流程 v2（2026-07-11 重配）

| 流程 | ITIL 实践 | 步骤 → 默认角色 |

## 十一、Aily + MCP 身份与普通用户权限（P0/P1 已实现）

### 11.1 Aily JWT 到 ITOM 用户

1. Nginx 将 `x-aily-jwt` 原样转发给内嵌 MCP Server，不记录完整头值。
2. Aily 在自定义 MCP 创建完成后才展示 `identityJWTSecret`；首次注册阶段仅允许 `initialize`、`tools/list` 等只读协议发现，且仍须启用 MCP 并命中 Origin 白名单，不能执行任何工具。
3. `tools/call` 只接受配置的 HS256 Secret，校验签名、`exp`、`tenant_id`、`agent_id` 和 Origin；缺失或不匹配直接拒绝。Aily 官方文档把用户 open ID 写为 `user_id`，但 2026-07-29 真实租户请求使用 `feishu_open_id`；服务端兼容两者并统一按 `open_id` 字符串处理。
4. 验签通过但租户尚未批准或用户尚未映射时，服务端只登记 `external_identity.status=pending` 候选并拒绝工具执行；管理员在飞书集成页确认 ITOM 账号、将租户加入白名单并激活映射后才能授权。
5. 活动外部 subject 通过 `external_identity` 映射到 `auth_user`；身份比较使用恒定时间比较，ID 全部按字符串处理。
6. 只有活动账号才能继续；随后由 ITOM 现有角色、权限矩阵、数据范围和流程守卫授权。
7. 每次工具调用写入脱敏 `mcp_tool_call`。`get_current_user_context` 只返回验证状态、账号状态和可读账号名；P1 业务工具只返回公开业务编号和用户可见摘要，不向模型返回 open_id、tenant_id、agent_id 或 ITOM 内部主键。

### 11.2 业务用户与 BDO 能力

- 搜索自己可申请的上架服务项并取得真实表单；
- 创建 `service_request` 并查看本人服务请求；P2 可列出本人待确认单据、按明确工单编号确认解决或未解决重开，并评价本人已关闭服务请求；
- 普通业务用户只能创建和查看本人服务请求；仅 BDO 使用现有 `requirements.create/view` 登记和查看本人 IT 需求，服务层强制 `requester == 当前 auth_user.id`；
- 不得创建 IT 事件或变更，不得查看他人单据，不得执行评审、改派、审批或内部流程任务。

服务请求工具不接受 `ticket_type`；需求登记调用独立 Requirement 领域服务。前端隐藏不是权限边界，网页 API、MCP 工具和领域服务都必须执行一致的后端约束。

### 11.2a IT 员工网页分流与转单权限（阶段 A/B/C 已实现）

“创建单据指引”对 ITOM 网页中的 IT 员工和系统管理员展示，不授予普通业务用户；分流推荐是临时、可改选的帮助，不保存问答。服务端同时检查 IT 员工或管理员资格与至少一个真实目标创建权限，并按当前权限过滤可跳转入口，不能绕过目标单据权限。该网页指引独立于 Aily MCP 工具；Aily 的 IT 需求工具本身仅向 BDO 和授权 IT 角色开放。

阶段 B 的关系读接口已按源/目标双方的可见性裁剪，不能通过已关联记录越权读取另一张单据；详情页也只展示该安全结果。阶段 C 的 `prepare/submit` 已实施：操作者必须同时拥有源单据的查看数据范围和目标单据的 `create` 权限；服务端从白名单推导目标类型，来源行锁期间先校验幂等键/请求摘要，再由目标领域服务继续校验其必填字段、流程节点、审批、角色和数据范围并同事务写关系。管理员拥有的系统级权限不允许代替业务提交人确认服务请求，也不改变 Aily 的普通用户边界。

### 11.2b 网页智能体身份、会话归属与能力裁剪（WA0 Task 2、5、6、7、8 已实现）

网页智能体只接受当前 ITOM 登录会话，不接收前端自报角色，也不复用 Aily JWT。每轮对话只根据活动账号、`effective_roles`、功能权限矩阵、已发布档案的能力代码和最高风险生成一次性可发现能力清单。普通 requester 仅服务请求；BDO 增加本人 IT 需求；IT 员工按真实授权获得内部模块指导和分阶段操作；管理员仍受“不能代提交人确认”等业务硬规则约束。记录数据范围、状态、所有权和当前流程任务不属于发现阶段的执行授权；固定处理器必须在调用领域服务时重新校验它们。

模型档案只决定表达、知识范围、已关闭能力和允许的最高风险等级，不能授权。Task 6 的 L3 handler 必须同时具有 `authorize_preview`、`preview` 和 `authorize_record`。预览只接受当前登录用户和服务端注册能力，使用注册输入模型重新校验；递归脱敏若改变规范化输入则统一拒绝，绝不把脱敏替代值持久化或执行。`authorize_preview/preview` 只接收独立预览 Session 内重新加载的 actor 上下文与 `ReadOnlyActionData` 门面，后者不暴露 Session-like 属性，只接受显式、有界的 SQLAlchemy `Select` 标量投影，返回递归冻结的 `FrozenActionRecord`，并统一拒绝实体/关系结果、eager 结果、所有行锁、text/DML、过大 offset 与超限读取。`authorize_preview` 在独立回滚 Session 中先验证当前数据范围/所有权/可见性，跨用户、未分配和不存在记录使用同一非泄漏错误，未通过前不得返回元数据；PostgreSQL 预览事务额外只读。模型或客户端自报的能力、风险、角色、处理器、SLA、队列、流程、分派和状态均不授权。确认凭证绑定 ITOM 用户、所属网页会话、能力、参数摘要和十分钟有效期，只存储凭证散列且只能消费一次。准备存在两条顺序化路径：已有 key 先无锁探测，再按 `AiAction → active 会话` 顺序锁定/重检并比较摘要；新动作则在预览结束后先锁定并刷新所属 active 会话，再无锁复查同 key，只有仍不存在才插入；命名唯一约束竞态会整笔 rollback 后以同样的 `AiAction → active 会话` 顺序恢复赢家。确认在锁定动作行后先锁定并刷新所属 active 会话，再按 Task 4 治理锁序证明会话绑定的档案/版本仍是当前完整发布状态及提供商仍启用、健康、兼容，再重载活动账号和当前有效角色/组权限，最后仅通过 `ActionUnitOfWork.lock_one()/update_locked()`、`FrozenActionRecord` 快照和不暴露真实 ORM 身份的 `LockedActionRecord` 让固定处理器在 mutation 前重新校验数据范围、记录状态、所有权、当前流程任务和领域不变式。处理器代码是受信任的进程内扩展代码，不是针对恶意 introspection/import hack 的沙箱；支持接口只保证正常用法下没有 Session 逃逸。审计员不可执行 L3，非归属动作与非归属会话一样返回统一 404；取消也仅限所属用户和 `prepared` 状态。SQLite 仅覆盖确定性锁序/回滚/savepoint 以及归档与 prepare/confirm 竞争；PostgreSQL 只读预览、准备竞态与确认失败等待者的双会话证据留待 Task 9 IDC 验收。

Fix Round 4 不改变用户角色或数据范围，但收紧授权处理器可见的数据形态：预览查询必须是单一直接映射表的安全标量 AST，不能通过子查询、CTE、join、函数、text、跨表表达式或任意层级行锁扩大可见范围；mutation 锁定句柄还必须属于精确签发 UoW、Session、外层事务和 savepoint，且一次成功更新后立即失效并轮换。身份、记录锁和事务范围因此不能由 handler 通过复用或伪造句柄跨越。

Fix Round 5 不改变用户角色或数据范围；它禁止 handler 通过 SQLAlchemy prefix、suffix、statement hint 或 table hint 绕过同一数据范围和行锁边界。四类原始修饰只要存在即在执行前统一拒绝，不因字符串内容、方言或当前数据库而例外。

Task 5 的创建、列表、详情和归档均从当前认证会话取得数据库 `auth_user_id`，不接受前端自报的用户、角色或权限；任一未归属会话均以相同 404 拒绝，管理员也没有隐含的用户会话审计入口。浏览器只能传递规范化站内 route、有限 page/entity/tab 与不超过 20 个 GLID；DOM/HTML、提示词、Cookie、请求头、外部 URL、协议相对 URL、穿越式路径和所有额外字段均被拒绝。普通消息写入还会重新加载当前数据库身份并要求其有效受众与会话档案一致；档案停用、删除、未发布或运行时版本证明失败时均停止新正文持久化。用户只能读取本人对话；管理员默认只读取运行指标和动作审计，不读取完整对话。完整身份与隐私契约见 [`docs/superpowers/specs/2026-08-01-itom-web-agent-design.md`](superpowers/specs/2026-08-01-itom-web-agent-design.md)。

Task 7 的消息流同样只使用当前登录账号：路由只传递不可变账号 ID，并在网络流开始前结束请求依赖事务；开始、能力发现、每次工具、L3 prepare 与最终消息分别在独立短 Session 中重新加载活动账号和授权事实，跨 provider await 不持有 `AuthUser` 或其他 ORM。跨用户访问即使来自管理员也失败关闭；endpoint 接受前仍为普通 HTTP 错误，接受后则以 HTTP 200 SSE `error→done` 表达，不泄露会话是否属于他人。浏览器、page context、知识正文、业务记录和模型工具结果全部属于不可信数据，任何其中声明的角色、权限、handler、风险或结果都不能提升能力。每次工具调用都按固定 code 从注册表重新发现并授权；L1/L2 handler 只取得 `ReadOnlyActionData`、不可变 `ActionActorContext` 和合作式执行上下文，PostgreSQL 在读取前设只读事务和严格短于工具 deadline 的 statement timeout，未知/禁用 code、非法参数、重复调用及所有 Session/ORM/DML 逃逸均失败关闭。专用有界执行器满载时在工具 Session 创建前拒绝；断流/deadline 会立即停止等待、不再发事件并通知合作式 handler 取消。Python 同步线程不能被安全强杀，非合作式阻塞可在后台继续到返回，但 Session 始终 finally rollback/close；硬终止任意 handler 需要进程隔离。L3 流式阶段只可为当前本人会话准备动作，不可确认、执行或替代提交人；服务端结果明确为“待确认、未执行”，最多保留 `prepared` 至过期且绝不执行。最终消息使用固定锁序：先 `FOR UPDATE + populate_existing` 锁账号并在锁后校验 active/deleted，再锁本人 active 会话、精确当前档案/版本和 `streaming` 占位状态，任一身份或运行时变化均不提交成功回答。真实 PostgreSQL 账号锁等待仍由 Task 9 留证。

Task 7 Fix Round 3 不改变身份或角色模型，只收紧运行边界：每次工具调用先预留有界执行容量，再创建能力发现/重授权 Session；满载时不会读取账号权限或运行 handler。开始/幂等、能力发现、权限感知降级、Gateway 提供商选择/审计、最终完成和失败清理等同步数据库边界均在线程 worker 内创建/关闭短 Session，不阻塞 SSE 事件循环。最终化在 provider 返回后复查连接，并在锁齐账号/会话/档案/占位后以及写 `completed`、commit 前合作式检查断流取消；已观察断流则 rollback。该措施是代码级合作式护栏，不承诺消除真实 socket/数据库锁调度的全部微小竞态，真实 PostgreSQL/ASGI 证据仍归 Task 9。

Task 7 Fix Round 4 继续不改变账号、角色或数据范围语义。仅消息流路由改用异步标量鉴权：Bearer 解析后的账号查询在共享有界 DB worker 自有短 Session 中完成并在返回前 rollback/close，endpoint 和 `StreamingResponse` 只保留 `actor_id` 字符串，不跨线程或网络等待传递请求 Session/`AuthUser` ORM。账号鉴权、Gateway 选择/审计与编排 DB worker 满载均失败关闭；最终账号仍按既定第一锁位重新 `FOR UPDATE + populate_existing` 校验。整轮共享一个绝对 deadline，账号/权限重授权和最终化不能通过阶段重置延长授权窗口；真实 PostgreSQL 锁等待和 ASGI socket 临界竞态仍由 Task 9 验证。

Task 7 Fix Round 5 仍不改变任何账号、角色或数据范围。Provider DNS 使用独立有界 DNS/IO executor 并受请求剩余 deadline 约束，不会把解析隐式排入默认 executor。断流取消的 provider 审计改为既有有界 DB executor 的后台 best effort：取消立即传播，满载不创建 Session，后台 Session 最终关闭；正常成功与可处理错误仍等待审计落库。最终事务继续先锁账号并重验活动状态；所有 pre-commit 工作严格受单一绝对 deadline 约束，deadline 前通过最后取消检查并进入权威 commit 后，为保证数据库 `completed` 与客户端终态一致会等待 commit/Session 收尾，可能小幅越过 deadline。真实 PostgreSQL commit/断流微竞态与真实 socket 证据仍由 Task 9 验证。

Task 7A 仍不改变账号、角色或数据范围；它只把最终化权威拆分为线程安全的 commit-started 与 durable-success，后者仅在 `db.commit()` 成功返回后设置。提交后的 Session close 异常只记录脱敏异常类型，不能把已持久化 `completed` 改报错误；commit 已开始后观察到断流时取消优先且不再发送 SSE 终态，commit 自身失败则保持既有 rollback、失败占位清理和安全错误路径。

Task 8 不改变账号、角色、数据范围或执行授权。全局启动器只在既有已认证的业务门户/内部工作台外壳中渲染；页面上下文由前端固定路由、允许标签和显式选中 GLID 白名单构造，不能读取 DOM、表单、Cookie、Token、权限矩阵或角色声明。`admin_ai` 菜单和 `/admin/ai-assistant` 路由守卫仅控制入口可见性，后端逐端点 `require_perm` 仍是最终权威；provider secret 只写且编辑时不回填。L3 卡片只把服务端预览标为待确认，客户端不会从模型文字推断成功，只有本人确认接口返回的 `succeeded` 才显示权威成功；Token 不展示并在终态清除。

Task 8B 不改变上述身份或权限矩阵。原始确认 Token 只在“当前数据库账号为动作属主、首次 L3 prepare、同一受控 action SSE”这一窄边界一次性交付，不能由客户端角色声明、模型文本、重放消息或其他用户取得。重放的 `server_preview` 不携带 action/Token，也不产生确认入口。确认仍按数据库 `auth_user_id` 查询本人动作并在锁行后校验状态、期限和摘要；跨用户统一不可见，重复、过期、取消、`[REDACTED]` 或畸形凭证均失败关闭。凭证不进入模型、持久化正文/结果、日志、审计或 REST 响应，通用递归脱敏规则保持不变。

Task 8C 继续以数据库属主与服务端状态为唯一授权事实。通过属主、Token、期限和运行时复核后，服务端必须先提交内部 `executing` 声明；其后任何重复或并发确认均因不再是 `prepared` 而拒绝，不能再次进入 handler。声明或后续终态持久化无法确认时不签发新 Token、不恢复可确认状态，也不向用户声称业务成功。浏览器对 action 期限只接受带 `Z` 的 UTC 线缆格式，重放 `server_preview.action_id` 必须与实时 action 使用同一 ULID 校验；这些校验不接纳模型或客户端自报的替代身份/状态。

Round 1 不改变身份映射或权限矩阵，但把原始 Token 的浏览器边界收紧为“有效 Token + 非空显式 UTC `Z` 期限”同时成立才可形成 `prepared`；缺任一条件均无确认入口。结果不确定不会降格为已知的 `failed/未执行`：卡片清除 Token 并显示不可重试的 `executing/结果待核实`，只有服务端已提交 `succeeded` 才能对所属用户显示成功。

Task 2 的 `capabilities_for_user()` 不接受浏览器或模型自报的角色/受众；它仅以用户 ID 重新加载活动、未删除的 `AuthUser`，再调用现有 `effective_roles()`、`user_permissions()` 和 `has_perm()`。requester 只可发现其服务请求范围；BDO 仅在此之外增加需求能力；直接和用户组授予的 IT 角色都按既有有效角色生效；仅 auditor 账号不得发现 L2/L3；admin 仍仅能发现已注册的非 L4 能力。已发布且启用的档案版本可以按明确能力代码和最高风险收窄发现结果；无完整已发布档案、停用账号或无角色均失败关闭。能力处理器、内部角色/权限细节和被禁用能力不进入模型 schema。

固定注册表拒绝重复能力代码、无确认策略的 L3、所有 L4、无 Pydantic 输入模型和无处理器的定义；输入字段/别名还必须通过凭据及授权内部名称的分段校验，覆盖字段名、普通别名、`validation_alias`/`serialization_alias`、`AliasPath` 的每个字符串段及 `AliasChoices` 的全部替代路径，拒绝授权上下文、权限范围/矩阵和角色 ID。任意 `dict`/`Mapping`（含嵌套或列表项）及其可导出任意键 `additionalProperties` 的 schema 一律在注册和导出前失败关闭，能力输入只能使用有限、显式的 Pydantic 字段契约。导出的字段 schema 删除 `default/example(s)` 元数据和值但保留 `properties` 内同名的合法业务字段。该注册检查不替代业务执行检查：未来每个记录级处理器仍要在调用领域服务前重新验证数据范围、记录状态、所有权和当前流程任务。入模、`AiMessage.content` 持久化和普通日志/审计摘要必须调用相同的递归确定性脱敏；mapping 键和文本赋值共用分类，保证密码、Token、Secret、Cookie、Authorization、API/access/private key、Bearer/JWT 文本及动态敏感表单值不会保留原值。

WA0 在系统管理模块中登记 `admin_ai`（AI 智能体）。该模块不写入 requester、BDO、IT 员工或 auditor 的默认权限矩阵；只有 `admin` 通过既有隐式全权访问模型与档案治理入口。该功能入口不授予业务数据范围、流程权限或代替业务提交人确认的权限。

### 11.3 确认、幂等与防串单

建单/登记先生成 `mcp_operation_intent`，提交时同时校验确认凭证与幂等键；确认解决、未解决重开和评价本身已是用户明确动作，直接建立同事务幂等意图，不再签发第二个凭证。所有动作绑定 ITOM 用户、工具和规范化参数摘要。确认解决和评价必须携带明确工单编号；存在多张待确认工单时 Aily 必须让用户选择，不能使用“最近一张”猜测。重复调用返回首次结果，不重复建单、关单、重开或评价；同键不同参数拒绝执行。

服务请求最终用户确认任务只允许提交人本人操作，管理员也不能代确认。网页、MCP 和飞书卡片回调均遵循同一领域规则：确认后关闭，未解决则携带原因回退到最近实际处理节点。Aily 主动消息接收人从该账号最近使用的活动飞书身份中选择，消息只含用户可见进展，不包含内部备注、根因或审批信息。普通对话仍以 Aily JWT 映射身份并走 MCP；卡片按钮是唯一例外。ITOM 先验证飞书回调签名、时效、Verification Token、Bot App ID，并要求回调头与 `operator` 的 `tenant_key` 一致。Aily JWT `tenant_id` 与卡片回调 `tenant_key` 是不同标识命名空间；二者不直接相等时，必须用 `operator.open_id/user_id/union_id` 在允许的机器人/Agent 应用范围内唯一找到“属于已授权 Aily 租户”的活动 `external_identity`，再由领域服务校验该账号确为工单提交人。未知跨命名空间身份直接拒绝；可直接识别租户下的未知身份可登记为 `pending` 候选后拒绝；多映射到不同账号时按歧义拒绝。卡片动作值不携带飞书标识、JWT、ITOM 内部主键或内部处理字段。

Task 8C Round 2：身份与权限边界不变；浏览器只有在 action expiry 同时显式使用 UTC `Z` 且日历有效时，才允许进入 `prepared` 展示状态。
